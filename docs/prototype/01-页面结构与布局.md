## 1. 路由结构

| 路由 | 页面 | 覆盖功能 | 备注 |
|---|---|---|---|
| `/` | 主工作台 | F-01 / F-02 / F-03 / F-04（列表侧） | 默认页，也是唯一的三栏页 |
| `/tasks` | 任务中心 | F-04（筛选 / 历史 / 分页 / 终止态） | 含**任务详情抽屉**（见 §4.4） |
| `/models` | 模型库 | F-05 | 含**导入模型弹窗**（见 §5.1） |
| `/hardware` | 硬件能力 | F-06 | |
| `/settings` | 系统配置 | F-07 | |
| `/:pathMatch(.*)*` | → 重定向到 `/` | — | SPA 兜底。**不单独设计 404 页**：Tab 主导航下用户几乎不可能手输错误路径，为它设计页面属过度工程 |

**导航**：顶栏 `MainNav` 常驻 5 个 Tab。选中态 = `bg-hover` 底 + `text-primary` + Medium 字重；未选中 = 无底 + `text-secondary` + Regular。**选中态不能只靠颜色**，字重同时变化。

**为什么不用侧边栏导航**：主工作台已经把左栏给了"素材与任务"，再加侧边导航会形成三层面板嵌套，与"以图片预览为主角、控件克制"（PRD §6.4）冲突。

## 2. 全局骨架

```
AppShell (fill, vertical)
├── TopBar                        固定高 56px
│   ├── Brand（标识 26×26 + 「WebSR」）
│   ├── TierBadge（档位胶囊，如「T1 · 消费级 8G」）
│   ├── MainNav（5 Tab）
│   ├── Spacer（fill_container，推开左右两组）
│   ├── EpBadge（当前生效后端，如「CUDA EP · fp16」）
│   └── ThemeButton（32×32 图标按钮）
└── PageContent                   高 = 100vh − 56px
```

**TopBar 规格**

| 项 | 值 |
|---|---|
| 高度 | 56 |
| 左内边距 / 右内边距 | 16 / 12 |
| 子项间距 | 12 |
| 背景 | `$:Theme:bg-panel` |
| 垂直对齐 | `counterAxisAlignItems: CENTER` |

**两条设计意图**

1. **档位与生效后端常驻顶栏**：这两项分别回答"我能跑什么"和"我现在在用哪个后端"。放在每一页都可见的位置，是 PRD §1.3「暴露真实硬件能力」与 §2.3 原则 3「档位对用户可见」的直接落点。
2. **Spacer 把状态与操作分到两侧**：左侧是"我是什么"（品牌 / 档位 / 导航），右侧是"当前状态 + 全局操作"（后端 / 主题）。避免用户在两堆不同性质的信息之间来回找。

## 3. P1 · 主工作台（三栏）

### 3.1 横向分配

| 区域 | 宽度 | 内容 |
|---|---|---|
| LeftPanel | **320 固定** | 上传区 + 任务列表 |
| DividerLeft | 1 固定 | 1px 竖线，`border-subtle` |
| CenterPanel | **fill_container** | 预览工具条 + 对比画布 |
| DividerRight | 1 固定 | 同上 |
| RightPanel | **340 固定** | 参数面板 + 底部操作区 |

> 用 1px 分隔帧而非 stroke，是为了让边框位置精确可控（stroke 四边统一，做不到"只画一条竖线"）。

### 3.2 LeftPanel（320）

```
LeftPanel (vertical, fill bg-panel)
├── LeftHeader        高 44  「素材与任务」 + 「清空已完成」
├── UploadWrap        padding 16/16/8
│   └── UploadZone    圆角 8，虚线位（border-strong），padding 20
│                     （上传图标 24 + 主文案 + 格式与大小说明）
└── TaskSection       fill_container
    ├── TaskHeader    高 40  「任务」+ 计数 + 「全部」
    └── TaskList      padding 16，gap 8，纵向滚动
        └── TaskCard  圆角 8，padding 10，gap 8
            ├── Row：缩略图 36×36 + Info(名称 / 元信息) + 操作按钮
            └── ProgressTrack（仅"进行中"态，高 4，胶囊圆角）
```

**关键点**：任务卡片的**元信息行承担状态表达**（进行中 → `link` 蓝 / 已完成 → `success` 绿 / 降级完成 → `warning` 黄 / 失败 → `error` 红 / 已取消 → `text-tertiary`），因此**不需要额外的状态标签**，卡片高度可保持在 56–80 之间。

### 3.3 CenterPanel

```
CenterPanel (vertical)
├── PreviewToolbar    高 52，padding 左右 24
│   ├── 标题组（文件名 13px + 尺寸与耗时 11px mono）
│   ├── CompareModeSwitch（分段控件：并排 / 滑块 / 局部放大）
│   └── DownloadButton（「下载结果」）
└── PreviewStage      fill_container，内容居中
    ├── CompareCanvas  730 × 410（16:9）
    │   ├── 原图区（左半）/ 结果区（右半）
    │   ├── 分割线（2px 白）
    │   └── 拖动把手（24×24 白圆 + 双向箭头）
    └── CompareLegend  左右两侧标注实际像素尺寸与所用模型
```

**为什么对比图是 16:9 而非撑满**：图片比例未知，撑满会在不同比例下反复改变画布尺寸，导致工具栏与图例位置跳动。固定 16:9 的**最大可视区**，实际图片按 `contain` 居中适配。

**为什么图例在下方而不叠在图上**：PRD §6.4 明确要求"避免在图片区域叠加过多浮层"——浮层会遮挡被判断的图像内容本身。

### 3.4 RightPanel（340）

```
RightPanel (vertical, fill bg-panel)
├── PanelHeader        高 52  「参数」 + 「重置」
├── PanelBody          fill_container，padding 16，gap 18
│   ├── Group · 放大倍数     2× / 3× / 4× 三选一（等分）
│   ├── Group · 模型         下拉选择器 + 一行约束说明（最低显存 / 当前可用 / 格式）
│   ├── Group · 执行方式     自动档开关 + 说明
│   ├── Group · 高级参数     tile / 精度 / EP（自动档开启时 opacity 0.5 + 「由自动档接管」）
│   └── Group · 本次决策     决策理由卡片
└── PanelFooter        固定底部，padding 16，gap 10
    ├── FallbackNotice 保底档提示（warning 色）
    ├── RunButton      高 40 主按钮「开始超分」
    └── EstimateText   预估耗时与输出尺寸
```

**三个关键设计意图**

1. **参数分组顺序 = 用户决策顺序**：先定放大倍数（目标），再选模型（手段），然后才是执行方式（由谁决定细节）。高级参数默认置灰，符合"渐进式披露"——复杂度在需要时才展开。
2. **「高级参数」置灰而非隐藏**：用户需要知道这三项存在、以及**此刻由自动档在管**。隐藏会让人以为产品不支持手动调参。
3. **「本次决策」卡片回答"为什么"**：PRD §1.3 核心价值 2 要求"明确告诉用户当前用的是哪个 EP、精度、分块尺寸，以及**为什么**"。这张卡片是"为什么"的落点。
4. **执行按钮固定在右栏底部**：主操作位置在所有页面状态下恒定（空态、加载中、有结果时都在同一位置），符合"稳定操作锚点"原则。

## 4. P2 · 任务中心

```
PageContent (vertical)
├── PageHeader        padding 32/32/24/16
│                     标题「任务中心」+ 副标题（条数与保留策略）
│                     右侧：汇总文字（mono）+「清理已完成」
├── FilterBar         状态 chips（全部 18 / 进行中 1 / 已完成 12 / 失败 2 / 已取消 3）
│                     + Spacer + 搜索框（220 宽）
└── TableWrap         padding 32/32/32
    └── TaskTable     圆角 8，描边 border-subtle，fill bg-panel
        ├── TableHead 高 40，fill bg-elevated
        ├── Row × N   高 48，7 列
        ├── TableSpacer  fill_container（把分页推到底部）
        └── TablePager   左「共 18 条 · 第 1 / 2 页 · 保留 30 天」+ 右「上一页 / 下一页」
```

**列定义（总宽 1344，不含单元格内边距）**

| 列 | 宽度 | 内容与对齐 | 字体 | 对齐 |
|---|---|---|---|---|
| 状态 | 110 | 进行中 / 已完成 / 降级完成 / 失败 / 已中断 / 已取消，按语义着色 | Noto Sans SC Medium 12 | 左 |
| 文件 | fill | 文件名（主行）+ 中屏合并进来的 `4× · W×H`（副行） | Inter 12 | 左 |
| 放大 | **88** | `4×` | JetBrains Mono 12 | 左（右边距 20） |
| 模型 / 后端 | **300** | `RealESRGAN_x4plus · CUDA fp16` | JetBrains Mono 11 | 左（左边距 20） |
| 耗时 | **120** | `12.4 s`；进行中显示 `3 / 12 块` | JetBrains Mono 11 | **右**（右边距 20） |
| 产出 | **180** | `7680 × 4320` | JetBrains Mono 11 | **右**（右边距 20） |
| 操作 | **176** | 取消 / 对比+下载 / 查看日志+降低倍数重试 | Noto Sans SC 11 | 右 |

**固定列合计 = 110 + 88 + 300 + 120 + 180 + 176 = 974**，文件列 `fill_container` 吸收剩余宽度（1344 − 974 = 370，页面 1440 下外层 padding 32×2 后实际约 430）。

> **三处列的修正（依据 5A 视觉审查实测）**
>
> 1. **列间距从"无"改为 20px 统一内边距**。初版所有列 `padding: 0`，导致相邻列的文本**紧贴在一起**——实测中 `4×` 与 `RealESRGAN_x4plus` 之间间隙不足 2px，视觉上连成一个词。现改为：左对齐的列加 `padding-left: 20`，右对齐的列加 `padding-right: 20`，形成规则的列沟。
> 2. **「耗时」「产出」改为右对齐**。这两列都是数值型（时间、像素尺寸），左对齐会让 `12.4 s` 与 `21.7 s` 的小数点错位，`7680 × 4320` 与 `3840 × 2160` 的位数参差。右对齐后两个数值的右边缘与「操作」列左边界对齐，形成**数值纵线**，扫描效率显著提高。
> 3. **「放大」保持左对齐而非右对齐**。「放大」列的值域只有 `2× / 3× / 4×` 三种且宽度一致，右对齐无收益；而右对齐会把它推到紧贴「模型 / 后端」列的位置，重新制造粘连。它与「状态」「文件」同属**标识型列**，统一左对齐。

> **表格不画行分隔线**：用行高（48）与留白区分。只有表头有 `bg-elevated` 底色。这是"避免依赖过多分割线制造层次"的落点。

### 4.1 行点击行为

**整行可点击**（操作列按钮除外，需 `stopPropagation`）→ 打开**任务详情抽屉**。行悬停态为 `bg-hover`，光标 `pointer`。

> 为什么需要它：列表行只能表达"状态"，无法承载 `TASK.resolved`（实际生效参数）、`TASK.error`（错误码）、产物清单与日志。详见 `04` §3。

### 4.2 状态枚举与界面文案对照

| `TASK.status` | 界面文案 | 颜色 | 主操作 |
|---|---|---|---|
| `pending` / `running` | 进行中 | `link` | 取消 |
| `canceling` | 正在取消 | `link`（按钮禁用） | — |
| `done`（无降档） | 已完成 | `success` | 对比 / 下载 |
| `done`（有降档） | **降级完成** | `warning` | 对比 / 下载 |
| `failed` | 失败 | `error` | 查看日志 / 降低倍数重试 |
| **`interrupted`** | **已中断** | **`warning`** | **重试 / 查看日志 / 清理** |
| `canceled` | 已取消 | `text-tertiary` | 重试 |

## 5. P3 · 模型库

```
PageHeader     标题「模型库」+ 副标题（共 N 个 · 当前档位可运行 M 个）
               右侧：「导入模型」主按钮
FilterBar      chips（全部 6 / 可运行 4 / 不可用 2）
GridWrap       padding 32，layout: wrap，gap 16
└── ModelCard  宽 448（3 列），高 hug_contents，垂直，padding 16，gap 10
    ├── CardHeader   模型名（mono 13）+ 格式徽标（右上）
    ├── ModelMeta    参数量 · 体积 · 倍数 · 格式细节
    ├── VramInfo     最低显存 · 当前可用 —— 可运行 / 不可用
    ├── ConditionalNotice（可选，仅条件支持项）
    └── CardActions  导出 ｜ Spacer ｜ 删除（error 色）
```

**置灰规则**：不可用模型整卡 `opacity: 0.55`（**不用 0.4 以下**——低于此值说明文字将不可读），并保留 `VramInfo` 行写明具体原因（"需 ≥ 24 GB 显存 · 当前 7.4 GB"）。**依据 PRD §2.3 原则 3：不能让用户点了才失败。**

**条件支持标注**：`.bin` 的 ncnn 来源在卡片内以 warning 色提示"待验证，不计入 v1 承诺"，与 PRD §7.5 的措辞保持一致。

### 5.1 导入模型弹窗（两级）

**为什么必须有**：PRD §7.5 规定模型有 **4 种格式路由**（`.onnx` / OpenVINO IR / `.pth`+`.safetensors` 离线转换 / `.bin` 双来源分派），tech-arch §5.2 定义了 `MODEL_MISSING_COMPANION`、`FORMAT_MISMATCH` 错误码。若只放一个「导入模型」按钮而不定义流程，用户拿到 `.pth` 将无处可去。

**一级：文件选择与格式识别**

```
Dialog「导入模型」宽 560
├── FileDrop        拖拽区（同上传区规格，border-strong）
├── FormatDetect    识别结果行：文件名 · 识别格式 · 配套文件状态
│                   ✅ 配套完整 / ⚠️ 缺失配套（红字说明缺哪一个）
└── Actions         取消 ｜ 下一步（识别失败时禁用）
```

| 识别结果 | 下一步行为 |
|---|---|
| `.onnx` | 直接进入二级的元信息填写 |
| `.bin` + 同名 `.xml` | 判定为 **OpenVINO IR**，进入二级 |
| `.bin` + 同名 `.param` | 判定为 **ncnn**，进入二级，并**强制附加条件支持提示**（PRD §7.5：ncnn 按"条件支持"表述，Windows/Python 可用性未验证） |
| `.bin` 无配套 | **阻断**，报 `MODEL_MISSING_COMPANION`：「缺少配套文件（需要同名 `.xml` 或 `.param`）」 |
| `.pth` / `.safetensors` | **转入"离线转换指引"分支**（见下） |
| 其他 | **阻断**，报 `UNSUPPORTED_FORMAT` |

**离线转换指引分支（`.pth` / `.safetensors`）**

按 ADR-003，此类格式**不捆绑 PyTorch**，必须由用户在自带环境离线转换。弹窗内展示三步指引：

1. 说明「本应用不含 PyTorch 训练/转换栈，需在您的环境中完成转换」
2. 给出转换命令模板（`torch.onnx.export(...)`，操作数、动态轴、opset 版本按模型填）
3. 提示「转换完成后，回到本弹窗导入生成的 `.onnx`」

> **不给「自动转换」按钮**，因为应用内不装 PyTorch（ADR-003 硬约束）。这里如实告知，优于给一个点了会失败的按钮。

**二级：元信息填写**

| 字段 | 校验 |
|---|---|
| 显示名称 | 非空；与已有模型重名时**触发冲突处理**（见下） |
| 参数量 / 体积 | 自动读取，只读展示 |
| 放大倍数 | 必填，正整数 |
| 最低显存 `min_vram_mb` | 必填，正整数。用于按档位置灰（PRD §2.3 原则 3） |
| 后端支持集合 | 多选：ORT CPU / ORT CUDA / OpenVINO。用于 `MODEL.supported_backends` |

**重名冲突处理（`04` §5 已定义，此处为落点）**：检测到同名模型时不静默覆盖，弹出三选一——**重命名 / 覆盖 / 取消**，并写明「覆盖将替换 `data/models/` 下的同名文件，不可恢复」。

## 6. P4 · 硬件能力面板

```
PageHeader   标题「硬件能力」+ 副标题（实读值非标称值）

ContentWrap  padding 32，gap 16
├── TierCard      档位卡：大徽标(T1) + 标题 + 判定依据（整行，横向）
├── TwoColumn     左右等分，gap 16
```

## 7. P5 · 系统配置

```
PageHeader   标题「系统配置」+ 副标题 + 「保存」主按钮
ContentWrap  padding 32，gap 16
├── SectionCard · 存储与数据
│     数据根路径（输入框，宽 420）／ 模型目录（只读说明）／ 任务保留 ／ 上传上限
└── SectionCard · 执行与性能
      并发度上限 ／ 日志级别 ／ 首启自标定状态 ／ 档位模拟开关
```

**每行统一为 `SPACE_BETWEEN` 的 key-value 结构**（key 左、值右）。需要输入的项用 `bg-elevated` 的输入框容器，纯展示项用等宽文字。这个行模式在 P4 / P5 两个页面复用。

### 7.1 档位模拟开关的强制可见性（不可省略）

PRD §2.3 要求提供 `force_tier` / `force_vram` / `force_has_tensorrt` 三个模拟开关，用途是"在 T1 上执行 T2/T3 代码路径"。**但这带来一个安全风险：模拟态下的档位徽标会显示一个用户的机器实际不具备的档位。**

因此模拟开启时必须有**全站级、不可忽略**的区分：

| 位置 | 表现 |
|---|---|
| 顶栏 `TierBadge` | 文案改为「T1 · **模拟 T3**」（`warning` 底 + `warning` 文字），**不是**直接显示 T3 |
| 全局横幅 | 在 `PageContent` 顶部插入一条 `warning` 色横幅（高 32）：「档位模拟已开启 · 当前显示的能力不代表真实硬件」，带「关闭模拟」按钮 |
| P4 硬件能力 | `TierCard` 的"判定依据"改为写明模拟来源，并标注真实探测值 |
| P5 该行 | 值域显示「开启 · **模拟中**」（`warning` 色），辅助文字保持"仅开发者测试用，不代表真实能力" |

> **为什么不能只靠 P5 那一行的开关状态**：用户开启模拟后可能立刻跳到主工作台或硬件页。若警示只留在 P5，用户在这两页看到的就是一个**错误的能力声明**——这与 PRD §1.3「暴露真实硬件能力」直接冲突。警示必须跟着档位徽标走。

## 8. P6 · 主工作台空态
