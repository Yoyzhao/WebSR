## 1. 这是什么

本目录是**步骤 5A 的前端原型产出**，用途是**冻结 S1 的界面方案**，使步骤 5C 可以按图落地，而不必在编码阶段重新决定颜色、间距、圆角、布局骨架与组件选型。

**设计稿本身是可编辑的**：颜色与尺寸全部绑定在设计变量上（`Theme` 含 Dark / Light 两个模式），切换模式即可整套换肤，页面结构不做任何改动。

**范围**：S1 首发切片 —— F-01 单图超分、F-02 参数配置、F-03 对比预览、F-04 异步任务中心、F-05 模型库、F-06 硬件能力面板、F-07 系统配置。F-11（分块羽化）无独立界面，其过程通过任务进度的"正在推理 N / M 块"文案体现。

**不在本阶段**：S2（自标定、批量、预设、产物管理、微调支持）与 S3（P3 档位能力）的界面。注：F-10 自标定虽属 S2，但其**状态入口**（标定状态与"重新标定"按钮）已在硬件面板与系统配置中预留，因为 S1 期间的"保底档"必须对用户可见。

### 2.1 设计稿本体与导出归档（重要）

| | 位置 | 性质 |
|---|---|---|
| **可编辑设计稿** | **云端在线文件**（`WebSR 前端原型 · S1`，fileId `731432065276167`） | **本体**：含图层树、组件结构、28 个设计变量（Dark / Light 双模式）。可继续编辑。**不在仓库内** |
| **导出归档** | `docs/prototype/assets/*.svg`（7 页） | **快照**：由设计稿导出，非截图。随仓库交付、可离线查看 |
| **Token 导出** | `docs/prototype/tokens.css` | 设计变量的 CSS 形式，供 5C 直接复用 |

**归档时点**：2026-09-30（步骤 5A 完成）。若后续修改云端设计稿，需重新导出并更新归档，否则快照会与本体脱节。

**为什么只保留一种格式**：SVG 是栅格图的**信息超集** —— 它同时携带矢量几何与精确十六进制色值（逐值对齐 `tokens.css`），且分辨率无关。归档同一内容的 PNG 属于格式冗余，已移除。代价是 SVG 在缺失字体时回退渲染，但结构完整性不受影响，浏览可读性不变。

> ⚠️ **两条实现约束（供 5C 注意）**
> 1. 归档 SVG 的目的是**可追溯的设计证据**，**不是**切图资源。5C 应从 `tokens.css` 取色值、按 `01`/`02` 的规格写代码，**不要**从 SVG 反推样式或直接内嵌。
> 2. 导出精度曾出现过偏差（设计变量以浮点存储，导出时 `tokens.css` 走 `round`、SVG 走 `floor`，导致同一色值差 1 级）。现已通过把变量取值为 `(n + 0.25) / 255` 使两条导出路径同时精确还原。**若今后修改颜色变量，请沿用该取值方式**，否则归档色值会与 token 再次出现偏差。

## 5. 设计决策依据（为什么是这样）

| 决策 | 依据 |
|---|---|
| 顶栏放 5 个主导航 Tab，而非仅图标入口 | WebUI 原则"导航可预期"。模型库 / 硬件 / 配置是独立页面，仅靠图标入口会使用户迷路 |
| 深色为默认主题（PRD §6.4 原本待定） | 图像对比类工具的行业惯例（Photoshop / Lightroom / Figma 均为深色），深色背景不干扰对图像色彩与亮度的判断 |
| 主强调色为 `#0078D4`（Windows 蓝） | 运行环境为 Windows 11，且语义化色彩规范要求"蓝色用于信息与主要操作"。**禁止彩虹强调色**，全站唯一强调色 |
| 数值一律用等宽字体 + `tabular-nums` | 显存 GB、tile、耗时 ms、节点数、sha256 会大量出现；比例字体下数字宽度不等会导致刷新时跳动 |
| 参数面板把"自动档"置顶、"高级参数"置灰 | 产品语义：自动档只接管 tile / 精度 / EP 三项；开启时这三项由引擎决定，手动调它们没有意义。置灰比隐藏更好——用户需要知道"它存在但现在由谁在管" |
| 硬件面板必须有"EP 真实性证据"表 | PRD §2.5 F-06 验收标准硬性要求"展示的执行提供器必须有 profile 节点归属作为证据"。这是防静默回退的唯一手段，不是可选装饰 |
| 保底档提示出现在主工作台底部与系统配置两处 | PRD §1.4 要求"当前正处于保底档必须对用户可见"。放在执行按钮正上方，是因为它直接影响用户对本次耗时的预期 |

## 8. 5C 后 UI 调整记录（2026-10-08）

前端实现完成后，用户在实际 2K 显示器上使用并提出两项问题，均已修复并复验。

### 8.1 默认字号偏小（2K 下阅读吃力）

**根因不止是字阶偏小**：`tokens.css` 定义了 `--font-size-*`，但组件内 **111 处字号是硬编码 px**、token 仅被引用 14 次 —— 直接改 token 几乎不会生效。

**处置（三步，顺序不可颠倒）**：

1. **先收敛硬编码**：125 处 `font-size` 全部改为 token 引用（111 处 px + 14 处已有引用）。**不先做这一步，后续调整无效**；
2. **字阶整体上调一档**：采用**重新编号**而非「改值不改名」，token 名始终等于像素值 —— `10/11/12/13/15/18/24` → `11/12/13/14/16/20/26`；
3. **布局尺寸同步上调**：顶栏 `56→60`、表格行 `48→52`、输入框 `36→40`、图标按钮 `32→36`。面板宽度保持不变（加宽会直接挤占工作台中栏的预览面积）。

实体影响：`body` 字号 `13 → 14px`（原为硬编码，现指向 `--font-size-14`）。

### 8.2 独立页内容宽度不一致

**根因**：`PAGE_MAX_WIDTH` 原为逐页差异化（tasks 1344 / models 1408 / hardware 1200 / settings 880），切换页面时内容区左右边界跳变。

**处置**：统一为 **1344**（`constants.ts` 改一处即全站生效）。

**连带调整**（不处理会引入新问题）：容器放宽后，`SettingsRow` 的「label 左 / 值右」两端对齐会让二者相隔近千像素。

| 页面 | 原问题 | 处理 |
|---|---|---|
| P5 系统配置 | 单列下 label 与值相隔约 900px | 改为 **grid 双列**（每列约 630px） |
| P4 硬件能力 | 卡片全宽单列（约 1288px），同样脱离 | `SettingsRow` 增加**容器查询**：卡体 ≥ 1000px 时改为「固定 220px label 列 + 值左对齐」 |

**实测复验（1600 视口）**：四页容器均为 `1344`、`left=128`、右侧留白 `128`，**完全一致**；设置页 `635 + 635` 双列；硬件页 `SettingsRow` 为 `grid 220px / 1002px`、值左偏移 `236px`；工作台窄栏（约 300px）正确保持 `flex + space-between`，**无回归**。响应式三档 `1344 / 1280 / 900` 逐档收敛。

### 8.3 一处 CSS 陷阱（已写入 `05` §2.2）

`@container` 覆盖块**必须置于样式表末尾**。它要覆盖 `.settings-row` 与 `.settings-row__value` 的基础声明，而两者特异性相同（0,1,0），胜负由**书写顺序**决定。首次实现时误置于基础声明之前，症状为 **「明明变成了网格、值却仍贴在右侧」**（`display: grid` 生效，但 `align-items` / `text-align` 被后面的基础样式覆盖）。

### 8.4 未处理（待用户判断）

**顶栏导航按钮宽窄不一**：`.tb-link` 由文字宽度撑开，「工作台」「模型库」（3 字）`66px`，其余（4 字）`80px`。用户本次确认修复范围是「页面内容宽度上限」，故未改动。

### 8.5 工作台参数面板的对齐修正

**用户反馈**：「参数选择这部分，文字和选项看着有点乱」。

**实测定位出三个客观缺陷**（参数卡片卡体仅约 280px）：

| # | 缺陷 | 实测证据 |
|---|---|---|
| 1 | **控件左边界逐行错位**（锯齿） | 两端对齐下各控件贴右：自动/手动 104px、256/384/512 155px、fp32/fp16 95px —— 左边界各不相同 |
| 2 | **后端选项折行且不齐** | 4 个按钮合计 247px > 可用 228px，`flex-wrap` 折成 **3 + 1**，第二行仅一个按钮孤立 |
| 3 | **hint 右对齐且出现孤字** | 「…由引擎按实测标定决 / 定」，末行只剩一个字 |

**处置**（`web/src/views/WorkbenchView.vue`）：

- 窄栏参数行改为**固定 label 列（64px）+ 控件左对齐**
- 后端选项改**固定 2×2 网格**（原为 `flex-wrap` 自然折行）
- hint 加 `text-wrap: balance`，折行按长度均衡
- 同一套规则同时覆盖**窄屏参数抽屉**（`ElDrawer`，320px），两处表现一致

**实测复验**：

| 指标 | 改前 | 改后 |
|---|---|---|
| 控件左边界 | 逐行错位 | **全部对齐**（左栏 x=127 ／ 抽屉 x=94） |
| 后端按钮宽度 | 49 / 78 / 42 / 78（3 + 1 行） | **96 / 96 / 96 / 96（2×2）** |
| 参数卡片高度 | 516px | 542px（仅 +26px，未变臃肿） |

**为什么用局部覆盖而不是改 `SettingsRow`**：中宽卡体（设置页双列 630px）下两端对齐观感正常，且其值多为短文本，不存在「控件左边界锯齿」问题。改动共享组件会波及 3 个页面，收益不成比例。

**由此显形的规律**：`SettingsRow` 的两端对齐**只在中间宽度成立** ——
过窄（< 400px）控件左边界错位，过宽（≥ 1000px）label 与值相隔过远，
**两端都需要改为「固定 label 列 + 左对齐」**。这条规律已记入 `05` §2.2 的连带调整说明。

### 8.6 参数面板的语义分组线

**用户建议**：「做成卡片式或者使用分割线分隔开是不是好一点」。

**先摆出约束**：设计基线取向明确 ——「**用层级而非分割线建立层次**」（`02` §32；禁止事项第 7 条亦为「用留白而非分割线制造层次」）。因此不能直接照做，要先判断这是「基线之外的合理诉求」还是「基线已解决的问题」。

**做法：把候选方案实际渲染出来对比**（运行时注入样式，不改源码），而不是凭偏好取舍：

| 方案 | 卡片高度 | 结论 |
|---|---|---|
| 当前（无分隔） | 542px | 行边界弱 |
| 每行分割线 | ~760px | 边界最强，但 **+40% 高度逼出滚动**，且与基线正面冲突 |
| 卡片式（`bg-elevated` 无描边） | ~760px | **实测更差**：内填 padding 压缩内容宽（272 → 248px），hint 折行增多；6 个嵌套卡片层级过重 |
| **语义分组线（采纳）** | **563px** | 1 条线分清「可调」与「自动档接管」，仅 +21px |
| 纯增大行距 | 590px | 不引入线、最贴基线，但边界感弱于线条 |

**最终落地**：只在**第 4 行前**加一条线 ——

- 组 1（1–3 行）：自动档 / 模型 / 放大倍数 —— 由用户直接决定
- 组 2（4–6 行）：分块 tile / 精度 / 后端 —— 「自动档」打开时由引擎接管
- **组内仍靠留白**，线只用于标记**语义边界** → 不与「用留白制造层次」的基线相悖

**为何不逐行加线**：6 条**等权重**的线会稀释「这 6 项里哪 3 项会被自动档接管」这个真正要传达的信息 —— 线越多，重点越模糊。

**实测**：仅第 4 行为 1px 线（`#2e2e2e`），其余 0px；控件左边界仍全部对齐 `x=127`（无回归）；左栏与窄屏抽屉表现一致。

**方法论沉淀**：面对「是不是更好」这类主观提议，**既不要凭偏好取舍，也不要用规则挡回去** ——
把候选方案实际渲染出来，用「高度 / 溢出 / 折行」等客观量排序，再结合设计基线判断。
本次正是靠「每行加线会 +40% 高度、逼出滚动」这个数字，否掉了「都加线更清晰」的直觉。
