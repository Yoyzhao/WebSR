# 04 · 状态与交互定义

> 步骤 5A 产出（5B 将在此基础上补齐字段级契约）｜ 最后更新：2026-09-30

---

## 1. 主流程（F-01 / F-03）

```
上传 ──▶ 预处理校验 ──▶ 提交任务（返回任务号） ──▶ [异步] 引擎决策 ──▶ 分块推理 ──▶ 拼接羽化
                                                            │                        │
                                                    进度事件推送                     ▼
                                                            │                 结果落盘 + 缩略图
                                                            ▼                        │
                                                    进度条与阶段文案 ◀───────────────┘
                                                                                     │
                                                          对比预览 ◀─────────────────┘
                                                              │
                                                          下载 / 清理
```

### 界面时序

| 步骤 | 触发 | 界面表现 | 约束 |
|---|---|---|---|
| 1 | 拖入 / 选择文件 | 上传区进入上传中（进度）；左侧任务列表插入一条"排队中" | 前端先做扩展名与大小校验，不合格立即拒绝，不发起上传 |
| 2 | 上传完成 | 中栏立即显示**原图**与真实像素尺寸；右栏参数面板由"不可用"变为可用 | 不等待推理 |
| 3 | 点「开始超分」 | 提交请求；**≤ 1 s 内返回任务号**（NFR §3.1） | 提交不带推理，立即返回 |
| 4 | 任务入队 | 任务卡片进入"进行中"；进度条出现 | 进度事件间隔 **≤ 1 s** |
| 5 | 推理中 | 进度条 + 阶段文案（「正在推理 3 / 12 块 · tile 512」）；两级进度以 item 为准 | 进度**单调不减** |
| 6 | 完成 | 中栏自动切入对比视图（默认**滑块**模式）；任务卡变"已完成"并显示耗时与产出尺寸 | 切换不打断用户当前操作，若用户正在看别的任务则不抢焦点 |
| 7 | 下载 / 清理 | 下载结果文件；或清理中间产物 | — |

### 参数变更提示（PRD §6.1-5）

任一参数改动后，**在参数面板内出现「参数已修改，需重新执行」提示**（`warning` 色，位于执行按钮上方）。提示不阻塞任何操作——用户可以继续改，提示一直存在，直到重新执行或重置。

> 为什么不做成自动重跑：CPU 档单图需数分钟（PRD §1.3），自动重跑会让用户在不经意间消耗大量算力。

## 2. 六种状态定义

> **为什么是六种**：原五态（空 / 加载 / 异常 / 降级 / 取消）漏掉了后端进程崩溃重启后产生的 **`interrupted`（已中断）** 态。该态由 `TASK.status` 枚举定义（tech-arch §4.1），且**必然发生**（非边缘场景）——若不定义界面表现，前端收到未知枚举值会显示空白或抛错。

### 2.1 空态

| 位置 | 表现 |
|---|---|
| 左栏任务列表 | 居中：图标 32 + 「暂无任务」+ 「上传图片并执行后，任务会出现在这里」 |
| 中栏 | 拖拽区 600 × 380，图标 48 + 「拖拽图片到此处，或点击选择」+ 支持格式与大小 + 保底档提示条 |
| 右栏参数面板 | 保留骨架，内容为「参数暂不可用」说明卡（`opacity: 0.6`）+ 跳转硬件页的引导链接 |
| 模型库 / 任务中心 | 各自的 `EmptyState`（图标 + 说明 + 一个可执行动作，如「导入模型」） |

> 三栏各自回答不同问题：左栏说明"结果会出现在哪"，中栏说明"能做什么"，右栏说明"为什么现在不能用"。**空态不是空白页。**

### 2.2 加载态

| 场景 | 表现 | 关键约束 |
|---|---|---|
| 上传中 | 上传区进度 | 走 `el-upload` 的进度 |
| 推理中 | 进度条（高 4）+ 阶段文案 + 右上角百分比 | **两级进度**：item 级（当前第几张）与 chunk 级（当前第几块）；`percent` 以 **item** 为准，chunk 用于阶段文案 |
| 模型列表首次加载 | 骨架屏（`el-skeleton`） | PRD §6.2 明确要求 |
| 任务列表加载 | 骨架屏（3 条占位） | — |
| 硬件探测中 | 面板内局部 loading，**不阻塞整页** | 能力探测为非阻塞（tech-arch §6.6 启动序列） |

**进度条不做无限循环动画**——真实进度必须与动画区分开，否则"卡住"与"正在跑"无法分辨。

### 2.3 异常态

| 异常 | 表现 | 下一步动作 |
|---|---|---|
| 上传失败 / 格式不支持 | 上传区内联错误（`error` 色）+ 具体原因（如「不支持的格式 .gif」） | 重新选择 |
| 文件过大 | 「文件 128 MB 超过上限 50 MB」 | 重新选择 |
| 推理失败（显存不足） | 任务行状态「失败」+ 原因「自动降档 2 次后仍显存不足」 | **「查看日志」+「降低倍数重试」**（后者为主按钮） |
| EP 未生效（静默回退） | **顶栏 EP 徽标改变** + 硬件面板判定列标红 + 异常事件落盘 | 无需用户操作，但**必须可见**（不得静默） |
| 服务不可达 | 全局 `el-message` + 受影响区域的错误态 | 重试 |

**错误信息三要素**（PRD §5 统一错误体）：错误码 + 可读消息 + **排查建议**。界面只展示可读消息与建议，错误码放在"查看日志"详情里。

### 2.4 降级态（本项目特有，必须可见）

| 场景 | 表现 |
|---|---|
| 保底档（冷启动，未标定） | 主工作台右栏底部 + 空态页 + 系统配置三处提示：「当前为保底档 · 标定完成后自动切换实测参数」（`warning`） |
| OOM 自动降档 | 任务行标注「已降档 tile 256」，任务仍标记为完成但状态文字用 `warning`（**不是** `success`） |
| 参数被自动档接管 | 高级参数三项置灰，值显示「自动 · 保底 512」等，并标「由自动档接管」 |
| 模型不可用 | 卡片整卡 `opacity: 0.55` + 卡片内写明「需 ≥ 24 GB 显存 · 当前 7.4 GB —— 不可用」 |

> **`project-rules` §2.2-5：降级必须显式，不得静默降画质；用户须能知道自己当前处于哪个档位。** 因此"降级完成"在状态语义上**不等于**"成功"——它用 `warning` 而非 `success`。

### 2.5 取消态

```
点「取消」 ──▶ 状态置 canceling（显示「正在取消」）──▶ 推理中断 ──▶ 资源释放 ──▶ 归入「已取消」
```

| 约束 | 值 | 依据 |
|---|---|---|
| 从点击到资源释放 | **≤ 2 s** | PRD §2.5 F-04 |
| 取消中表现 | 状态文字「正在取消」+ 取消按钮变为禁用 | — |
| 取消后 | 任务归入"已取消"，卡片提供「重试」 | — |
| 中间产物 | 清理 | PRD §2.6 异常分支 |

**协作式取消**（tech-arch / ADR-005）：推理在块与块之间检查取消标志，因此取消的生效时机是"当前块跑完之后"。界面文案使用「正在取消」而非「已取消」，正是为了如实反映这个中间态——**不能让用户以为点了就立刻停了**。

### 2.6 已中断态（`interrupted`，启动回收产生）

**来源**：后端进程崩溃 / 被杀 / 断电后重启，启动序列会扫描 `status ∈ {running, canceling}` 的任务并回收为 `interrupted`（tech-arch §4.1、§6.6 启动序列）。这是**运行时必然发生**的场景，不是边缘情况。

> **v1.0 口径修正（2026-10-10，T-700）**：早期稿写作 `{pending, running, canceling}`，但
> **v1 无 `pending` 状态**——任务落库即 `queued`（`manager.submit`），启动回收只扫 `running` / `canceling`。
> 契约 v1.0 §3.1 已以服务端枚举为准冻结。

| 位置 | 表现 |
|---|---|
| 状态文字 | 「已中断」（`warning` 色，**不是** `error`——它不是推理失败，是外部原因导致的非正常结束） |
| 原因说明 | 「上次运行被异常终止（进程退出）」 |
| 可执行动作 | **「重试」**（主按钮）+「查看日志」、「清理」（清理可能残留的中间产物） |
| 进度条 | 不显示（进度已失去意义），仅保留中断时最后的位置说明「中断于 3 / 12 块」 |
| 产物 | 若已有完整输出 → 仍可「对比」；若无 → 只剩重试 |

**与「失败」的区别（不可混淆）**

| | 失败（`failed`） | 已中断（`interrupted`） |
|---|---|---|
| 成因 | 推理本身的错误（显存不足、模型损坏） | 外部因素（进程退出、断电） |
| 颜色 | `error` | `warning` |
| 主操作 | 「降低倍数重试」（需改参数） | 「重试」（参数通常无需改） |
| 依据 | PRD §2.6 异常分支 | tech-arch §4.1 状态枚举 |

> **实现提示（5C）**：`StatusText` 组件的 `status` prop 必须接受 `interrupted` 值，且**未知枚举值的兜底策略是显示原值 + `text-tertiary`**，绝不抛错或留空。

## 3. 任务详情抽屉（F-04 的必需承载）

**为什么必须有**：`GET /api/tasks/{id}` 返回 `params`（请求参数）+ `resolved`（**实际生效**的 tile / 精度 / EP）+ `error`（完整体），`GET /api/tasks/{id}/artifacts` 返回产物清单（tech-arch §5.3、§4.1）。这些字段**目前在界面上没有任何落点**——任务中心只有列表行。

**为什么是抽屉而非独立页**：与列表同源、不新增路由、可复用 `05` 已定义的小屏降级规则（`el-drawer` 已是本项目的既定模式，见 `03` §3）。

**入口**：P2 / P9 任务中心的**整行可点击**（操作列按钮除外，需 `stopPropagation`）；P1 左栏任务卡点击卡片主体。

**分四个区段（Tab 或纵向堆叠，窄屏改用纵向堆叠）**

| 区段 | 内容 | 数据来源 | 关键约束 |
|---|---|---|---|
| **① 执行概览** | 文件名、原图尺寸、放大倍数、耗时、产出尺寸、时间戳 | `TASK` + `ARTIFACT` | — |
| **② 实际生效参数** | **请求值 vs 生效值 对照**：tile / 精度 / EP，以及「降档次数」与每次降档的原因 | `TASK.params` ↔ `TASK.resolved` | ⚠️ **这是"降级必须显式"的唯一证据位**。两者不同的项必须高亮（`warning`），并写明为何不同（如「显存不足，512 → 256」） |
| **③ 错误详情** | 错误码 + 可读消息 + 排查建议（PRD §5 错误三要素） | `TASK.error` | `04` §2.3 已规定"错误码放在详情里"——本区段即该出口。无错误时显示「本次任务无错误」 |
| **④ 产物** | 产物列表：类型（输出 / 中间）、路径、尺寸、体积；输出可下载、**中间产物可清理** | `ARTIFACT` | PRD §2.6 要求"可清理中间产物"；中间产物标注 `warning` 色并写明"可安全删除" |
| **⑤ 日志** | 按级别过滤的日志行；支持复制与下载 | 后端日志（含错误码） | `03` §6 / `01` §159 / `04` §2.3 三处引用的"查看日志"**均指向本区段**。默认只显示 `warning` 以上级别 |

> **`resolved` 是"自动档"唯一可验证的输出**：用户开了自动档后，tile / 精度 / EP 三项由引擎决定。若不给用户看 `resolved`，"自动档"就成了黑箱，直接违背 PRD §1.3 核心价值 2（"明确告诉用户当前用的是哪个 EP、精度、分块尺寸，以及**为什么**"）。

## 4. 反馈机制

| 操作 | 反馈 | 延迟要求 |
|---|---|---|
| 点击「开始超分」 | 按钮立即进入 loading + 任务卡出现 | ≤ 1 s |
| 参数改动 | 「参数已修改」提示出现 | 即时 |
| 切换对比模式 | 画布切换，不重新加载图片 | 即时 |
| 拖动分割滑块 | 两侧严格对齐跟随 | 实时（60fps 目标） |
| 删除模型 | 二次确认弹窗（写明模型名与是否可恢复） | — |
| 清空已完成 | 二次确认（写明将删除的任务数） | — |
| 保存配置 | `el-message` 成功提示 + 按钮短暂成功态 | — |
| 导出诊断 JSON | 触发下载 + 成功提示 | — |

**没有任何交互可以"没有反馈"**。

## 5. 危险操作保护

| 操作 | 机制 |
|---|---|
| 删除模型 | 二次确认；文案说明「该模型文件将从 `data/models/` 移除，不可恢复」 |
| 清空已完成任务 | 二次确认 + 显示数量；说明同时会删除结果文件 |
| 覆盖同名模型导入 | 导入时检测重名，提示"已存在同名模型"并提供"重命名 / 覆盖"两个选项，不静默覆盖 |
| 修改数据根路径 | 保存前提示"已有任务仍指向原路径"，不自动迁移 |
| 清理中间产物 | 二次确认；说明"仅删除中间产物，输出结果保留，但下次无法从断点继续" |
| 中断任务的重试 | 若上次为 `interrupted` 且已有完整输出，重试前提示"将覆盖现有结果" |

## 6. 表单校验

| 字段 | 校验 | 时机 |
|---|---|---|
| 上传文件 | 扩展名白名单（jpg / png / webp / bmp / tif）+ 大小 ≤ 50 MB；**服务端二次校验真实格式，不信任扩展名** | 前端即时 + 服务端兜底 |
| 上传文件 | 实际格式与扩展名不符 → 明确报错并说明实际格式 | 服务端返回后 |
| 数据根路径 | 非空、目录可写 | 失焦 + 保存时 |
| 任务保留天数 | 正整数，≥ 1 | 实时 |
| 并发度上限 | ≥ 1 且不超过探测出的上限（上限由可用内存反推，**不写死**） | 实时 |

**默认值优先于校验**：能给出合理默认值的字段一律预填，减少用户输入（防错优先）。

## 7. 键盘与无障碍

| 项 | 要求 |
|---|---|
| 焦点可见 | 所有可交互元素必须有可见焦点环（`border-strong` 或 `primary` 描边） |
| 图标按钮 | 必须有 `aria-label`（主题切换、硬件、设置） |
| 状态传达 | **不只靠颜色**：任务状态有文字、模型不可用有原因文字、降级有数值说明 |
| 点击热区 | 图标按钮 ≥ 32×32；表格内按钮 ≥ 28×24（含内边距） |
| Tab 顺序 | 按视觉顺序：顶栏 → 左栏 → 中栏 → 右栏 |
| 对比滑块 | 支持键盘左右方向键调整分割位置（`el-slider` 的键盘能力无法用于自绘组件，需自行实现 `role="slider"` + `aria-valuenow`） |
| 焦点管理 | 模态/抽屉打开时焦点移入并在关闭后归还；任务完成时**不自动抢焦点** |

## 8. 与 5B 的交接

本文件定义了**状态的分类、表现与约束**。5B 需要在此基础上补齐：

1. **字段级契约**：每个状态对应的 API 字段与取值（如 `TASK.status` 的枚举值到界面文案的映射表）；
2. **SSE 事件到界面状态的映射**：`item` / `chunk` 两级进度事件如何驱动进度条与阶段文案；
3. **错误码清单**：`docs/tech/api-contract.md` 中的错误码 → 界面文案的对照表；
4. **边界态**：断线重连后的进度恢复、页面刷新后的任务列表恢复、`canceling` 超时后的兜底。
5. **`interrupted` 的产生时机**：启动回收的具体触发条件、是否可配置、与 `canceling` 的关系（见 `04` §2.6）。
6. **日志接口**：任务详情抽屉的「日志」区段依赖一个尚未在 `api-contract.md` 中定义的日志拉取端点，需在 5B 补齐。
