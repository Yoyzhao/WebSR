## 2. 执行中发现并修复的缺陷（4 个）

### D1 · `F-02` 倍数不校验：主链路上用户可见的必然失败（🔴 P0）

- **现象**：请求 `scale=2` 配 ×4 模型 → 任务被接受，跑到推理时报通用
  `INTERNAL_ERROR / 推理执行失败 / 请导出诊断 JSON`（真实原因藏在 `detail.exception`：
  块结果尺寸不匹配）。用户无法从错误体得知该做什么。
- **根因**：`TaskParamsIn.scale` 只声明 `int`，无与 `model.scale` 的交叉校验；前端倍率控件
  有 ×2/×3/×4 三档且不受模型约束，而内置模型全是 ×4。
- **修复**：
  - 服务端 `tasks/manager.py::submit()`：门控后**前置拒绝**（`VALIDATION_ERROR` + 三要素齐全 +
    文案含模型真实倍数，`model.scale` 未声明时不校验——宁可放行不误拒）；
  - 前端 `WorkbenchView.vue`：倍率选项按模型置灰 + 提示原因 + `watch` 自动对齐。
- **回归**：`TC-S1-014` 全 5 条断言 + `TC-S1-015` 全 4 条断言通过。

### D2 · 模型导入 100% 失败：跨卷落盘（🔴 P0）

- **现象**：`POST /api/models/import` → **500**。日志：`OSError [WinError 17] 系统无法将文件
  移到不同的磁盘驱动器`（`C:\…\Temp` → `E:\…\data\models\imported`）。
- **根因**：路由层临时文件落在 `%TEMP%`（C:），数据目录在项目盘（E:）；
  `Path.replace` → `os.rename` **无法跨卷**。`.pth`/`.safetensors` 离线转换产物走同一路径，一起挂。
- **修复**：`model_registry.py::_move_into_place()` —— 同卷 `os.replace`（原子），
  `OSError` 时回退 `shutil.move`（跨卷复制+删除）。
- **回归**：导入 → 201 → 两张图真实跑通（`2048×2048` / `1280×960`）。

### D3 · 既有回归脚本的同卷隔离掩盖了 D2（测试体系缺陷）

- **现象**：`verify_t604_models.py` 的导入用例一直 43/43 全绿，真实环境却 100% 失败。
- **根因**：`t604` 把 `APP_DATA_DIR` 也设在系统临时目录 → 与上传临时文件**同卷** →
  永远走不到跨卷分支。与 `T-703` 记下的「断言把缺陷固化成了期望」同类。
- **修复**：新增段 `6b` —— 显式构造「系统临时目录 → 项目盘」移动并断言（44 断言全绿）。

### D4 · `F-06` 面板「实读」实为启动时刻快照，会话内漂移超阈（🟠 P1，全量回归批次中逮到）

- **现象**：验收单跑时 `TC-S1-050` 通过（面板 6.9 GB vs `nvidia-smi` 7.1 GB，差 2.42%）；
  并入**全量回归批次**（同进程已运行较久、期间桌面显存占用变化）后复测连续失败：
  面板仍报 6.9 GB，`nvidia-smi` 实际空闲 7.66 GB → **漂移 9.58% / 9.64% > 5%**。
- **根因**：`get_snapshot()` 按 `data_root` 做**进程内缓存**（设计目的：避免每次请求重跑
  阶段 B profile），但缓存把 `device_facts` 一并冻住 —— `available_vram_gb` /
  `available_ram_gb` 是**快照构建时刻**的值，而显存/内存占用在会话内持续变化。
  此前所有测试都是「后端刚启动就测」，漂移小，从未暴露。
- **为什么不能整快照刷新**：`probe_device_facts()` 单次 577 ms，若在快照层刷新会波及
  任务提交路径（`get_capability_snapshot()`，T-707 要求提交 P95 ≤300 ms）。
- **修复**：`device_probe.py` 新增公开入口 `read_nvidia_free_mb()`（与阶段 A 共用
  `_probe_nvidia`，**同一口径**，同 `read_system_memory_mb` 纪律）；
  `capabilities.py::refresh_dynamic_memory()` 只重探两项动态内存字段；
  `system_info.build_capabilities()`（**仅面板端点**）返回前刷新。
  决策/标定/门控路径（`get_capability_snapshot`）保持缓存，P95 不受影响。
- **验证**：修复后面板 7.6 GB vs `nvidia-smi` 7.56 GiB（差 ~0.5%）；`t706` 复跑
  **62/0/0**，受影响区域 `t608` 15/0、`t901` 74/0 无回归。
- **教训**：验收判据在「刚启动」与「长会话」两种状态下结果不同 —— **时间维度也是
  判据的一部分**。与 `TC-S1-005` 的「绝对阈值随内容漂移」互补：这一条是「快照值随时间漂移」。

## 6. 观察项（不阻塞验收，登记供后续迭代）

1. **导入时不校验 ONNX 内容**（`TC-S1-043` 相关）：损坏 `.onnx` 登记为 `ready/available`，
   错误推迟到提交时暴露。与「能力缺口前置到列表页」有落差 —— 建议导入时做轻量结构探测
   （读 graph 头即可），属体验优化，非 S1 验收条目。
2. **临时数据根用例的环境残留**：`F-07` 用例在临时根下创建的任务/文件记录会残留在 DB
   （服务端无 `DELETE /api/tasks` 端点），文件已随临时目录删除 → 任务列表渲染这些行时
   源图/缩略图 404（行仍可渲染，操作不受影响）。浏览器级脚本健康检查已按
   「本脚本造成」口径过滤并记观察。这也提示一个真实场景：**换根 / 清理后遗留任务引用
   缺失文件的健壮性**（占位图而非 broken image）可作为后续体验项。
3. **×2/×3 资产缺口**：PRD §2.5 举例「2x 与 4x 的输出尺寸不同」，但 `data/models/` 内
   无 ×2/×3 权重（内置 5 个全 ×4），该示例无法演示。已改以「模型切换 / tile 改动」证明
   "结果随参数变化"，并立 `TC-S1-014/015` 覆盖"不可用倍数被明确拒绝"。
4. **`T0` 缺口**（沿用遗留账）：`SAFMN ×4` / `SPAN ×2` 轻量模型尚未进 `data/models/`，
   纯 CPU 档的"可用性"依赖资产补齐（非本任务范围）。
5. **水位高条目采样是时机敏感的**：`verify_t704_degradation.py` 在全量回归批次中出现过
   一次「历史里存在真实的高水位条目」失败（OOM 降档救回后、水位采样执行前显存已被
   释放 → 采到低水位），单独复跑 31/0/1 通过。属瞬态竞态而非产品缺陷；该机制分支本就
   由 `t804` 用构造水位覆盖（见 t704 脚本内登记），此处如实留痕。
