## 1. 项目概述

### 1.1 项目背景

已有阶段完成的工作（见 `docs/tech/research/`）：

- 横向调研了开源超分/修复方案，确认 **Real-ESRGAN 系（BSD-3-Clause，可商用）** 是当前可落地的推理主力；
- 在开发机上完成了机制级实测验证：**EP 真实性验证方法、tile × 精度矩阵、三后端对比、显存测量方法**；
- 产出了跨环境自适应架构设计（探测 → EP 验证 → 首启自标定 → 决策 → 运行时反馈）。

现在缺少的是**可用的产品形态**。本 PRD 定义 v1 的功能边界。

### 1.2 目标用户

| 用户 | 场景 |
|---|---|
| **主要用户：开发者本人**（单机自用，无账号） | 本机批量处理低清图/截图/动漫图，需要看到原图与结果对比，并能换模型/调参数试效果 |
| 次要用户：同机使用者 | 未来可能扩展；v1 不做账号体系与数据隔离 |

### 1.3 核心价值

1. **把已验证的推理能力变成可点选的产品**，而不是停留在脚本；
2. **暴露真实硬件能力**：明确告诉用户当前用的是哪个执行提供器、精度、分块尺寸，以及**为什么**；
3. **长任务不卡界面**：CPU 上单图需数分钟，必须可取消、可看进度、可刷新页面不丢。

### 1.4 关键前提（架构级约束，源自前置实测）

> ⚠️ **本机是开发机，不代表用户环境。** 因此：
> - 所有**数量**（tile / 精度 / 并发度）由运行时探测 + 首启自标定得出，**不进 PRD 作为固定值**；
> - 只有**因果性防御**写死：EP 真实性校验、`arena_extend_strategy` 覆盖、CPU 禁 fp16、Intel GPU 判定看 `FULL_DEVICE_NAME`、OOM 降档链。
> 详见 `docs/rules/project-rules.md` §2.2。
>
> ⚠️ **本机只有 T1 硬件（8 GB 消费卡 + 无核显 CPU），没有 T2/T3 硬件可测。** 因此：
> - T2/T3 功能**照常实现**（P3，排在 T1 之后），但**交付时标记"未验证"**；
> - 通过**档位模拟开关**在 T1 上真实执行 T2/T3 的控制面逻辑，把"无法验证"压缩到只剩数据面性能与显存行为；
> - **禁止按设备型号硬编码分支**，一律走能力声明，否则真卡到位仍需重写。详见 §2.3 与 §7.1。
>
> ⚠️ **"数值运行时求"对冷启动有一条显式例外：保底档。**
> 原则禁止把数值写死，但**首次运行、标定尚未完成之前**，引擎必须能立刻开始工作。因此允许存在一组**保守下界参数**（下称"保底档"），但必须同时满足三个条件：
> 1. **可判定为保守**：只取"任何环境都不会 OOM"的下界（如最小 tile、fp32、并发 1），不得取本机实测值；
> 2. **来源可追溯**：由"已验证能力的下界"推导，而非开发机测量结果；
> 3. **一次性且可见**：标定完成后**立即**被标定结果替换，且"当前正处于保底档"必须对用户可见（与 §2.3 原则 3、§7.2"不得静默降级"一致）。
>
> 保底档是**例外条款，不是把硬编码数值合法化**——它只覆盖"标定完成前"这一个时间窗。机制见 `tech-arch.md` §6.8。

## 2. 功能需求

### 2.1 业务模块划分（概要设计）

| 模块 | 职责 | 依赖方向 |
|---|---|---|
| **M1 任务中心** | 所有长任务的统一入口：提交、排队、进度、取消、历史、产物 | 被其余模块调用 |
| **M2 推理引擎** | 核心。能力探测 → EP 真实性验证 → 首启自标定 → 参数决策 → 分块推理 → 降级 | 依赖 M3 |
| **M3 模型库** | 模型元信息登记、导入、导出、哈希校验、按需下载 | 被 M2 调用 |
| **M4 图像处理** | 预处理（色彩通道/归一化/尺寸约束）、后处理、拼接羽化、格式转换 | 依赖 M2 |
| **M5 媒体管理** | 原图/结果/缩略图的存储、检索、对比预览、清理 | 被 M1/M4 调用 |
| **M6 参数预设** | 参数组合的保存、加载、内置预设 | 被 M1 调用 |
| **M7 系统配置** | 存储路径、并发度、日志、标定状态、硬件信息展示 | 被全部模块读取 |
| **M8 微调支持** | 数据集打包导出（仅 HR，自动生成配对 LR）、训练脚本模板、训练产物回灌模型库。**应用内不承载训练执行**，无训练进度与损失曲线 | 依赖 M3 |

**约束**：模块间单向依赖，禁止跨模块直接访问数据；统一的推理出口只有 M2。

### 2.2 功能清单

**图例**

- **优先级**：
  - `P0` = v1 必须（**T1 消费级核心链路**）
  - `P1` = v1 尽量（T1 体验完善，可延至 v1.x）
  - `P2` = 次优先（T0 兜底完善、T1 可选项）
  - `P3` = **低优先：要做，但排在 T1 全部工作之后，且当前机器无法验证**
- **档位**：`T0` 纯 CPU ｜ `T1` 消费级 8G 独显 ｜ `T2` 高端 16–24G ｜ `T3` 专业卡（48G+）
- **v1 承诺范围**：**以 T1 为基准做扎实**；T0 保证降级可跑；**T2/T3 功能一并在范围内，但排在 P3、且交付时标记为"未验证"**（见 §2.3 与 §7.2）

**A. 功能主表**

| 编号 | 功能 | 优先级 | 档位 | 说明 |
|---|---|---|---|---|
| F-01 | **单图超分** | P0 | T0–T3 | 上传图片 → 配置参数 → 执行 → 得到放大结果。**T1 是主战场** |
| F-02 | **参数配置** | P0 | T0–T3 | 放大倍数（2/3/4）、模型选型、分块尺寸、精度、是否叠加人脸修复；**支持"自动"档，由引擎按标定结果决定** |
| F-03 | **原图/结果对比预览** | P0 | 全档 | 并排对比 + 滑块分割 + 局部放大；显示分辨率与放大倍数 |
| F-04 | **异步任务中心** | P0 | 全档 | 提交即返回任务号；实时进度；可取消；历史列表；页面刷新不丢 |
| F-05 | **模型库管理** | P0 | 全档 | 内置模型列表；**导入支持 4 种格式：`.onnx` / `.pth` / `.safetensors` / `.bin`**（`.bin` 必须带配套文件，见 §7.5）；导出；sha256 校验。**每个模型必须带"最低显存需求"，UI 按当前档位过滤——T2/T3 模型在 T1 上置灰并说明原因**（这是"留出场景"最直接的体现） |
| F-06 | **硬件能力面板** | P0 | 全档 | 展示：CPU 指令集与核数、GPU 型号与驱动、**实读可用显存/内存**、实际生效的执行提供器、**验证证据（节点归属）**，以及**识别出的档位** |
| F-07 | **系统配置** | P0 | 全档 | 数据根路径（默认 `data/`，含模型/上传/输出/缩略图/标定子目录，见 §4.2）、默认参数、并发度上限、日志级别、任务保留策略 |

| F-09 | **参数预设** | P1 | 全档 | 保存/加载/删除参数组合，含内置预设。**预设需能绑定档位**（同一场景在 T1 与 T3 上的推荐参数不同） |

**B. 高端 / 专业档功能（`P3`：实现，但当前机器无法验证）**

> 这些是"高端与专业卡场景"的落点，**在范围内、要写实现代码**，只是排在 T1 全部工作之后。
>
> 关键认识：**同一个功能，"控制面"能在 T1 上验证，"数据面"不能。** 据此逐项拆开——目的是**把"无法验证"的范围压到最小**。

| 编号 | 能力 | 目标档位 | ✅ 可在 T1 上验证（控制面） | ⏳ 必须等硬件（数据面） |
|---|---|---|---|---|
| G-01 | 不分块整图推理（`tile=0`） | T2+ | `tile=0` 语义与参数校验、**显存不足时的明确报错与降档链** | 整图能否装下、真实耗时 |
| G-02 | batch 推理 | T2+ | `supports_batch` 能力声明、batch 维度传递、batch=2 + 小 tile 的正确性 | 大 batch 的吞吐与显存行为 |
| G-03 | 吞吐优先调度 | T3 | 两套调度行为、策略切换不破坏单任务正确性 | 专业卡（H20 等）上的真实吞吐收益 |
| G-04 | TensorRT 现场构建 | T2+ | 后端枚举、构建流程、缓存键设计、**不可用时的明确降级与提示**（本机无 TRT，恰好可测负路径） | 构建耗时、引擎性能、精度对齐 |
| G-05 | 高分辨率输入（4K/8K） | T2+ | **完全可测**：可配置上限 + 小 tile 跑大图 | 无（仅需真实大图样本） |
| G-06 | 任务并行 / 多实例 | T3 | 并发度 > 1 的机制正确性、并发 2 下的内存压力、取消时的资源释放 | 高并发下的稳定性与吞吐 |
| F-15 | 视频逐帧超分 | T2+ | 逐帧管线正确性、音轨保留、进度与取消 | 实际帧率 |
| F-17 | 扩散类模型池 | T2+ | 能力门控、模型元信息、UI 置灰、**依赖缺失时的明确报错** | ⚠️ **整条执行链路**、显存占用、耗时、画质 |

**交付时必须携带的状态标记**：所有 P3 功能在界面与文档中标注 **"未验证（当前无对应硬件）"**。用户在有硬件的机器上首次使用时，走**自标定 + 首次运行验证**，而不是假定它能跑。

**降风险的三条硬要求**

1. **只按能力声明分支，禁止按设备型号硬编码**（不写 `if "4090" in gpu_name`）。这样等硬件到位时，只需验证、不必改逻辑。
2. **必须提供"档位模拟"开关**（见 §2.3 原则 4），否则 T2/T3 分支永远不会被执行过——那才是真正的盲写。
3. **P3 不得阻塞 T1 主链路**：任何 P3 代码失败都必须能被安全绕过，不得影响 T1 用户。

### 2.3 硬件档位与功能矩阵

> 本表是"**重点做消费级、但留出高端与专业场景**"这一优先级的落点。档位定义与 `docs/tech/research/图像超分修复应用-多硬件适配技术路线.md` 保持一一对应。

| | `T0` 纯 CPU | **`T1` 消费级 8G 独显** | `T2` 高端 16–24G | `T3` 专业卡 48G+ |
|---|---|---|---|---|
| 典型硬件 | 任意 x86 CPU | RTX 3050 8G / 4060 Ti 8G | 4090 24G / A5000 | RTX PRO 5000 48G / H20 96G |
| 推理后端 | OpenVINO 原生 `fp32` | **ORT + CUDA，`fp16`** | ORT/TensorRT `fp16`/`bf16` | TensorRT + PyTorch |
| 分块 | 必需（小 tile） | **必需，tile 由自标定决定** | 可不分块（G-01） | 不分块 |
| batch | 1 | 1 | 可 >1（G-02） | 高并发（G-02/G-06） |
| 调度策略 | 延迟优先 | **延迟优先** | 延迟优先 | **吞吐优先**（G-03） |
| 主模型 | 轻量（SPAN/SAFMN） | **`RealESRGAN_x4plus`** | 同左 + 扩散池 | + SUPIR 级 |
| 扩散池（F-17） | 不支持 | 不支持 | 支持 | 支持 |
| 视频（F-15） | 不支持 | 不支持 | 支持 | 支持 |
| 输入长边上限 | 受限（按内存） | ≤ 4096 | 无硬限（G-05） | 无硬限（G-05） |
| 用户可感知预期 | "能用 / 预览" | **"主力体验"** | "进阶质量" | "质量天花板 / 服务端" |
| **优先级** | `P1` 保证降级可跑 | **`P0` 主战场** | `P3` 实现，**未验证** | `P3` 实现，**未验证** |

**四条执行原则**

1. **v1 的一切取舍以 T1 为准。** 排序上 T1 永远优先；但**不因此砍掉 T2/T3 的实现**——它们进 P3，排在后面做。
2. **T2/T3 是"实现+未验证"，不是"留个字段"。** 代码要写完整（含错误路径与降级），只是交付时标注"未验证（当前无对应硬件）"。判断标准很具体：届时接上真卡，改动应只落在"新增一个实现类 + 确认参数"，而非修改数据库 schema 或 API 契约。
3. **档位对用户可见。** 面板要显示识别出的档位；模型在非适用档位上必须置灰并说明原因（如"该模型需 ≥16 GB 显存，当前 7.4 GB"），而不是让用户点了才失败。P3 功能同样要标注未验证状态。
4. **必须内置"档位模拟"开关**（本项是让 P3 不沦为盲写的关键机制）：
   - 允许**强制声明档位/能力**（如 `force_tier=T2`、`force_vram=24G`、`force_has_tensorrt=true`），绕过真实探测；
   - 用途：在 T1 机器上**真实执行 T2/T3 的代码路径**——档位判定、能力门控、UI 置灰/解禁、参数传递、调度策略切换、错误与降级链；
   - 这能让 P3 功能中**占代码量绝大多数的控制面逻辑在 T1 上被真实跑过并验证**，把"无法验证"压缩到只剩数据面的性能与显存行为；
   - 必须放在开发者设置中，并显式提示"模拟档位仅用于测试，不代表真实能力"。

**档位判定规则**：`T0`–`T3` 一律**由能力声明推导**（判据用实读可用显存 + 已验证后端），**不按设备型号**。判定顺序与边界见 `tech-arch.md` §6.2。

### 2.5 P0 验收标准（可客观验证）

| 编号 | 验收标准 |
|---|---|
| F-01 | 给定一张图与参数，任务成功产出结果文件；文件可打开、尺寸 = 原图 × 倍数（误差 0）、色彩与输入一致（无通道错乱） |
| F-02 | 页面上改动任一参数后执行，结果确实随参数变化（如 2x 与 4x 的输出尺寸不同）；"自动"档能正确落到引擎决策值并在界面显示该值 |
| F-03 | 对比视图可切换并排/滑块/放大；滑块拖动时两侧对齐无偏移；显示原图与结果的实际像素尺寸 |
| F-04 | 提交后 ≤ 1 s 内返回任务号；进度在 ≤ 2 s 内开始更新且单调不减；取消后 ≤ 2 s 任务状态变为"已取消"且资源释放；刷新页面后任务列表与进度仍在 |
| F-05 | 导入一个合法 `.onnx` 后被加入列表并可选用；导入损坏/不兼容文件时给出明确错误而非崩溃；显示文件 sha256 |
| F-06 | 面板显示的可用显存与实际相差 < 5%；**展示的执行提供器必须有 profile 节点归属作为证据**（这是防静默回退的唯一手段） |
| F-07 | 修改存储路径后新建任务写入新路径；配置重启后保持 |

> **适用范围**：本表只覆盖**首发切片**（§2.7 的 S1）中的 P0 项 F-01~F-07；F-11 的质量验收见 §2.7。
> **P1 项（F-08~F-13）的验收标准不在此预设**，在步骤 4 拆解时随任务卡逐项定义（含可复现的验证手段）。

                                                      │                        结果落盘 + 缩略图
                                                      ▼                              │
                                              前端进度条 ◀───────────────────────────┘
                                                                                     │
                                                              对比预览 ◀─────────────┘
                                                                  │
                                                              下载 / 清理

  · 显存/内存不足 ──▶ 自动降一档 tile ──▶ 重试一次 ──▶ 仍失败 ──▶ 显式提示"当前硬件状态不支持"

### 2.7 v1 首发切片与交付顺序

> **`P0`/`P1`/`P3` 是优先级，不等于交付顺序。** 本节把优先级落成可验收的切片，避免实现期同时铺开 18 项功能导致主链路长期不可用。

| 切片 | 范围 | 验收依据 | 说明 |
|---|---|---|---|
| **S1 首发切片**<br/>（可独立交付） | **F-01 单图超分**、**F-02 参数配置**、**F-03 对比预览**、**F-04 异步任务中心**、**F-05 模型库**（`.onnx` 主路径 + 导入/导出/哈希）、**F-06 硬件能力面板**、**F-07 系统配置**、**F-11 分块羽化拼接** | §2.5 的 F-01~F-07 验收标准；F-11 按"无可见接缝"做质量检查 | 打通**完整闭环**：上传 → 任务 → 推理 → 对比 → 下载。**S1 验收通过即视为"v1 可用"** |
| **S2 T1 体验完善** | F-05 剩余格式（`.bin`/`.pth`/`.safetensors` + 离线转换）、F-08 批量串行、F-09 参数预设、**F-10 首启自标定**、F-12 产物管理、F-13 微调（离线形态） | 验收标准在步骤 4 随任务卡逐项定义 | S2 内部可再拆、可并行，但**不得阻塞 S1** |
| **S3 / P3** | F-14 人脸修复、F-16 量化导出、F-15 视频预留、G-01~G-06、F-17 扩散池 | 控制面在 T1 上用**档位模拟**验证；交付时标注"未验证（当前无对应硬件）" | 排在 S1/S2 全部之后；失败必须可安全绕过 |

**两条约束**

1. **任何 S2/S3 项的失败都不得影响 S1 主链路**（与 §2.2 B 段"P3 不得阻塞 T1 主链路"同源）。
2. **引擎的 A/B/D/E 四阶段（探测 / EP 验证 / 决策 / 降级）属 S1**——F-06 的能力面板与"不用错后端"都依赖它们；**C 阶段（首启自标定，即 F-10）属 S2**：S1 期间"自动"档回落到**保底档**（§1.4），用户仍可显式指定参数。F-10 完成后"自动"档才真正生效。

## 3. 非功能性需求（NFR）

> ⚠️ **性能阈值一律表达为相对量或机制性上限，不写死本机实测绝对值**（理由见 §1.4）。

### 3.1 性能

| 项 | 阈值 | 说明 |
|---|---|---|
| 任务提交响应 | P95 ≤ 300 ms | 不含推理；提交即返回 |
| 进度事件间隔 | ≤ 1 s | SSE 推送 |
| 取消生效 | ≤ 2 s | 从点击到资源释放 |
| 首启标定预算 | ≤ 8 s | 超预算则停在当前最优档 |
| 二次启动 | 标定结果直接读缓存，≤ 200 ms | 不重复标定 |
| 单块推理耗时 | 必须落在自标定基线的 **±10%** 内 | 运行时校验；偏离即视为环境异常并告警 |
| 峰值显存/内存 | < 标定安全线（**可用量的 80%**） | 留 20% 余量给运行时波动 |
| 并发度 | 默认 1；上限由可用内存/显存反推，**不写死** | CPU 档瓶颈是物理内存不是显存 |

### 3.2 安全

| 项 | 要求 |
|---|---|
| 服务绑定 | 本地单机形态绑 `127.0.0.1`，**禁止** `0.0.0.0` |
| 鉴权 | v1 无账号体系；**若未来改为局域网可访问，必须先补鉴权** |
| 上传校验 | 限制扩展名白名单（jpg/png/webp/bmp/tif）与单文件大小上限；服务端二次校验真实格式，不信任扩展名 |
| 路径穿越 | 所有文件读写路径必须做规范化校验，禁止拼接用户输入直接访问文件系统 |
| 环境变量 | 敏感项只写 `.env.*`；`.env.prd` 必须进 `.gitignore` |
| 依赖许可 | 只打包许可明确可商用的模型；**Upscayl 的 Remacri / Ultramix / Ultrasharp 为非商用，禁止打包** |

### 3.3 兼容性

| 项 | 要求 |
|---|---|
| 操作系统 | **Windows 优先**（开发与验证环境）；架构上不引入 Windows 专属依赖，Linux 可跑 |
| 硬件 | 有 NVIDIA 卡走 CUDA；有 Intel GPU 走 OpenVINO 原生；**都没有则降级 CPU 并明确告知** |
| 浏览器 | Chrome / Edge 最新版 + Firefox 最新版；对比视图不得依赖实验性 API |
| 分辨率适配 | 界面在 1280×720 及以上正常；参数面板在窄屏可折叠 |
| **语言** | **中文单语**（不做 i18n 框架，但文案集中管理，便于后续扩展） |
| **运行方式** | **本机直接运行**（前端 dev server + 后端进程）。**不做 Docker**——用户指定放到 v2，见 §7.3 |

### 3.4 可观测性

- 每次任务记录：使用的后端 EP、精度、tile、峰值显存/内存、耗时、决策理由；
- **硬件事实 + EP 验证结果 + 标定记录必须能一键导出为单个 JSON**（用于排查"为什么这台机器慢/崩"）；
- 日志分级，默认 info；异常事件（含 EP 静默回退）必须落盘。

## 6. 交互与体验需求

### 6.1 关键交互流程

1. **主界面**：左侧上传/任务列表，右侧参数面板与预览区（或上下布局，由步骤 5A 定稿）；
2. **上传**：拖拽 + 点击选择；上传后立即显示原图与尺寸；
3. **执行**：点执行 → 任务卡片出现并进入队列 → 进度条 + 当前阶段文案（如"正在推理 3/12 块"）；
4. **对比**：结果产出后自动切入对比视图，默认滑块分割；
5. **参数变更**：任一参数改动后标记"参数已修改"，提示重新执行。

### 6.2 状态要求（必须覆盖）

| 状态 | 要求 |
|---|---|
| **空态** | 未上传时给出引导（拖拽提示 + 支持格式说明）；无任务时列表区给出说明而非空白 |
| **加载态** | 上传中显示进度；推理中显示进度条与阶段文案；模型列表加载显示骨架屏 |
| **异常态** | 上传失败/格式不支持/文件过大 → 明确原因与建议；推理失败 → 显示错误摘要 + 一键查看日志；EP 未生效 → 显式标注实际后端 |
| **降级态** | 处于降档后必须可见（如"当前为省显存档：tile 256"），并说明原因 |
| **取消态** | 取消中显示"正在取消"，完成后任务归入"已取消"分组 |

### 6.3 响应式与适配

- ≥ 1440px：三栏（上传/任务 · 预览 · 参数）；
- 1024–1440px：两栏，参数面板可折叠；
- < 1024px：单栏堆叠，预览优先。

### 6.4 界面风格

以图片预览为主角，控件克制；**避免在图片区域叠加过多浮层**。

- **主题**：⏳ **待定**——用户指定"后面做前端时再定"。步骤 5A 前端原型阶段必须先确认深色 / 浅色 / 跟随系统 / 可切换，再进入页面设计。
- **语言**：中文单语（见 §3.3）。

## 7. 约束与风险

### 7.1 技术约束

| 约束 | 说明 |
|---|---|
| 环境隔离 | 严禁全局安装；应用依赖需新建 `.venvs/sr-app`，**不得污染** `sr-gpu` / `sr-ov` / `sr-ovep` 三个基准环境 |
| 推理出口唯一 | 所有推理必须经 M2，禁止在业务代码里直接创建推理会话 |
| 数值不硬编码 | tile / 精度 / EP / 并发度必须运行时求得 |
| **模型格式（4 种）** | 支持 `.onnx` / `.pth` / `.safetensors` / `.bin`（用户指定，**不扩展其它格式**）。各格式的后端路由与依赖代价见 **§7.5**。`.bin` **必须带配套文件**方可导入 |
| 服务绑定 | 本地形态必须绑 `127.0.0.1` |
| **为后续演进预留接缝** | v1 的推理接口**不得**把"推理 = 单次 ONNX 前向"写死。M2 必须支持**引擎能力声明**（显存需求、推理步数、是否需要文本 prompt、是否生成式），使扩散引擎（F-17）与浏览器引擎（F-18）能作为**同级实现**接入，而不是重写 |
| **按能力声明分支，禁止按型号硬编码** | 不得出现 `if "4090" in gpu_name` 这类判断。所有档位相关分支必须走**能力声明**（显存需求、`supports_batch`、`has_tensorrt` 等），否则 P3 功能在真卡到位时仍需重写 |
| **必须提供档位模拟开关** | 见 §2.3 原则 4。没有它，T2/T3 分支永远不会被执行过——那才是真正的盲写。这是让 P3 可交付的前提条件 |

### 7.2 已知风险

| 风险 | 影响 | 应对 |
|---|---|---|
| **分块拼接无羽化** | 结果有可见接缝，是**质量缺陷** | F-11 必须做，不得以"先跑通"为由跳过 |
| **CPU 档能否实用未确定** | 若轻量模型（SPAN/SAFMN）在 CPU 上仍慢，CPU 用户的"能用"预期落空 | 单列为引擎 P0 任务，先验证再定 CPU 档的产品承诺 |
| **P3 功能无硬件可验证**（T2/T3 全部） | 写了但没跑过的代码 = 未验证代码。真实性能、显存行为、驱动兼容性都只能等硬件 | ① 用档位模拟开关把**控制面**在 T1 上真跑一遍（§2.3 原则 4）；② 交付时标注"未验证"；③ 有硬件的用户首次使用走自标定 + 首次运行验证，而非假定可用 |
| **F-17 扩散池是盲写风险最高项** | 它需要整套 PyTorch/`.safetensors` 依赖栈，而本机连一次完整执行都跑不了；依赖体积、版本冲突、显存行为全部未知 | 排 P3 最末；**先做可验证部分**（能力门控、模型元信息、UI 置灰、依赖缺失报错），执行链路最后做；建议在有 ≥16 GB 卡的机器上用一周时间专门验证 |
| ~~微调需求易膨胀~~ | ~~从"轻量微调"滑向完整训练平台~~ | **v1.7 后该风险已从根上消除**：F-13 改为**离线形态**（§7.6），应用内不含训练执行，没有可膨胀的训练平台 |
| 推理阻塞后端 | 进程内推理若不做隔离，长任务会影响接口响应 | 任务执行放独立线程/进程；接口层保持轻量 |
| Windows 拿不到按进程显存 | 无法精确归因显存占用 | 界面明确说明为设备级读数；诊断 JSON 记录基线 |
| 开发机单一样本 | 用其数值做产品承诺会翻车 | §1.4 前提 + `project-rules.md` §2.2 |
| **扩散输出的语义边界** | 扩散模型"恢复"出的细节是**模型生成的合理内容**，不是原始信息的还原。用于取证、档案、医疗等场景是**不可接受**的 | 接入 F-17 时必须在输出侧标注所用模型与参数，并对该类场景给出明确提示。**这是诚实问题，不是技术问题** |
| **ncnn 后端可用性未验证** | §7.5 对 `.bin`（ncnn 来源）的格式承诺可能落空 | 先验证 ncnn 在 Windows/Python 下的获取方式（任务 **T-210，P0**）；不可行则降级为调用 `realesrgan-ncnn-vulkan` 可执行文件。**在验证通过前，PRD 对 ncnn 一律按"条件支持"表述**，不计入 v1 承诺 |

### 7.3 非目标

> **区分"暂不交付"与"永久不做"。** 把可规划的能力写成"明确不做"，会把后续路线堵死——本节的 A/B 两段就是为此拆分。
>
> 📌 **重要修订**：原先写作"v1 不做"的 T2/T3 功能（含 F-17 扩散池），现已改为 **P3 = 实现但未验证**（见 §2.2 B 段）。原因：**没有硬件不等于不该写代码**——控制面逻辑完全可以在 T1 上通过档位模拟验证。所以本节 A 段剩下的是**真正因成本或形态问题而推迟**的项目。

**A. 暂不交付，但已写明启动条件**

| 项 | 何时做 | 启动条件 |
|---|---|---|
| **扩散类模型池**（F-17） | **P3，实现但未验证** | 代码在 v1 范围内写完（先做可验证的门控与元信息部分）；**真正可用需等有 ≥16 GB 显存的机器做一周验证**。理由见 §7.4 |
| 浏览器端 WebGPU 推理 | v2+ | 出现以下任一需求时：① 要发布成**公开网页**且服务端算力不够；② 要在**无独显**的机器上也能用（浏览器 WebGPU 用核显可能反而快于后端 CPU 路径）；③ 要做**浏览器端即时草稿**（轻量模型出预览，后端出终稿）。**原因是它要用 TS 重写整条管线，与 Python 引擎完全重复**，成本远高于 T2/T3 的档位扩展 |
| **Docker 容器化** | **v2** | **用户指定：本期不需要**。当前为本机直接运行（前端 dev server + 后端进程）；v2 再做容器化与一键交付 |
| 云端部署与多租户 | 需要多人协作时 | **启动前必须先补鉴权**——当前无账号体系，直接开放会有数据越权风险 |

**B. 永久不做**

- ❌ 分布式训练、多卡训练（定位单机单卡）
- ❌ 移动端原生 App
- ❌ **在 CPU 上跑扩散模型**（耗时不可接受）
- ❌ **在浏览器端跑扩散模型**（显存与模型导出均不可行）

> 账号体系不作为"永久不做"，而是随交付形态启动——见 A 段第三行。

### 7.4 扩散为什么排在 P3 最末（决策依据，供后续复核）

前置调研（`docs/tech/research/`）的原始结论是：**扩散类单独成池、v3 引入、仅显存 ≥16G 暴露**。改为"P3 实现但未验证"后，它仍排在**所有功能之最后**，四个硬理由：

| # | 理由 | 说明 |
|---|---|---|
| 1 | **导出路径不同，是第二套推理栈** | 扩散类多为多分支 + 动态 shape，ONNX 导出性价比低，必须走 PyTorch / `.safetensors` + TensorRT。这不是"多放一个模型文件"，而是**并行的第二条推理链路** |
| 2 | **显存不够** | 开发机 8 GB（实测可用 7.4 GB）。SUPIR 24 GB 起步；StableSR 128→512 已需约 8.9 GB。OSEDiff / HYPIR 需 tiling + 分阶段加载权重才勉强能跑且明显慢 |
| 3 | **依赖重量** | 需要 diffusers / transformers / torch / CLIP 文本编码器 / VAE，数个 GB，与现有 ORT + OpenVINO 环境是两套东西 |
| 4 | **同期铺第二条推理栈会让 T1 主线永远出不来** | v1 的首要目标是把已验证的 ONNX 路径在消费级档位上做成产品；扩散栈与它零复用 |

**但"扩散=慢"的印象已经过时**：单步扩散/蒸馏系（OSEDiff、InvSR、HYPIR、AdcSR、D³SR）把多步去噪压到 1 步，HYPIR 单卡 1.7 s / 1024²，OSEDiff 已被 OPPO Find X8 产品化落地。所以它值得排在 v2/v3，而不是永不。

**真正的不可替代场景**：严重退化的老照片。CNN/GAN 类（含 Real-ESRGAN）在极端退化下只能"变干净"，补不出细节；扩散能补，但补的是**生成内容**——见 §7.2 的语义边界风险。

### 7.5 模型格式与后端路由（用户指定支持 4 种）

| 格式 | 配套文件 | 目标后端 | 依赖代价 | 备注 |
|---|---|---|---|---|
| **`.onnx`** | 无 | ORT（CUDA / CPU EP）、OpenVINO（转 IR） | **无额外依赖** | **主路径**，已验证 |
| **`.bin`** | **必须带 `.xml`（OpenVINO IR）或 `.param`（ncnn）** | OpenVINO 原生；ncnn 为**条件支持** | 取决于配套 | **单文件不可用**；`data/models/ir/` 下现有权重即属此类。⚠️ **ncnn 来源为"条件支持"**：其 Windows/Python 可用性尚未验证（T-210），**验证通过前不计入 v1 承诺**，见 §7.2 |
| **`.pth`** | 无 | PyTorch → 转 ONNX 后走主路径 | **需 PyTorch（数百 MB ~ 2.5 GB）** | 训练框架原生格式 |
| **`.safetensors`** | 无 | 同 `.pth`（需 spandrel 类架构识别） | 同上 | 需按 `architecture` 字段识别网络结构 |

**两条架构影响（步骤 3 必须落定）**

1. **`.pth` / `.safetensors` 是否在应用内捆绑 PyTorch**
   - **方案 A（推荐）**：不捆绑。提供**离线转换工具**把 `.pth`/`.safetensors` 转成 `.onnx`，应用只导入转换产物；原格式可登记但标注"需先转换"
   - **方案 B**：捆绑 PyTorch + spandrel，应用内直接加载（依赖体积与部署复杂度显著上升）
   - 若用户的主要意图是"把自己训练出的权重用起来"，**方案 A 足够且更干净**
2. **`.bin` 的识别歧义**：OpenVINO 的 `.bin` 与 ncnn 的 `.bin` **同名不同格式**，必须靠配套文件区分（有 `.xml` → OpenVINO；有 `.param` → ncnn）。导入流程要**显式要求用户同时选择配套文件，不能靠猜**。

### 7.6 轻量微调的离线形态（F-13）

**决策（2026-09-30 用户指示）：应用内不引入 PyTorch 训练栈。** 微调能力保留，改为**离线形态**。

| 环节 | 谁做 | 应用提供的支持 |
|---|---|---|
| 数据集准备 | **应用** | **打包导出**：用户只提供 HR 图，应用自动降采样生成配对 LR，导出为训练可用的目录结构 |
| 训练执行 | **用户**（自带 PyTorch 的外部环境） | 提供**训练脚本模板**（含推荐超参与 LoRA 级配置），由用户在自有环境运行 |
| 产物回灌 | **应用** | 训练产物经 **F-05 模型导入**进入模型库：`.onnx` 直接可用，`.pth`/`.safetensors` 走 §7.5 离线转换 |

**为什么这样可接受**

- "加载侧"早已定为离线转换（§7.5 / ADR-003），微调走离线与之**同构**，不引入第二套依赖语义；
- 应用依赖环境 `.venvs/sr-app` 因此保持轻量——**不含 torch**，启动快、打包小、版本冲突面小；
- 训练对交互的要求远低于推理（一次几十分钟到几小时），放进 Web 界面的收益有限，代价却是整条训练依赖链。

**由此产生的边界（必须显式，不得回收进应用）**

- 应用**不展示**训练进度与损失曲线，**不存**训练任务状态（§4.1 已移除 `FinetuneJob` 实体）；
- 训练环境的可用性、显存占用、失败原因由**用户自行负责**，应用不做兜底；
- 训练脚本模板随版本维护，**必须与当前模型架构对齐**，否则回灌会出现"格式合法但结构不匹配"。
