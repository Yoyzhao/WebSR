#### 判据设计纪律

**优先用相对/自指判据，少用绝对阈值** —— 绝对阈值会随图像内容漂移，容易变成"调参调到绿"：

| 判据 | 形式 |
|---|---|
| 色彩无通道错乱 | **互换反证**：输出面积平均回源尺寸后，恒等映射误差必须**小于** R↔B 互换映射误差 |
| 无周期性接缝伪影 | **双跑一致性**：同图用不同 tile 各跑一次，两次差异**不得沿任一方块网格呈周期性结构**（ratio < 1.25） |
| 块边界无突变 | 边界带梯度 vs **同图块内基线**的比值（ratio < 1.30） |
| 管线正确性 | 与 **官方参考实现**产物比对（PSNR），而不是自证 |

### 画质验收：三层判据

1. **客观（自动断言）**：尺寸精确 ×4；色彩恒等映射优于互换映射。
2. **官方参考交叉校验（最强的一条）**：把本项目 ONNX 管线的输出，与 **Real-ESRGAN 官方 ncnn
   可执行文件**对**同一张图**的 ×4 产物逐像素比对（`exe_out_x4.png` 是 T-210 留下的同源参考）——
   实测 **PSNR = 38.20 dB、平均绝对差 0.99、最大通道均值差 0.25**。
   → 说明我们的 ×4 结果与官方实现**结构一致**，而不是"自己看着还行"。
3. **人眼复核（1:1 裁剪，非缩放全图）**：
   - 写实照片：细枝结构**真实恢复**（不是把模糊放大），无伪影、无串色；
   - 动漫插画（`mdl_4`）：线条干净锐利、色块平整洁净；
   - 轻量模型（`mdl_5`）：细节不及主模型但显著优于输入，色彩保持。
   ⚠️ **方法论教训**：缩放的整幅并排图会因显示重采样产生**观感假象**（曾据此误判"沙变灰"，
   而两半的通道均值差 < 1）。**画质结论必须建立在 1:1 裁剪 + 客观指标上**。

## T-704 异常与降级链联调

### 为什么 `t804` 全绿还不够

`verify_t804_engine.py` 已经把阶段 E 的**机制**验证过了 —— 降档链的每个分支（tile 折半、GPU→CPU、耗尽报错）、
OOM 识别的正负例、水位追踪器的阈值逻辑，都各有断言。但它用的是**抛构造异常的假执行器**（`_FastExecutor`）
+ **注入的构造水位值**。也就是说：

> 降档链的每个分支都被单测过，**但它从来没有被真实 OOM 触发过**。

这正是 `T-703` 留下的教训的同构版本：**「控制面全绿 ≠ 数据面正确」**。

### 目标与边界

**范围内**：真实 OOM → 自动降档 → 重试；降档链耗尽报错；真实水位采样；EP 回退（因果性防御在真实 HTTP 路径）；
保底档可见且不污染标定表 / 模型元信息。
**范围外**：取消与并发边界（`T-705`）、逐条测试用例（`T-706` / M7）。

### 怎么在不伪造硬件事实的前提下真实触发 OOM

**不降显存、也不改 `device_facts`** —— 走**产品自身的真实入口**：

```
POST /api/tasks   body: { params: { auto: false, tile: <很大> } }
```

非自动档（`auto=false`）允许用户**显式指定 tile**，而因果性防御只保证「**不低于下界、是 align 倍数**」——
**不为"这台机器跑不动"兜底**（那是降档链的职责）。再配一张**短边小于 tile 的图**：
`plan_tiles` 会把内容**居中补齐成完整 `tile×tile` 块** → **单块即耗尽显存**，触发快、可重复。

> 这条路径**不需要**档位模拟。`T-901` 解除的是「用 `force_vram` 声明小显存」这条**备选**触发路径
> （已验证可用）；而「**用户手动指定大 tile**」是**更贴近生产**的触发方式 —— **用户真的会这么干**。
> 两条路径都拿得出真实降级证据，本轮选了后者。

### 🔴 核心缺陷：**真实 OOM 根本没被识别**（本轮最有价值的发现）

| # | 现象 | 根因 | 后果 |
|---|---|---|---|
| 1 | 主动请求 `tile=1024/2048/4096` 均**真实 OOM**（`BFCArena::AllocateRawInternal Failed to allocate memory for requested buffer of size 4294967296`），但终态是 `INTERNAL_ERROR / 推理执行失败 / 请导出诊断 JSON` | `engine/model_loader.py::infer()` 把推理异常包装成 `ModelLoadError(INFERENCE_FAILED, "推理执行失败", detail={"exception": <原始 ORT 错误>})`；`ModelLoadError.__init__` 调 `super().__init__(message)`，使 **`str(exc)` 只剩面向用户话术**；而 `engine/watermark.py::is_oom_error()` **只读 `str(exc)`** | **(A)** 降档重试**完全失效**（核心机制在最需要它时是哑的）；**(B)** 违反 PRD §2.2 铁律 5「**降级必须显式**」 |

**修复**：`is_oom_error()` 改为遍历 `_candidate_texts()` —— **看穿包装层**，把
`str(exc)` + `message` / `reason` 属性 + `detail` 字典值 + `__cause__` / `__context__` **异常链**（深度 4）
**全部**纳入判定，而不是只看最外层那句话术：

```python
def is_oom_error(exc: BaseException) -> bool:
    for text in _candidate_texts(exc):      # 看穿包装：自身 + 属性 + detail + 异常链
        low = text.lower()
        if _WIN_OOM_RE.search(low):         # Windows 特有的显存/内存不足话术
            return True
        if any(pat in low for pat in _OOM_PATTERNS):   # "out of memory" / "allocate" 等
            return True
    return False
```

**回归防线（`verify_t804_engine.py` 段 7，+3 条）**：`detail["exception"]` 里的原始 OOM 仍被识别；
**带 `__cause__` 链**的包装异常仍被识别；模型加载类失败（`InvalidProtobuf`）**不误判**为 OOM
（断言数 **132 → 135**）。

**修复后实测（真实推理路径）**：
- `tile=1024` → **`completed`，降档 `1024 → 512`，`degraded=true`** —— 降档链**真的把任务救回来了**；
- `tile=4096` → **`VRAM_INSUFFICIENT`** + message「显存不足：已自动降档仍无法完成」+
  `downgrade_attempts=1` + 现场水位 `ratio 0.9495` —— 耗尽路径给出**结构化、可照做**的失败。

### 新增验证资产

- **自适应探测 tile**（段 2）：从一个足够大的 tile 起，`completed 且有 downgrades` → 命中；`VRAM_INSUFFICIENT` → 记耗尽的 tile；`completed 无降档` → **继续翻倍**。**不硬编码"多大 tile 会 OOM"**（那是本机实测值，换机器就变）。
- **保底档必须验到"真保底"**（段 6）：本机 `mdl_1` **有标定** → `source=calibration`、`using_fallback=false`，
  故断言改为**条件式**，并**另找一台无标定的模型**（`mdl_5`）真实走保底档 —— 否则这一条会被**弱化成假绿**。

### 待验清单（逐条对照，均引自已冻结的引擎硬约束）

| # | 判据 | 结果 |

### 诚实边界

- **「连续 2 次 > 85% → 降档」在本机无法按需复现**（**1 项 SKIP**）：真实高水位只可能来自 OOM 现场，
  而 OOM 降档会 `note_downgrade()` **复位计数** → 计数永远到不了 2。该机制由 `t804` 的**构造水位值**覆盖。
  这是**环境事实**，不是缺陷；换一台能长时间贴近水位的机器即可真实复现。
- **WDDM 限制仍在**：Windows 下 `vram_*` 是**设备级**用量（含桌面进程），水位**只能看趋势**，不作绝对判据。
- **`GPU → CPU` 那一跳未被真实触发**：本机 CPU 后端虽已验证，但要把 `tile` 折到下界 64 仍跑不动、
  才会跳到 CPU —— 本机在折半阶段就成功或已耗尽，**该跳的分支由 `t804` 覆盖**。
- **EP 回退验的是"因果性防御回落"**，不是"EP 运行时崩溃后重试"（后者属驱动级故障，不可按需复现）。
- **OOM 识别只对"能读到的文本"负责**：拿不到文本的异常（如纯 C 层返回码）无法判定 —— 这是尽力而为的启发式。

## T-705 取消与并发边界联调

### 目标与边界

**范围内**：取消 **≤ 2 s 生效**（可复现测量）、`canceling` 中间态、**取消后资源释放**（不留产物 / 不占并发槽）、
**并发拒绝**（`max_concurrency=1` 下的 409）、终态后并发槽**立即释放**、重复取消的幂等边界。
**范围外**：异常与降级链（`T-704`）、逐条测试用例（`T-706` / M7）。

### 已有资产（本轮不重做，只补边界）

- `T-702` 已修掉「**取消后界面永久停在『正在取消』**」—— 根因是前端**提前退订 SSE** 丢掉了终态 `done`，属**前端**缺陷。
- `T-806` 已验「**协作式取消生效、取消不留半个文件**」，属**单任务**语义。
- **本轮补齐的是边界**：并发（`max_concurrency`）、进程级资源释放、2 s 时限的**可复现测量**、终态后并发槽的释放时机。

### 新增验证资产

| 路径 | 说明 |
|---|---|
| `scripts/test-script/verify_t705_cancel_concurrency.py` | 主脚本（9 段 / **24 项断言**），走**真实后端 + 真实推理** |

脚本段落：`[0]` 可达性 → `[1]` 准备（**640×480 夹具**，配 `tile≈256` 切多块）→ `[2]` 基线（顺带测单块耗时）→

**设计口径**：`pick_model()` 取**可用且门槛最低**的模型（跑得快、便于在任务完成前观察到取消）；
`CANCEL_DEADLINE_S = 2.0` 来自 NFR。

### 关键设计：把「最坏延迟 = 单块耗时」的因果关系钉死

协作式取消（ADR-005 约束 3）**只在块间检查标志**，块内不可中断 → **最坏取消延迟 = 单块耗时**。
若不测这一点，"取消 0.14 s 达成"会被误读为"取消总是很快"，而**大 tile 下取消可能逼近甚至超过 2 s**。
故段 `[4b]` 用 `tile=256`（单块 ≈116 ms）单独跑一次，并**把比值算出来**：

| 场景 | 取消延迟 | 单块耗时 | 比值 |
|---|---|---|---|
| 默认（小 tile，多块） | **0.143 s** → 复测 **0.02 s** | ≈11 ms | — |
| 大单块（`tile=256`，9 块） | **0.106 s** | ≈116 ms | **0.91** |

比值 ≈ 0.91 → 取消延迟**紧贴单块耗时**，证实「**最坏延迟 = 单块耗时**」而非引擎轮询开销。
断言写成**蕴含式**：`实测 ≤ 2 s` **或** `单块本身 > 2 s`（后者意味着 2 s 是**结构性不可达**，不是缺陷）。

| 判据 | 结果 |
|---|---|

| 取消 ≤ 2 s（默认多块） | ✅ 实测 **0.143 s** → 复测 **0.02 s** |
| 大单块取消 ≤ 2 s | ✅ 实测 **0.106 s**（单块 ≈116 ms） |
| 取消留有 `canceling` 中间态 | ✅ |
| **取消不留产物**（含大单块） | ✅ `[]` |

| **终态落库后并发槽立即释放**（观测动作不占调度位） | ✅ |
| 重复取消 → **409 `TASK_CANCELED`** | ✅ |
| `verify_t705_cancel_concurrency.py` | **24 通过 / 0 失败 / 0 跳过** |

### 诚实边界

- **取消时延强依赖单块耗时**：小图小 tile 下是**几十毫秒**，大图大 tile 下可能升至**秒级**；
  「≤ 2 s」是**默认档位下**的结论，**不构成对任意参数的保证**（本脚本正是为此加了段 `[4b]`）。
- **`queued` 即刻取消**（尚在队列、未开跑）那条分支未被本脚本真实命中 —— 由
  `t806` / `t702` 的机制级断言覆盖。
- **并发度仍为 1**：只验证了 `max_concurrency=1` 下的**拒绝与串行**语义；
  **并发 > 1**（`T-907`）未验证，`max_concurrency` 设置**已保存但尚未生效**。
- **进程级资源释放**只验到"任务层"（无残留产物、无占用并发槽）；**显存/内存是否回到基线**
  受 WDDM 限制（设备级用量、含桌面进程）**不作绝对判据**。
