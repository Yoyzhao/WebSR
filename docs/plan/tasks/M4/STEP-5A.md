## 阶段入口前置决策

### T-302 定案 UI 组件库（自 M3 移入）

**结论**：**Element Plus 2.14.6** + `@element-plus/icons-vue` 2.3.2

**候选与判据**（按本项目的实际约束排序）

| 判据 | Element Plus | Naive UI | 采用 |
|---|---|---|---|
| 主题可定制（PRD §6.4 强制前置） | CSS 变量 + SCSS 变量，深色走 `html.dark` + `dark/css-vars.css` | CSS-in-JS，运行时主题切换更省事 | 两者均可，EP 需构建期 SCSS 定制，但**本项目只有一个强调色需要覆盖**，成本可控 |
| S1 高频组件开箱可用 | 表格 / 进度 / 骨架屏 / 抽屉 / 提示全部齐备 | 同样齐备 | 平手 |
| 中文文档与社区 | 国内生态最大、示例最丰富 | 规模较小 | **Element Plus 胜** |
| 用户确认 | — | — | **用户选择 Element Plus** |

**范围外**：具体页面的组件选型（属 T-403）、视觉规范（属 T-401）。

**落点**：`docs/tech/dev-info.md` §1 / §2。
**版本核实方式**：`npm view element-plus version` → `2.14.6`（registry 实测，非记忆值）。

**已知实现代价（须在 5C 处理）**：
- 设计稿的扁平方形 Tab（4 圆角、无下划线）与 `el-tabs` 默认形态差异较大 → 5C 需**二选一**（自绘或深度覆盖），不得混用；
- `el-tag`、`el-progress`、`el-pagination` 的默认尺寸/形态与设计稿不符，需覆盖；
- 深色模式需同时引入 `element-plus/theme-chalk/dark/css-vars.css` **并**把 `--el-color-primary` 覆盖为设计稿的 `--Theme-primary`。

### T-401 定案界面主题

**结论**：**深色为默认 → 支持手动切浅色 → 支持跟随系统**（三态并存）

**依据**：
1. PRD §6.4 要求 5A 前必须确认四种形态（深色 / 浅色 / 跟随系统 / 可切换）中的哪一种；
2. 图像对比类工具的行业惯例为深色（Photoshop / Lightroom / Figma），深色背景不干扰对图像色彩与亮度的判断；
3. 用户确认该策略。

**落点**：`docs/tech/dev-info.md` §1 / §2 / §10；完整 token 见 `docs/prototype/tokens.css`（含 `[data-theme="Light"]` 覆盖块）与 `docs/prototype/02-视觉与主题基线.md` §6。

**方案偏差（重要）**：设计系统的场景约束中有一条 `C1 no light theme`（"创意工具默认无浅色主题"）。该约束与用户已确认的三态策略冲突，**按"用户指引优先"处理，该约束作废**，浅色主题照常实现。

## T-402 页面结构与布局骨架

### 目标与边界

**目标**：冻结 S1 全部页面的主骨架、模块分区、信息层级与尺寸规格，使 5C 无需重新决定布局。

**范围内**：7 个页面的结构与布局（P1–P7，见 `docs/prototype/README.md` §2）；三档响应式断点与降级规则。

**范围外**：字段级交互契约（属 5B T-405）；页面编码（属 5C）。

### 技术方案

**影响位置**

- 页面/组件/状态：7 个页面骨架 + 12 个业务组件的边界划分
- 服务端路由/服务/API：无
- 数据模型/迁移/存储：无

**实现说明**

- **基准尺寸 1440 × 900**，对应 PRD §6.3 的 ≥1440px 三栏基准；
- 主工作台为**唯一的三栏页**（左 320 / 中 fill / 右 340），其余为「顶栏 + 单栏内容」；
- 导航采用**顶栏 5 Tab**（工作台 / 任务 / 模型库 / 硬件 / 设置），而非仅图标入口——依据 WebUI 原则「导航可预期」；
- 颜色与尺寸**全部绑定设计变量**，实现 Dark / Light 双模式切换而不改动任何结构。

**权威文档引用**：PRD §6.1 / §6.3 / §2.7（S1 切片）；tech-arch §3；`docs/prototype/01-页面结构与布局.md`。

### 技术输入与交付

- **输入产物**：PRD §6、§2.7；tech-arch §3、§5；`docs/tech/dev-info.md`
- **输出产物**：`docs/prototype/README.md`、`01-页面结构与布局.md`、`05-响应式规范.md`；设计稿 **9 页**（7 页 1440 基准 + 2 页响应式验证）；`docs/prototype/assets/`（9 张 SVG 矢量快照）
- **对接阶段**：5B（在此骨架上补交互与契约）、5C（按图落地）

### 验证与验收

- **验证步骤**：设计稿逐页截图检查；对 P1 与 P2 执行结构校验（`capture_layout`）
- **验证结果**：结构校验报告 11 项 warning，**全部为有意留白**（顶栏 Spacer 两侧分隔、参数分组呼吸感、预览区居中留白）与**有意层叠**（对比滑块把手叠于画布之上），无结构性缺陷。
- **验收标准**：用户确认页面结构与布局
- **证据落点**：设计稿 + `docs/prototype/assets/`

### 风险与恢复

- **风险**：7 个页面的设计工作量较大，若在 5C 阶段被逐页质疑布局，会引发返工
- **缓解**：把布局决策的**依据**逐条写入 `01` 与 `README` §5，使 5C 能自行判断而不是重新设计
- **回滚/恢复**：设计稿为可编辑文件，局部调整成本低；token 已变量化，改主题/改色板不需要重画

## T-403 组件映射与交互草案

### 目标与边界

**目标**：把每个界面区块映射到具体组件（Element Plus 或需封装的业务组件），并给出交互草案与五种状态的覆盖清单。

**范围内**：12 个业务组件封装清单；Element Plus 组件映射与定制要求；五种状态定义（空 / 加载 / 异常 / 降级 / 取消）；反馈机制、危险操作保护、无障碍要求。

**范围外**：组件的实际实现（属 5C）；后端接口实现（属 5D）。

### 技术方案

**影响位置**

- 页面/组件/状态：组件清单与状态矩阵
- 服务端路由/服务/API：无（仅标注每个状态需要哪些字段支撑）
- 数据模型/迁移/存储：无

**实现说明**

- **必须封装的 12 个业务组件**（禁止各页重复实现）：`AppTopBar`、`PageHeader`、`SettingsRow`、`StatusText`、`SectionCard`、`TaskCard`、`ModelCard`、`CompareSlider`、`FallbackNotice`、`ActionButtons`、`EmptyState`、`SegmentedControl`；**第二轮补入 3 个**：`TaskDetailDrawer`（任务详情五区段）、`ParamDiffRow`（请求值 vs 生效值对照）、`ModelImportDialog`（导入两级弹窗），合计 **15 个**；
- **明确禁止 `el-slider` 充当图像对比滑块**（语义错误，无障碍无法达标），必须自绘 `CompareSlider`；
- **降级态是本项目特有的必需状态**：任务卡、表格行、参数面板、硬件面板都必须能表达"降了什么、降成什么、为什么"（依据 `project-rules` §2.2-5）。

**权威文档引用**：PRD §6.2、§6.4；WebUI 设计原则与检查清单（`6-frontend-rules.md`）；`docs/prototype/03-组件映射与复用.md`、`04-状态与交互定义.md`

### 技术输入与交付

- **输入产物**：PRD §6.2（状态要求）、§6.4（风格）；tech-arch §5
- **输出产物**：`docs/prototype/03-组件映射与复用.md`、`04-状态与交互定义.md`、`tokens.css`；`docs/tech/api-contract.md`（草案，5B 冻结）
- **对接阶段**：5B（补字段级契约）、5C（按映射实现）

### 验证与验收

- **验证步骤**：逐条核对 5A 原型设计检查清单（14 项）；对设计稿做视觉验证截图
- **验证结果**：检查清单 14 项全部满足（见 `README.md` §6）；视觉验证发现并修正 2 处（任务卡元信息文字换行挤压 → 缩短文案；`text-tertiary` 对比度不达标 → 取值修正）。**第二轮（覆盖度审计 + 视觉审查）另发现并修正 9 处**，详见 `README.md` §7 —— 含 3 处设计稿实测缺陷（P4 未居中、P2 列间无间距、P2 数值列未右对齐）与 2 处规范推导错误（P2/P3 宽度上限）
- **验收标准**：用户确认组件映射与状态清单
- **证据落点**：`docs/prototype/` 全部文档；`README.md` §7 审查记录；`assets/` 中 P2 / P4 已按修正重导

### 风险与恢复

- **风险**：组件封装清单若遗漏高频结构，5C 会出现"同类多套实现"
- **缓解**：清单已覆盖 P1–P7 全部重复结构；`03` §5 列出 7 条禁止事项，违反即返工
- **回滚/恢复**：组件清单为文档级约束，调整成本低

### 方案偏差

1. **`T-302` 归入 5A 入口执行**：T-302 原挂 M3 但实际未开工。M3 验收的是**拆解产物**（计划本身），而 T-302 是**执行型任务**。为避免"已验收里程碑下挂着未完成任务"的口径混乱，将 T-302 与 T-401 一并作为 5A 的入口前置决策执行并记录在本文件。
2. **设计系统的 `C1 no light theme` 约束作废**：与用户确认的三态主题策略冲突，按"用户指引优先"处理（见 §T-401）。
3. **`text-tertiary` 取值修正**：初版 `#6E6D6D` 在 `bg-panel` 上对比度仅 3.44:1，不满足 WCAG AA。修正为 `#8C8C8C`（5.2:1），浅色版同步由 `#8F8C87` 修正为 `#757370`（4.8:1）。
4. **导航结构迭代**：初版顶栏仅有 3 个图标入口（主题 / 硬件 / 设置），在设计过程中发现独立页面缺少可预期的导航，改为 **5 Tab 主导航**，并移除重复的图标入口。
5. **独立页缺少内容宽度上限与响应式规定（阶段内回补）**：首版只把 PRD §6.3 的响应式要求落到了主工作台——独立页仅"硬件面板窄屏改单列"一句，且设置类页面没有 `max-width`。后果实测：P5 在 1440 下 label 与其值相隔 **1085px**（1920 下约 1565px），**信息关联断裂**而非仅仅"显得空"。已回补三项：① 按内容类型为 4 个独立页设定宽度上限（880 / 1200 / 1600 / 1904），超出居中；② `05-响应式规范.md` 重写，补齐独立页在中屏与窄屏的逐页行为；③ 新增 **P8（窄屏）/ P9（中屏）** 两张响应式验证稿并截图验证。设计稿由 7 页扩为 **9 页**。
6. **功能页面覆盖度审计（阶段内回补）**：对照 PRD §2.2 全部 F-01~F-18 / G-01~G-06 与 tech-arch §5.3 全部端点逐条比对，发现并补入 5 项承载：**任务详情抽屉**（`TASK.resolved` / `TASK.error` / `ARTIFACT` 三个已定义字段无落点）、**模型导入两级弹窗**（PRD §7.5 四格式路由与 `MODEL_MISSING_COMPANION` 无界面出口）、**`interrupted` 状态**（状态枚举含该值，进程崩溃必然产生，原五态遗漏）、**档位模拟警示**（模拟态会在顶栏显示错误的能力声明，与 §1.3 冲突）、**SPA 兜底路由**。均以弹窗/抽屉/文档规则形式落地，**不新增设计稿页**。
7. **第 2 处宽度上限推导错误（阶段内修正）**：5 中设定的 P2 = 1600 / P3 = 1904 两项，经复核发现推导依据有误——P3 的 1904（4 列）在 1440px 基准稿下永不触发，导致**规范写"4 列"而设计稿画"3 列"**。已修正为 P2 = **1344**、P3 = **1408**（3 列）。
8. **P4 设计稿与本规范脱节（阶段内修正）**：P4 的 `ContentWrap` 虽为 1200 固定宽，但**未居中**，1440 下实际靠左。已新增居中包裹层修正。
