### 3. 任务粒度与依赖原则

1. **单一阶段、单一交付物**：一个任务不跨阶段，不并列无关联交付物。
2. **依赖最少的先做**：无前置依赖、可独立验证的任务优先。
3. **契约先行**：`T-405`（冻结 API 契约）完成前，5C / 5D 的任务不得启动。
4. **基础设施先于业务**：工程骨架、数据模型、运行时基线（DLL 注册、启动序列）先于业务模块。
5. **引擎与业务解耦**：`T-6xx`（后端骨架与业务模块）与 `T-8xx`（引擎核心）通过 `M2` 的接口交汇——业务侧不直接创建推理会话。

### 4. S1 优先如何落地

`project-progress.md` 的每个阶段分组内**按 S1 → S2 → S3 排序**。具体表现：

- **5C**：先做上传 / 参数 / 任务中心 / 对比预览 / 能力面板（S1 页面），模型库的"剩余三种格式"与预设、产物管理排后。
- **5D**：先做工程骨架、数据模型、运行时基线、模型库 `.onnx` 主路径、任务中心、SSE（S1 后端），再做 S2 项。
- **F-11（分块羽化）属 S1**，不可延后——它是 S1 验收的一部分（"无可见接缝"）。
- **F-10（首启自标定）属 S2**：S1 期间"自动"档回落**保底档**，用户仍可显式指定参数。

### 5. 为什么把两项前置验证放进步骤 4

`T-305`（ncnn 可用性）与 `T-306`（SPAN/SAFMN 的 CPU 速度）都不是代码任务，而是**结论任务**，且都影响**产品承诺**：

- `T-305` 不通过 → PRD §7.5 的 `.bin` ncnn 来源要降级为"调用外部可执行文件"，`T-806`（模型加载器）的接口范围随之变化。
- `T-306` 不通过 → **T0 纯 CPU 档的产品承诺要改**（PRD §3.1 / §2.3 对 CPU 档的预期）。

两者都发生在**写代码之前**最有价值，因此放在步骤 4 的时间窗内执行，不占用 5D 工期。

## T-305 前置验证：ncnn 在 Windows/Python 下的可用性

> 承接原 `T-210`（编号保留），从 M2 组移入本阶段执行。

### 目标与边界

#### 目标

判定 `.bin`（ncnn 来源）能否在 Windows + Python 环境下真实加载，从而决定 PRD §7.5 中 ncnn 是"条件支持"还是"降级为外部可执行文件"。

#### 范围内

- 探明 ncnn 的 Python 绑定在 Windows 上的获取方式（pip wheel 是否存在、是否需自行编译）
- 若可用，跑通一次最小推理并与 ONNX 主路径做输出比对
- 若无 pip 方案，评估降级路径：调用 `realesrgan-ncnn-vulkan` 可执行文件的可行性
- 复核已知的"黑图"bug 与 Vulkan 可用性

#### 范围外

- ncnn 后端的**实现**（属 5D `T-806` 模型加载器）
- 其它三种格式的验证（`.onnx` 已验证）

### 技术方案

#### 影响位置

- **服务端路由/服务/API**：预留 `server/app/engine/` 的 ncnn 后端接入点
- **数据模型/迁移/存储**：影响 `MODEL.supported_backends` 的取值集合
- **环境**：`.venvs/` 下**新建独立环境**，**不得污染** `sr-gpu` / `sr-ov` / `sr-ovep`

#### 实现说明

必须遵守"严禁全局安装"（`project-rules.md` §2.1）。验证脚本放在 `tools/`，**不进入应用运行时**（tech-arch §6.7）。

判据：不只看"能否 import"，必须**跑出一次真实推理并检查输出非全黑**——ncnn 有输出全黑的已知 bug。

#### 权威文档引用

- **技术架构**：`docs/tech/tech-arch.md` §6.4 模型格式路由、§6.7 与 `tools/` 的关系、§7 风险 1/2
- **ADR**：`docs/tech/arch/ADR-003-模型格式支持策略.md`
- **需求**：`docs/prd/prd.md` §7.2（风险行）、§7.5
- **项目规则**：`docs/rules/project-rules.md` §2.1

### 实施步骤

1. 在项目内新建隔离环境，尝试 `pip install ncnn`（或等价 wheel）
2. 不可用则评估 pnnx / 自行编译路径的成本，或直接转入降级方案评估
3. 可用则用一张确定性合成图跑最小推理，检查输出均值非全黑、与 ONNX 路径结果量级一致
4. 记录结论 + 建议的 `.bin` 支持策略

### 技术输入与交付

- **输入产物**：`data/models/` 现有 ONNX 权重（作为对照）、`tools/_bench_common.py::make_test_image`
- **输出产物**：验证脚本（`tools/`）+ 结论文档（`docs/tech/research/`）+ PRD §7.5 的措辞更新（如需）
- **对接阶段**：5D `T-806`（模型加载器）、5B（若 UI 需体现"条件支持"）

### 验证与验收

- **验证步骤**：脚本可重复运行并输出确定的结论；结论附原始日志
- **质量门控**：不适用（验证脚本）
- **验收标准**：给出明确的"可用 / 不可用 / 需降级"三选一结论及证据
- **证据落点**：脚本输出日志 + 结论文档

### 风险与恢复

- **风险**：结论为"不可用" → PRD §7.5 需把 ncnn 从"支持"改为"调用外部可执行文件"，`T-806` 接口范围变化
- **兼容性**：仅影响 ncnn 后端，不影响 `.onnx` / OpenVINO 主路径
- **回滚/恢复**：ncnn 定位本就是**条件支持**，不可用即从候选链剔除（tech-arch §7 风险 2）

### 完成结论（2026-10-09 回填）

**验收标准三选一 → ✅ 可用。**

| 判据 | 结果 |
|---|---|
| 获取方式 | PyPI **官方 wheel**（`cp38`~`cp314` × `win_amd64`），**无需自行编译** |
| 真实推理（判据要求，非"仅 import"） | `realesrgan-x4plus` 999 层，64×64 → 256×256 |
| 输出是否全黑 | **未触发**（mean 0.4834 / std 0.1748） |
| 与 ONNX 路径比对（判据要求） | **corr 1.0000 / PSNR 63.39 dB** — 量级与结构完全一致 |
| Vulkan 可用性复核 | wheel 内含 Vulkan，真机枚举 RTX 3050；CPU↔Vulkan 最大差 0.0067 |
| 降级路径评估 | 官方 `realesrgan-ncnn-vulkan.exe` rc=0、220→880 px 非全黑（**即便主路径失效也有一条可用退路**） |

`tools/verify_ncnn_windows.py` **14/14 断言通过**（`verdict = usable`，退出码 0）。

**产物**：`docs/tech/research/图像超分修复-T210-ncnn可用性验证结论.md`（含两条实现陷阱与依赖代价结论）。

**对 T-806 的影响**：ncnn 分支可正式实现，**无需 pnnx 转换工具**；须内建 `Mat(numpy)` 的 CHW/借用缓冲区防御与 `destroy_gpu_instance()` 收尾；安装用 `--no-deps` 以避开 113 MB 的 `opencv-python`。

**遗留**：无阻塞项。未验证范围（非 RealESRGAN 的 ncnn 模型层覆盖、无 Vulkan 设备的回退、无 AVX2 CPU、Intel/AMD 卡）已在结论文档 §5 明示，属 `T-806` 实现期按"加载失败即降级"处理。

## T-306 前置验证：SPAN/SAFMN 在 CPU 上的真实速度

> 承接原 `T-801`（编号保留），从 M2 组移入本阶段执行。

### 目标与边界

#### 目标

测出轻量模型（SPAN / SAFMN）在**纯 CPU** 路径下的真实速度，据此决定 **T0 档的产品承诺**是否成立。

#### 范围内

- 获取 SPAN / SAFMN 的 ONNX 权重（或从开源实现导出）
- 在 CPU 上以 OpenVINO 原生 API 实测（**不是** ORT + OpenVINO EP，后者实测慢 2.5 倍）
- 记录不同 tile 下的耗时与峰值内存（CPU 档瓶颈是**物理内存**不是显存）
- 给出结论：T0 档可用 / 仅预览可用 / 不可用

#### 范围外

- 在应用内实现 SPAN/SAFMN 的加载与调度（属 5D）
- GPU 路径的对比（已有 Real-ESRGAN 的数据）

### 技术方案

#### 影响位置

- **数据模型/迁移/存储**：影响 `MODEL.min_vram_mb` 之外的 CPU 档元信息（是否需要 `min_ram_mb`）
- **需求**：可能影响 PRD §2.3 对 T0 档"用户可感知预期"的表述

#### 实现说明

- 走 **OpenVINO 原生 API**，`sr-ov` 环境（openvino 2026.4.0）——**禁止**在 ORT 里注册 OpenVINO EP（`project-rules.md` §3）；
- CPU 路径**必须 fp32**（无 fp16 加速单元的桌面 CPU 上 fp16 更慢）；
- 必须用**确定性合成图**，与既有基线可比（`tools/_bench_common.py::make_test_image`）；
- 验证脚本放 `tools/`，不进入应用运行时。

#### 权威文档引用

- **技术架构**：`docs/tech/tech-arch.md` §6.1 阶段 A/C、§7 风险 4
- **需求**：`docs/prd/prd.md` §2.3（T0 档承诺）、§3.1（性能阈值用相对量）、§7.2（CPU 档风险）
- **项目规则**：`docs/rules/project-rules.md` §2.2（CPU 禁 fp16、Intel 走 OpenVINO 原生）
- **既有证据**：`docs/tech/research/图像超分修复-P0实测报告.md`

### 实施步骤

1. 获取 / 导出一个轻量模型的 `.onnx`，登记到 `data/models/`
2. 在 `sr-ov` 下用 OpenVINO 原生 API 跑多档 tile 的矩阵
3. 记录耗时与峰值内存，与 Real-ESRGAN 的 CPU 数据对比
4. 给出 T0 档结论，并写明"结论可迁移的边界"

### 技术输入与交付

- **输入产物**：`tools/_bench_common.py`、`tools/bench_openvino_native.py`
- **输出产物**：基准结果（`.workbuddy/results/`）+ 结论文档 + PRD §2.3 / §7.2 的措辞更新（如需）
- **对接阶段**：5D（T0 档的模型清单与降级链）

### 验证与验收

- **验证步骤**：矩阵脚本可重复运行；同参数下结果稳定
- **质量门控**：不适用
- **验收标准**：给出明确的 T0 档结论（可用 / 仅预览 / 不可用）及数据
- **证据落点**：`.workbuddy/results/*.json` + 结论文档

### 风险与恢复

- **风险**：结论为"不可用" → PRD §2.3 中 T0 档"能用 / 预览"的预期需下调，可能连带影响 F-01 的档位标注
- **兼容性**：只影响 T0 档；T1 主链路（Real-ESRGAN + CUDA）不受影响
- **回滚/恢复**：不适用（纯验证任务，无实现可回滚）
