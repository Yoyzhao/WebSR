### 为什么不能拿"已有验证脚本全绿"当验收

步骤 6/7 的验证脚本（`verify_t702_e2e.py` / `verify_t703_quality.py` / `verify_t704_degradation.py` /
`verify_t705_cancel_concurrency.py`）都是**按机制拆**的：它们回答「链路通不通」「画得好不好」
「降级链灵不灵」「取消快不快」。PRD §2.5 的验收标准是**按用户可见功能条目**写的
（`F-01`~`F-07`，每条含多个子项，且明确写了量化阈值：≤1 s / ≤2 s / <5% / 误差 0）。

**两者不是同一件事**：

| 差异 | 按机制拆的脚本 | 按验收条目拆的用例 |
|---|---|---|
| 组织方式 | 一个脚本覆盖一个机制 | 一条用例覆盖一条验收标准，**可逐条判通过/不通过** |
| 是否覆盖"界面" | 多数只到 HTTP 层 | `F-02`/`F-03`/`F-04`/`F-06` 都有**界面**子项，必须浏览器级判 |
| 结论形态 | "N 项断言全绿" | **验收结论**（哪条通过、哪条不通过、为什么），供用户裁决 |

→ 本任务的实质：**换成验收方的视角重新过一遍**，并把结论写成可交付的测试报告。

### 判定纪律

- **量化阈值一律取自 PRD §2.5 原文**（≤1 s / ≤2 s / 误差 0 / <5%），**不自拟**。
- **优先相对/自指判据**（沿用 `T-703` 的教训）：绝对阈值会随内容漂移，容易变成"调参调到绿"。
- **不可判定的条目要如实标"不通过"或"不具备判定条件"**，不得用"相关脚本已全绿"顶替。
- 用例编号遵循 `project-rules.md` §4：`TC-<模块>-XXX`。

### 完成记录（2026-10-10）

- **交付**：`scripts/test-script/verify_t707_performance.py`（真实推理路径，**14 通过 / 0 失败 / 0 跳过**）。
  模型 / tile / 块数全部**从接口推导**，不硬编码本机数值。
- **[1] 提交 P95 ≤ 300 ms**：12 次串行真实提交（96×96 单块图）→ **P95 = 23.0 ms**
  （中位 10.8 ms / 最大 23.0 ms），全部受理无 409 混入。
- **[2] 进度事件间隔（SSE 节流）**：800×600（12 块）真实任务，双侧判据 ——
  ① **节流生效（不洪泛）**：11 帧 / 10.9 s = **1.01 帧/s**（帧数 ≤ max(活跃秒数, 块数)+余量；
  节流机制 = `manager.py THROTTLE_SECONDS=1.0`，首末块必发）；
  ② **不饥饿（新鲜度）**：最大间隔 1.556 s ≤ **1.907 s**
  （自指上界 = 节流 1.0 s + 单块平均 907 ms —— 事件只在块 `report()` 到来时才可能发出）。
  ⚠️ 注意 PRD「间隔 ≤ 1 s」**不能**按字面断言 `gap ≤ 1.0 s`：节流本身就是 1.0 s 周期，
  实测间隔恒 ≈1.0 s + ε —— 字面执行会把机制正确判成失败（与 `TC-S1-025` 同类判据教训）。
- **[3] 峰值 < 可用量 80%（标定安全线）**：1280×960 真实任务（29.3 s，33 个采样点 @150 ms）——
  ① **VRAM**：WDDM 拿不到按进程显存 → 用**设备级相对基线增量**口径：
  任务自身消耗 **2079 MB ≤ 5945 MB**（基线 761 / 峰值 2840 / 总 8192 MB；桌面占用计入基线，不冤枉任务）；
  ② **RAM**：后端进程峰值 **RSS 2051 MB ≤ 2878 MB**（启动时系统可用 3598 MB × 80%）。
- **工具链踩坑**：中文 Windows 的 `netstat`/`tasklist` 输出是 **ANSI（GBK）码页** →
  `subprocess` 必须 `encoding="mbcs"`，否则采样线程 `UnicodeDecodeError`。
- **🔴 顺带逮到并修掉缺陷 5：取消响应违反冻结契约（P1，全量回归批次复现）** ——
  契约 §3.3 冻结点承诺 `POST /api/tasks/{id}/cancel` 响应体为 `status: "canceling"`，
  但原实现是「`manager.cancel()` 置受理态 → 路由**重读 DB** 序列化」，工作线程可能在
  两者之间就翻转终态（协作式取消的固有竞态）→ 响应直接是 `canceled`。
  此前 `T-705` 多轮全绿只是竞态没命中 —— **同一批次里 `t704` 换了判据后机器时序变化，
  竞态连续两轮命中**。修复：`manager.cancel()` 返回**受理时刻**置下的状态，
  路由层以受理时刻为准保证契约响应（客户端随后 GET 仍见真实终态）。
- **测试判据修订（`t704`，时机依赖 → 确定性证据）**：「历史里存在真实的高水位条目」
  依赖任务边界采样恰好落在 WDDM 延迟释放完成之前 —— 而边界采样**设计上就在资源释放
  之后**（`_record_water_level` 排在 `_release_active` 后），采到高水位纯属时机运气
  （同一天先 31/0/1 后连续失败）。改为确定性判据：`_fail_task` 在**受阻瞬间**采的
  `detail.water_level.ratio > 0.5`（降档耗尽 = 分配请求 > 剩余可用的必要推论）；
  边界历史的高水位条目降级为**观察项**（如实登记，不作判定）。
- **诚实边界**：PRD §3.1 其余行不在本任务范围（取消 ≤2 s 归 `T-705`、标定 ≤8 s 归 `T-805`、
  二次启动 ≤200 ms / 单块 ±10% 运行时校验属机制已覆盖项，未在本脚本重复断言）；
  峰值采样粒度 150 ms，短于单块的瞬时尖峰可能低于实际（arena 平台期使该偏差可忽略）；
  判据为单机 T1 实测基线，**不构成对任意硬件的保证**。
