# ADR-002 · 元信息库选 SQLite

- **编号**：ADR-002
- **状态**：✅ 已接受
- **日期**：2026-09-30
- **相关**：PRD §4 数据需求、`dev-info.md` §1

## 背景

应用需要持久化：任务与产物记录、模型库元信息、参数预设、系统配置、标定记录、微调任务。图片与模型**本体不存库**，只存文件路径与哈希（PRD §4.2）。

形态已确定为**单机自用、本机直接运行、不做 Docker**（PRD §3.3、§7.3）。

## 决策

**选用 SQLite**，数据库文件置于数据根下：`data/app.db`。
通过 **ORM（建议 SQLAlchemy 2.x）** 访问，不写裸 SQL 到业务层。

## 后果

**正面**
- 零配置、零常驻服务，与"本机直接运行"完全一致；用户不会因为装不上数据库而用不了
- 单文件即库，随 `data/` 一起备份与迁移，符合"数据根可迁移"的不变量
- Python 内置 `sqlite3`，无额外系统依赖
- 并发量级完全够用：本应用是单用户、任务串行执行，写冲突概率极低
- 经 ORM 抽象后，将来若转多用户/服务端，只需更换连接串与迁移脚本

**负面 / 代价**
- 并发写能力弱（SQLite 默认库级锁）。**缓解**：启用 **WAL 模式**；长任务（推理）绝不持有事务，只在任务状态变更时短事务写入
- 无原生网络访问、无内置鉴权。**缓解**：本应用无多用户需求；若将来开放局域网，必须先补鉴权（PRD §7.3）
- 无连接池与高可用。当前形态不需要

## 实施约束

1. **启动时设 `PRAGMA journal_mode=WAL`** 与 `PRAGMA foreign_keys=ON`
2. **推理过程不得持有数据库事务**——任务开始时写入一次"运行中"，结束时写入结果，中间不落库
3. 表结构变更用 **Alembic** 管理迁移，不手工改表
4. 时间字段统一存 **UTC**，展示层按 `Asia/Shanghai` 转换（避免夏令时/时区歧义）

## 替代方案

| 方案 | 为何未采用 |
|---|---|
| PostgreSQL | 需额外安装并常驻服务，与"本机直接运行、不做 Docker"冲突；对本应用量级属过度设计。**保留为将来服务端形态的迁移目标** |
| MySQL / MariaDB | 同 PostgreSQL，且 Windows 下部署更繁琐 |
| MongoDB | 元信息是强关系结构（任务↔产物、模型↔任务），文档型不占优 |
| 纯 JSON 文件 | 无事务、无索引、并发写会损坏；任务历史查询会退化为全量扫描 |
| Redis | 内存型，不适合做持久主库 |
