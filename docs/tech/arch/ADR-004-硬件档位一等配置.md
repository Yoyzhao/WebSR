# ADR-004 · 硬件档位作为一等配置，能力声明驱动，内置档位模拟

- **编号**：ADR-004
- **状态**：✅ 已接受
- **日期**：2026-09-30
- **相关**：PRD §1.4、§2.2 B 段、§2.3、§7.1；`docs/tech/research/图像超分修复-跨环境自适应设计.md`

## 背景

三个约束同时成立：

1. **开发机只有 T1 硬件**（RTX 3050 OEM 8G + 无核显的 i5-12400F），**没有 T2（16–24G）/ T3（专业卡）可测**
2. 用户要求 **T2/T3 功能照常实现**，但因无法测试而排在低优先级（P3）
3. 本机实测的**绝对数值不得进入产品**（单机样本，换机器即变）

天真做法有两种，都不可接受：① 只做 T1，把 T2/T3 留给将来（等于把架构堵死）；② 凭想象实现 T2/T3，写成按设备型号硬编码的分支（等于写不可维护的盲代码）。

## 决策

### 1. 硬件档位（Tier）是一等概念，贯穿全栈

`T0` 纯 CPU ｜ `T1` 消费级 8G ｜ `T2` 高端 16–24G ｜ `T3` 专业卡。

档位维度必须出现在：引擎能力声明、模型元信息（最低显存需求）、参数预设、UI 过滤与置灰、调度策略、并发度上限、输入尺寸上限。

### 2. 一切分支按**能力声明**，禁止按设备型号

- ❌ 禁止 `if "4090" in gpu_name`
- ✅ 只读能力字段：`vram_available_mb`、`supports_fp16`、`supports_batch`、`has_tensorrt`、`supports_tile0`、`is_generative` 等

### 3. 必须内置**档位模拟开关**

允许强制声明档位与能力（`force_tier` / `force_vram` / `force_has_tensorrt` / …），**绕过真实探测**，用于在 T1 机器上真实执行 T2/T3 的代码路径。

### 4. 明确"控制面可验证、数据面不可验证"

| | 内容 | T1 上能否验证 |
|---|---|---|
| **控制面** | 档位判定、能力门控、参数传递、调度策略切换、UI 置灰/解禁、错误与降级链 | ✅ **能**（占代码量绝大多数） |
| **数据面** | 真实吞吐、显存占用、驱动兼容性 | ❌ 不能，必须等硬件 |

### 5. 交付时标注状态

P3 功能在 UI 与文档中标注 **"未验证（当前无对应硬件）"**；用户在有硬件的机器上首次使用时走**自标定 + 首次运行验证**，而非假定可用。

## 后果

**正面**
- 把"无硬件 = 无法验证"从"整块不可验证"压缩到"只有数据面不可验证"——**控制面能在 T1 上真跑**
- 档位模拟开关使 T2/T3 分支**真的被执行过**，避免盲写
- 能力声明驱动使真卡到位时只需验证、不需改逻辑
- T2/T3 的实现不阻塞 T1 主链路，P3 失败可安全绕过

**负面 / 代价**
- 档位模拟开关是**新增的测试设施**，需要自己实现与维护（列入 T-901/T-902，且为 P3-首）
- 能力声明字段需要提前设计，部分字段在 T1 上恒为固定值（如 `has_tensorrt=false`），有"设计了但长期不用"的成本
- 新增"档位"维度使数据模型与 UI 都变复杂（模型列表要按档位过滤、预设要绑定档位）

## 实施约束

1. 档位模拟开关放在**开发者设置**中，并显式提示"模拟档位仅用于测试，不代表真实能力"
2. **P3 代码失败必须可安全绕过**，不得影响 T1 用户
3. 档位对用户**可见**：面板显示识别出的档位；模型在非适用档位置上置灰并说明原因（如"该模型需 ≥16 GB 显存，当前 7.4 GB"）
4. 档位判定结果与理由必须写入诊断 JSON，可一键导出

## 替代方案

| 方案 | 为何未采用 |
|---|---|
| 只做 T1，T2/T3 全部推迟 | 用户明确要求"高端功能也实现"。且架构上后补需要改数据模型与契约 |
| 凭推测实现 T2/T3，按型号硬编码 | 真卡到位后必然要重写；且型号枚举永远不全（新卡、OEM 改版、笔记本变体） |
| 用 mock 单元测试替代档位模拟 | 单元测试覆盖不到"参数在真实管线里的传递与降级链"；档位模拟是**端到端**的执行路径 |
| 租/借云 GPU 验证 | 成本高且不可持续；云卡多无消费级驱动环境，代表性也差。可作为将来一次性验证手段 |
