# ADR-003 · 模型格式支持策略

- **编号**：ADR-003
- **状态**：✅ 已接受
- **日期**：2026-09-30
- **相关**：PRD §7.5、PRD §8（原待确认项 1 / 7 / 8）

## 背景

用户指定支持 4 种模型格式：`.onnx` / `.bin` / `.pth` / `.safetensors`。

这 4 种格式的加载代价差异极大：

- `.onnx` —— 主路径，ORT / OpenVINO 直接吃，**零额外依赖**（已验证）
- `.pth` / `.safetensors` —— PyTorch 原生格式，**读取需要 PyTorch**（数百 MB ~ 2.5 GB）
- `.bin` —— **同名不同格式**：OpenVINO IR 的权重体（配 `.xml`）与 ncnn 的权重体（配 `.param`）

## 决策

### 1. `.pth` / `.safetensors`：走**离线转换**，应用内**不捆绑 PyTorch**

- 提供独立的**转换工具**（`tools/` 下的脚本或后端一次性任务）：`.pth`/`.safetensors` → `.onnx`
- 应用**只加载转换产物**（`.onnx`）
- 应用可**登记**原始 `.pth`/`.safetensors`，但状态标记为"需先转换"，并给出转换入口
- `.safetensors` 的架构识别依赖 `architecture` 元数据（spandrel 类能力），若无法识别则明确报错而非猜测

### 2. `.bin`：**两种来源都支持**，靠配套文件分派

| 配套文件 | 判定 | 加载路径 |
|---|---|---|
| 存在 `.xml` | **OpenVINO IR** | OpenVINO 原生 API（已验证路径） |
| 存在 `.param` | **ncnn** | ncnn 运行时 |
| 都没有 | **拒绝导入** | 提示"`.bin` 必须与 `.xml` 或 `.param` 一同提供" |

**导入流程必须显式要求用户同时选择配套文件，禁止靠文件名或内容猜测。**

## 后果

**正面**
- 应用依赖保持干净：主依赖仍是 ORT + OpenVINO，体积可控、启动快、打包简单
- 与既有 ONNX 主链路一致，不引入第二种运行时语义
- `.bin` 双来源靠配套文件分派，判定是确定性的，不存在歧义

**负面 / 代价**
- 用户拿到 `.pth` 不能直接拖进去用，必须先转换 —— **这是本决策最大的体验损失**
  - **缓解**：转换工具做成一键操作；模型库对 `.pth` 文件显示"转换"按钮而非报错
- ncnn 引入**两个真实风险**（见下）

**ncnn 相关的风险（必须在实现前验证）**

1. **Windows + Python 下的获取方式未验证**：ncnn 的 Python 绑定在 Windows 上的可用安装方式（pip wheel 或需自行编译）**尚未确认**；若不可行，需降级为调用 `realesrgan-ncnn-vulkan` 可执行文件
2. **官方模型少且有"黑图"已知 bug**：ncnn 官方仓库仅有 4 个模型，且存在输出全黑的已知问题（记于上游 TODO）；Vulkan 在部分驱动上亦可能不可用
3. **对策**：ncnn 定位为**可选后端**，探测失败即降级到 OpenVINO/ORT；ncnn 加载失败**不得影响其它格式**

## 替代方案

| 方案 | 为何未采用 |
|---|---|
| 应用内捆绑 PyTorch + spandrel，直接加载 `.pth`/`.safetensors` | 用户明确选择离线转换。捆绑会让依赖增加数百 MB ~ 2.5 GB，启动与打包显著变重，而本应用对 `.pth` 的需求本质是"把我训练的权重用起来"，转换成 ONNX 后收益相同 |
| 只支持 `.onnx`（原建议） | 用户明确要求 4 种格式 |
| `.bin` 只支持 OpenVINO IR | 用户明确要求也支持 ncnn |
| 靠文件内容魔数自动识别 `.bin` 来源 | OpenVINO `.bin` 与 ncnn `.bin` 头部特征不构成可靠判据；靠配套文件是确定性做法 |
