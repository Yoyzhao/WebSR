# ADR-005 · 推理内嵌后端进程 + 异步任务队列 + SSE 进度推送

- **编号**：ADR-005
- **状态**：✅ 已接受
- **日期**：2026-09-30
- **相关**：PRD §3.1 NFR、§7.1、`dev-info.md` §1

## 背景

两个已确认的需求约束：

1. 用户在需求澄清中选定：**推理在后端 Python 进程内**、**长任务走异步任务队列 + 进度推送**
2. 实测数据（单机样本，仅作量级参照）：CPU 上 1080p 整图约 4.5 分钟量级；GPU 上约 20 秒量级 → **同步 HTTP 接口必然超时，且无法取消**

## 决策

### 1. 推理内嵌后端进程

FastAPI 进程内直接持有 ORT / OpenVINO 会话，不引入独立的推理服务进程或消息中间件。

### 2. 任务执行与请求处理隔离

- 任务在**独立的工作线程/执行器**中运行，**不得占用事件循环**
- 接口层（`/api/tasks` 等）保持轻量、快速返回
- **并发度默认 1**，上限由可用内存/显存反推（不写死），见 ADR-004

### 3. 进度用 SSE（Server-Sent Events）

- `GET /api/tasks/{id}/events` 推送进度事件
- 事件至少包含：阶段、已完成/总块数、百分比、已用时、估算剩余
- 任务状态变更同时落库，**刷新页面后可从任务详情恢复进度显示**

### 4. 取消是显式能力

- `POST /api/tasks/{id}/cancel`
- 取消需在 ≤ 2 s 内生效并释放资源（PRD §3.1）
- 取消后清理中间产物

### 5. 不用 try/except OOM 当主要降档手段

按水位主动降档（连续 2 次峰值 > 85% 可用即降一档），OOM 只是最后一道防线（PRD §7、自适应设计 §七）。

## 后果

**正面**
- 零额外基础设施：无需 Redis / Celery / 消息队列 / 独立推理服务，与"本机直接运行"一致
- 复用已验证的推理环境，无跨进程序列化开销
- SSE 比 WebSocket 简单：单向推送、原生自动重连、无握手协议，浏览器原生支持
- 事件循环不被推理阻塞，接口保持可用

**负面 / 代价**
- **进程内崩溃会连带后端一起挂**。缓解：P3 代码与实验性后端必须在独立子进程中执行，异常不得穿透
- **推理与 API 争抢 GIL/CPU**。缓解：推理是 C 扩展调用（ORT/OpenVINO 会释放 GIL），实际影响小；但仍需实测
- **单进程无法水平扩展**。当前形态（单机自用）不需要；若转服务端形态需重新设计（届时见 §替代方案）
- SSE 在 HTTP/1.1 下有连接数限制；本地单用户不构成问题
- 任务队列是**进程内**的，重启后运行中的任务会丢失。缓解：启动时把"运行中"状态的任务标记为"已中断"并提示

## 实施约束

1. **推理绝不持有数据库事务**（配合 ADR-002）
2. 任务状态机：`待执行 → 运行中 → 已完成 / 已取消 / 失败`；重启后"运行中"须被回收为"已中断"
3. 取消采用协作式（在分块循环的每个块之间检查取消标志），**不得强杀线程**
4. 进度事件节流：**≤ 1 s 一次**，避免高频推送拖慢推理
5. 后端必须绑 `127.0.0.1`（PRD §3.2）

## 替代方案

| 方案 | 为何未采用 |
|---|---|
| 独立推理服务进程（HTTP/gRPC） | 多一层通信与运维；对"单机自用"是过度设计。**但这是崩溃隔离更好的做法**，若 P3/扩散栈引入后稳定性变差，可作为演进方向 |
| Celery + Redis 任务队列 | 需要 Redis 常驻服务，与"不做 Docker、本机直接运行"冲突；本应用任务量级不需要 |
| WebSocket | 双向能力用不上；SSE 更简单且自带重连语义 |
| 同步接口 + 长超时 | 已由需求排除：无法取消、页面刷新即丢、易被代理/浏览器超时切断 |
| 轮询任务详情接口（不用 SSE） | 可行但实时性差、请求量大。**可作为 SSE 失败时的降级通道保留** |
