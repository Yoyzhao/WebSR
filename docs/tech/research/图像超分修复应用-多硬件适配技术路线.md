# 图像超分 / 修复应用 · 多硬件适配技术路线选型

> 目标：**一套代码**，同时适配「纯 CPU」「消费级 8G 显卡（RTX 3050 8G / 4060 Ti 8G）」「专业级显卡（RTX PRO 5000 48G / H20 96G）」
> 日期：2026-09-29

---

## 一、一句话结论

**不要做四个版本，做「一个推理核心 + 三个硬件档位（Profile）」。**

- 用 **ONNX 作为统一中间格式**，一份权重在 CPU / CUDA / TensorRT / 浏览器 WebGPU 四处复用；
- 用 **spandrel** 加载模型，避免为每个网络架构手写实现；
- 用 **Profile 机制**（自动探测硬件 → 选模型档位 + 精度 + tile 参数）替代运行时到处写 `if`；
- 高端档（SUPIR / HYPIR / SeedVR2）**只放在专业卡形态**，不做全集兼容。

一句话选型：**低端保"能用"，中端保"好用"，高端保"惊艳"，三者共享同一套业务代码。**

---

## 二、核心架构：三层解耦

```
┌─────────────────────────────────────────────────────┐
│  应用层    UI / 任务队列 / 批处理 / 结果管理 / 模型下载   │
├─────────────────────────────────────────────────────┤
│  能力层    硬件探测 → Profile 选择 → 任务路由与降级      │
│           (tier / precision / tile / model-档位)       │
├─────────────────────────────────────────────────────┤
│  推理层    统一接口 IEngine                            │
│           ├─ ncnn-Vulkan   （CPU / 任意 GPU / 核显）    │
│           ├─ ONNX Runtime  （CPU EP / CUDA EP / WebGPU）│
│           ├─ TensorRT      （N 卡极致性能）             │
│           └─ PyTorch       （扩散类大模型，无法导出时）    │
├─────────────────────────────────────────────────────┤
│  模型层    Model Zoo：每个能力提供 S / M / L 三档权重    │
│           （统一用 spandrel 识别与加载）                 │
└─────────────────────────────────────────────────────┘
```

### 六条设计铁律

1. **ONNX 优先**。凡是能导出 ONNX 的（Real-ESRGAN、SwinIR、HAT、GFPGAN、Real-CUGAN）一律走 ONNX。这一步决定了你的应用能不能"一次开发、四处部署"。
2. **扩散类单独成池**。OSEDiff / HYPIR / SUPIR 这类多分支 + 动态 shape 的模型导出 ONNX 极其痛苦且收益有限，**留给 PyTorch / TensorRT 后端**，只在高档位暴露。
3. **同一个能力必须有"小模型兜底"**。每个功能（通用放大 / 人脸修复 / 动漫）都要有 tiny 版本，否则 CPU 用户直接不可用。
4. **tile 与精度由 Profile 注入，绝不写死**。这是显存适配的唯一有效手段。
5. **数值不硬编码，机制才硬编码**。本机实测的任何绝对值（倍数、秒数、MB、tile 甜点）都**只对那一台机器成立**，产品里必须由运行时探测 + 首启自标定得出。可以写入代码的是**因果性防御**（EP 真实性校验、arena 策略覆盖、集显判定看 `FULL_DEVICE_NAME`、OOM 降档）。详见 `图像超分修复-跨环境自适应设计.md`。
6. **降级必须是显式的**。显存不足 → 自动缩小 tile → 仍不足 → 换小模型 → 仍不足 → 提示"当前硬件不支持该档位"。不要静默降画质。

## 四、逐档详解

### Tier 0 · 只有 CPU

**推荐组合**
- **首选（纯 CPU 与 Intel 平台）**：**OpenVINO 原生 API**。Intel 官方有 Real-ESRGAN 的部署指南（文档 816445），但**该文档不含任何性能数字**，只含流程与代码。常被引用的"快 5~13 倍"来自第三方仓库在 **Xeon Platinum 8581C（8C/16T，AVX-512 + AMX）** 上的测试，**不代表消费级 CPU**。流程为 `PyTorch .pth → ONNX → OpenVINO IR → 推理`，`device_name="AUTO"` 会自动在 CPU/GPU/NPU 间选择。
  - 📌 **已实测（i5-12400F，2026-09-29）**：相对 ORT CPU EP 真实倍数是 **1.64x**（x4plus，fp32，tile 256/512），**不是 2~4x，更不是 13x**。1080p 整图 **272.6 s ≈ 4.5 min**（tile 512，RSS 3.55 GB）。
  - 📌 **CPU 上务必用 fp32**：实测 fp16 无收益（tile 256：5936 ms vs fp32 4894 ms）——桌面 CPU 无 fp16 加速单元，反而增加转换开销。
  - ⛔ **不要经 ORT 注册 OpenVINO EP**：实测比 ORT 自己的 CPU EP **还慢 2.5 倍**、比 OpenVINO 原生慢 4 倍。详见 `图像超分修复-P0实测报告.md` §5。
- 备选：**ncnn-Vulkan**（Real-ESRGAN / Real-CUGAN 官方都有 `.param` + `.bin`，无需 CUDA，Windows/macOS/Linux/ARM 全覆盖，且能直接吃到 Intel 集显的 Vulkan）。无 Vulkan 设备时走 CPU 线程。
- 部署最干净：**ONNX Runtime CPU EP + int8 量化**。
- 极轻兜底：**OpenCV `dnn_superres`** 加载 FSRCNN / ESPCN / EDSR —— 模型只有几 MB，CPU 上秒级出图，**质量明显弱于 Real-ESRGAN**，适合"实时预览"而非"最终输出"。

**⚠️ Intel 平台的后端优先级（易踩坑）**：
```
OpenVINO 原生  ≫  ncnn-Vulkan  >  ONNX Runtime CPU EP  ≫  DirectML（不要用）
                                  ✗ ONNX Runtime + OpenVINO EP（实测慢 2.5x，不要用）
```
实测（Arc A750 + yolo11n）：OpenVINO GPU **3.8ms** / ORT CPU 26.9ms / **DirectML 73.1ms**。
**DirectML 在 Intel 平台上比纯 CPU 还慢 2~3 倍**，且已进入维护模式，新项目不要作为主路径。
本机实测（i5-12400F + x4plus）：OpenVINO 原生 **4893.9 ms** / ORT CPU EP 8004.5 ms / **ORT+OpenVINO EP 20358.9 ms**（tile 256）。

**必须做的工程约束**
- CPU 上**不要开 fp16**（PyTorch CPU 直接不支持，会报错或静默降级）；
- 限制输入边长（建议 ≤1280），否则单图可能跑到十几分钟；
- 使用**多线程 + 分块并行**，而不是单张大图整体推理；
- UI 上明确标注"CPU 模式（慢速）"，并默认勾选**小模型 + 2x**，把 4x 作为高级选项。

**不要做**：不要试图在 CPU 上跑任何扩散模型（OSEDiff / SUPIR / HYPIR），耗时不可接受。

---

### Tier 1 · RTX 3050 8G / 4060 Ti 8G（最需要优化的一档）

这是**用户量最大、也最容易翻车**的一档。核心矛盾：8G 显存能装下 Real-ESRGAN，但装不下扩散模型。

**推荐组合**

| 能力 | 模型 | 说明 |
|---|---|---|
| 通用放大 | `RealESRGAN_x4plus`（fp16） | 主力。fp16 下权重+激活约 1.6–2GB，加框架开销实测峰值 2.5–4GB |
| 通用放大（省显存） | `realesr-general-x4v3` | 官方 tiny 模型，速度快数倍，带 `-dn` 去噪强度调节 |
| 动漫 | `RealESRGAN_x4plus_anime_6B` / `Real-CUGAN` | 体积小，8G 完全无压力 |
| 人脸 | GFPGAN v1.4 或 CodeFormer | 必须作为**独立第二阶段**串接 |
| 视频（可选） | `realesr-animevideov3`（2/3/4x） | 逐帧，8G 可跑 1080p 动漫 |
| 高质量模式（可选下载） | **HYPIR-SD2 LoRA** 或 **OSEDiff-SD21-base** | 需 tiling + 分阶段加载权重，8G 能跑但慢，**定位为"可选增强包"而非默认** |

**8G 的关键参数**

> ⚠️ **下表是本机（RTX 3050 OEM，2026-09-29）的标定结果，用于说明"标定应产出什么"，不是产品默认值。**
> 产品必须按 §八之二 的自标定流程现场重算——同一张 3050，显存被桌面进程占用不同，甜点 tile 就会变；换成 4060 Ti，所有数字都要重算。
> 真正跨硬件不变的是**机制**（`arena_extend_strategy` 必须覆盖、必须验 EP 真实性），不是这些数值。

```
tile = 384          # 本机标定：948 ms/块，峰值 3.2 GB（占可用 42%）→ 落在"峰值 <80% 可用"区间，定为稳健全局最优
                    # tile 512 本机也能跑：1.67 s/块，峰值 5.6 GB（占可用 74%），更激进
tile_pad = 10~32    # 出现网格接缝就调到 32（本机未做羽化，见质量缺陷）
half = True         # 本机实测 fp16 相对 fp32：显存 -23~32%（非 -40%），速度 +46~77%（非 +30%）
fp32 = False        # ⚠️ 极端场景才开：本机 fp32@512 峰值 7.29 GB = 可用显存的 96.2%，已进危险区
batch = 1           # 视频场景可适度增大，图像场景保持 1
```

**必设的 ORT 参数（这是机制，可跨硬件硬编码）**
```python
opts = {
    "arena_extend_strategy": "kSameAsRequested",  # ORT 默认 kNextPowerOfTwo → 本机 fp32@512 实测 31 s vs 3 s
    "cudnn_conv_algo_search": "HEURISTIC",        # 默认 EXHAUSTIVE，本机影响 <3% 但更省 workspace
    "do_copy_in_default_stream": "1",
}
```

**可用显存必须现场探测，不要假设标称值**：本机标称 8 GB，桌面进程占用后实测可用仅 **7.4 GB**。用户机器上这个值天天在变，产品应当以 `nvml` 实读为准，并对"显存被别的程序占满"这一常见真实情况给出明确提示而不是崩在 OOM。

**显存不足的自动降级链**（顺序是机制；具体 tile 值是标定结果）
```
tile 512 → 384 → 320 → 256 → 128 → 换 general-x4v3 小模型 → 提示不支持
```
降级判定**不要靠 try/except OOM**，应在每次切换后读一次真实可用显存，按"峰值是否 < 80% 可用"决定继续还是再降。

**明确不要放的东西**
- ❌ SUPIR（需 16GB 起步、24GB 才舒服，8G 上必然 OOM 或疯狂 swapping）
- ❌ SeedVR2-3B（官方说明最低也要约 18GB，除非用 GGUF-Q4 + BlockSwap 勉强降到 8G，但速度惨不忍睹）
- ❌ 默认开启的扩散模型。做成"用户主动下载 + 明确告知很慢"的可选包。

### Tier 2 · 16–24G（过渡档，可选实现）

- tile 可放宽到 768 或直接 `tile=0` 不分块；
- 可引入 **DiffBIR v2.1**（支持 tiled sampling，显存友好）、**StableSR**（128→512 仅约 8.9GB）；
- 视频可上 **SeedVR2-3B**（FP8/FP16）；
- 如果产品线要精简，**这一档可以合并进 Tier 3 的"中配预设"**，不必单独维护。

---

### Tier 3 · 专业级（RTX PRO 5000 48G / H20 96G）

**推荐组合**
- **SUPIR v0Q / v0F**：开源画质上限，SDXL + LLaVA 多模态引导，24GB 显存起步
- **HYPIR**（完整版，8K 细节 + 文字保真）
- **DiffBIR v2.1** / **SeedVR2-7B**（视频）
- 全部开启 **batch > 1**、**bf16**、**TensorRT 引擎**

#### ⚠️ 这里有一个非常容易踩的坑：H20 不是"加速卡"，是"吞吐卡"

| | RTX PRO 5000 Blackwell | H20 |
|---|---|---|
| 显存 | 48 GB GDDR7 | **96 GB HBM3** |
| 带宽 | 1.34 TB/s | **4.0 TB/s**（约为 3 倍） |
| FP32 算力 | **≈66.9 TFLOPS** | ≈39.5 TFLOPS |
| FP16 算力 | ≈66.9 TFLOPS（dense） | ≈148 TFLOPS（含稀疏口径） |
| 定位 | 桌面工作站 | 数据中心 |

**结论：**
- H20 的优势是**大显存 + 高带宽**，它的**单图延迟不一定优于 4060 Ti**——超分是计算密集型（卷积/注意力），H20 的算力被刻意限制过。
- 因此 **H20 的正确用法是**：
  1. 装得下 SUPIR / SeedVR2-7B 这类塞不进小卡的模型；
  2. 做**高并发批处理服务器**（大 batch + 线程池），把 4 TB/s 带宽和 96G 显存吃满；
  3. 不要把它当"提高单张出图速度"的手段。
- **如果产品目标是"单图低延迟"**，选 RTX PRO 5000 甚至 4060 Ti 都比 H20 更合理；**如果目标是"每分钟处理 N 张"，H20 才划算**。

## 五、格式与后端策略（决定长期维护成本）

| 模型类型 | 推荐格式 | 后端 | 备注 |
|---|---|---|---|
| Real-ESRGAN / Real-CUGAN / waifu2x | **ncnn (.param+.bin)** 与 **ONNX** 双份 | ncnn-Vulkan / ORT | 社区已有现成 ncnn 权重，直接复用 |
| SwinIR / HAT / DAT / SRVGGNet | **ONNX**（fp16） | ORT CUDA / TensorRT | 静态 shape，导出顺畅 |
| 人脸（GFPGAN / CodeFormer） | **ONNX** | ORT / TensorRT | 注意人脸检测器（RetinaFace/facexlib）也要一起导出 |
| 扩散类（OSEDiff / HYPIR / SUPIR / DiffBIR） | **PyTorch / .safetensors** | PyTorch → TensorRT | 动态 shape + 多分支，ONNX 导出性价比低 |
| 浏览器端 | **ONNX（fp16/int8）** → ORT Web / TF.js | WebGPU / WASM | 只放小模型 |

**Intel 平台额外多一步**：ONNX 再转 **OpenVINO IR（`.xml`/`.bin`）**，这是 Intel CPU / 集显的正解，细节见 `当前环境检测报告与可用方案.md` 第六节。（注：网上流传的"快 5~13 倍"实测于 Xeon 8581C+AMX，**不是消费级 CPU 的数字**。）

**TensorRT 加速路径**（8G 卡上也能再提速 1.5~2x）：
```
.pth → export ONNX（固定 batch/shape）→ trtexec --fp16 → .trt 引擎
    → 首次在目标机器上构建引擎（引擎与 GPU 架构/驱动版本绑定，不能跨机器分发）
```
⚠️ 注意：`.trt` 引擎**不可跨 GPU 型号分发**，必须在用户机器上构建（首次启动耗时较长，需做好进度提示与缓存）。

## 六、强烈建议使用 spandrel：不要自己写网络结构

**spandrel** 是从 chaiNNer 抽出来的库（核心包 **MIT 许可**），能**自动识别权重文件的架构与超参**并提供统一推理接口。目前已支持：

- 超分：ESRGAN(RRDBNet，含 Real-ESRGAN/RealSR/BSRGAN)、SRVGGNet(Real-ESRGAN Compact)、SwinIR、Swin2SR、**HAT**、DAT、Omni-SR、SRFormer、GRLIR、DITN、FeMaSR、SPAN、RCAN、**Real-CUGAN**
- 人脸：**GFPGAN**、**CodeFormer**、RestoreFormer
- 去噪：SCUNet、NAFNet、KBNet、Uformer ｜ 去 JPEG：FBCNN ｜ 上色：DDColor ｜ 修补：LaMa、MAT
- 支持 `.pth` / `.pt` / `.safetensors`，并给出 `scale`、`supports_half`、`size_requirements` 等元信息——**这些元信息正好可以用来驱动你的 Profile 决策**。

```python
import spandrel
model = spandrel.ModelLoader().load_from_file("RealESRGAN_x4plus.pth")
print(model.architecture, model.scale, model.supports_half, model.size_requirements)
```

**许可隔离设计（商用产品必看）**
- `spandrel`（核心）：只含 MIT / Apache-2.0 / 公有领域架构 → **商用安全**
- `spandrel_extra_arches`（可选包）：含非商用等限制性许可架构 → **单独安装、单独标注、界面提示**

把这两个包拆开，你的商用版可以只装核心包，社区版装全部——**这是最省事的合规方案**。
另注：spandrel 会对 `.pth` 反序列化做白名单限制，但**仍建议优先分发 `.safetensors`** 以彻底规避 pickle 任意代码执行风险。

## 七、部署形态决定能覆盖哪些档位（请先确认你要做哪一种）

| 形态 | 技术栈 | 能覆盖 | 不能覆盖 |
|---|---|---|---|
| **A. 纯浏览器端** | ONNX Runtime Web（WebGPU EP + WASM 回退）/ TensorFlow.js | Tier 0（WASM）～ Tier 1（WebGPU） | **Tier 2/3 完全做不到**，扩散类一律不可用 |
| **B. 本地原生客户端** ⭐ | Tauri/Electron + 本地推理进程（C++ ncnn 或 Python ORT/TensorRT） | **Tier 0 ～ Tier 3 全覆盖** | 需处理多平台打包与模型分发 |
| **C. 云端服务端** | 按档分机型 + 任务队列 + 路由 | 全覆盖，且能动态扩容 | 需考虑带宽、排队、隐私合规 |

**浏览器端的实测参考**：Real-ESRGAN ONNX 模型约 17MB，WebGPU 下 2x/4x 约 500ms–2s，Chrome/Edge 113+ / Firefox 121+ / Safari 2025+ 支持；无 WebGPU 时回退 WASM，**慢 10~100 倍**。必须做分块 + overlap（建议 min_overlap ≥ 12），否则接缝可见。高端档只能调服务端 API。

> 如果产品名里的 "Web" 指"浏览器内运行"，那么务实的路线是：**浏览器端做 Tier 0/1（WebGPU + 小模型），Tier 3 用服务端 API 兜底**；不要试图在浏览器里跑 SUPIR。

## 八、显存 / tile 调参速查

> ⚠️ **本表是"标定结果的合理参照区间"，不是查表即用的参数表。** 它是经验值 + 单机实测的混合，用来给自标定算法一个**起步点和上下界**，避免从 0 搜索。真实取值必须现场测（同机不同时刻都可能变）。

Real-ESRGAN 的 tile 参数是最有效的显存开关（`tile=0` 表示不分块、最快、最费显存）：

| 显存 | 可不分块的最大分辨率 | 推荐 tile（起步点） | 性能损失 |
|---|---|---|---|
| 2–4 GB | 很小 | 128 | 大 |
| 4–6 GB | — | 256 | 较大 |
| **8 GB** | ~1920×1080 | **512**（若被占用则退 384） | ~15% |
| 12 GB | ~2560×1440 | 768 | ~8% |
| 24 GB+ | ~3840×2160 | **0** | ~0% |

其他要点：
- `tile_pad` 控制块间重叠，10 起步，出现网格线就加到 32。**注意 pad 不是羽化**——只加 pad 不加混合权重仍会有接缝，生产版必须做 overlap + feather；
- **fp16 几乎白送，但仅限有 fp16 单元的 GPU**：本机（3050）实测显存 **-23~32%**、速度 **+46~77%**、PSNR 损失 <0.2dB；**CPU 上反向**（i5-12400F 实测 fp16 更慢），所以 `half` 必须由探测决定，不能全局开；
- 避免色彩错乱：Real-ESRGAN 系期望 **BGR** 输入（OpenCV 约定），PIL 读取后必须转换；
- SwinIR/HAT 类要求输入边长向上取整到窗口倍数（SwinIR 为 8），否则会报尺寸不匹配。

### 八之二、自标定：把上面这些数字变成运行时的结论

这是"一次开发、四处部署"能不能真正成立的**关键机制**。完整设计见 **`图像超分修复-跨环境自适应设计.md`**，此处给出骨架：

```
启动
 └─ 能力探测（静态、毫秒级）：CPU 指令集/核数/内存、GPU 型号与架构、驱动版本、
    EP 可用性、OpenVINO 设备（看 FULL_DEVICE_NAME）、是否笔记本双显卡
      ↓
 └─ 首启自标定（一次，秒~分钟级，结果缓存到本地）
    ① 在若干候选 tile 上跑 3~5 次，记录 p50 与峰值可用显存
    ② 选"峰值 < 80% 可用显存"前提下最大的 tile（留 20% 余量给波动）
    ③ 用 1 个小样例对照 fp16 vs fp32 的 max_abs/PSNR，达标才启用 fp16
    ④ 对候选 EP 各跑一次，**用 profile 验证节点真的落在该 EP 上**，并取实测最快者
      ↓
 └─ 运行时反馈（每次任务）
    · 任务前后读可用显存/内存；连续 N 次峰值 > 85% → 自动降一档并记入缓存
    · 出现 OOM/异常 → 降档重试一次 → 仍失败才报错（不静默降画质，要提示用户）
```

**为什么必须这样**：本机是一张 3050 + 一颗无核显的 i5。用它的数值去覆盖 40 系卡、核显笔记本、老驱动、显存被占满的用户，必然翻车。而**上面这套流程与硬件无关**——它把"适配"从开发期的猜测，变成用户机器上的测量。

## 九、落地路线图（建议按此顺序做）

**v1 · 两个档位就能上线（覆盖约 80% 用户）**
1. 抽象出 `IEngine` 接口 + `Profile` 数据结构；
2. 实现 Tier 0（**OpenVINO 原生 fp32**，兜底再叠 ncnn-Vulkan）+ Tier 1（ONNX Runtime CUDA + Real-ESRGAN fp16 + **tile 384 稳健 / 512 甜点**）；
3. 人脸走固定的"整图放大 → CodeFormer 精修 → 融合"两阶段管线（所有档位共用）；
4. 硬件探测 + 显存自适应 + 显式降级提示。

**v2 · 让它"可扩展"**
5. 接入 spandrel，把"新增模型"变成加一行配置；
6. 加模型下载管理器（按需下载、校验哈希、断点续传）；
7. 加 TensorRT 引擎的本地构建与缓存。

**v3 · 拉高上限**
8. 引入扩散模型池（HYPIR / OSEDiff / InvSR），仅在显存 ≥16G 时暴露；
9. 专业档接 SUPIR / SeedVR2-7B + batching；
10. 服务端形态与客户端形态共享同一套 Profile 定义。

## 十、反面清单（明确不要做）

- ❌ **不要为每种硬件写一套代码/分支**，维护成本会爆炸。
- ❌ **不要默认开启扩散模型**。8G 用户会立刻 OOM 并给你差评。
- ❌ **不要在 CPU 上启用 fp16**。
- ❌ **不要把 `.trt` 引擎打进安装包**（绑定 GPU 架构与驱动，必须现场构建）。
- ❌ **不要在浏览器端规划 SUPIR / SeedVR2**（显存与导出都不可行）。
- ❌ **不要静默降级**：用户必须知道"当前是 CPU 模式/小模型模式/轻量档"。
- ❌ **不要把 H20 当单图加速卡买**——它是吞吐卡，不是延迟卡。
- ❌ **不要把 Ultralytics 式的"通用模型"幻想成万能**：超分没有万能模型，通用 / 人脸 / 动漫 / 文字必须分模型。
