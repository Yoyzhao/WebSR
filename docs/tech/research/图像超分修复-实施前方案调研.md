## 0. 一句话结论

**最终方案 = 一个 ONNX 模型库 + 一个 ONNX Runtime 会话（按可用性注册 EP）+ ncnn-Vulkan 兜底通道。**

但本轮调研发现了一个比"选后端"更重要的东西：**决定 CPU/集显用户能不能用的，不是后端，是模型参数量。**

RealESRGAN_x4plus 是 16.7M 参数 / 约 89 GFLOPs（256² 输入）。而 SPAN 是 **411K 参数**、SAFMN 是 **240K 参数**——差距 **40~70 倍**。同一个 CPU 上，x4plus 是"分钟级"，SPAN/SAFMN 是"秒级"。**所以方案里必须同时准备"画质模型"和"速度模型"两条模型线**，而不是只做一套权重。

## 2. 模型侧调研（本轮最关键的发现）

### 2.1 参数量 vs 算力：CPU 可用性的真正分水岭

| 模型 | 架构 | 参数量 | 算力参考 | 权重体积 | 许可 |
|---|---|---|---|---|---|
| RealESRGAN_x4plus | RRDBNet 23 blocks | **16.7M** | 89.2 GFLOPs @256² | ~67 MB | BSD-3 |
| RealESRGAN_x4plus_anime_6B | RRDBNet 6 blocks | 5.9M | — | 17.1 MB | BSD-3 |
| realesr-general-x4v3 | SRVGGNet | ~1M 级 | — | 4.7 MB | BSD-3 |
| realesr-animevideov3 | SRVGGNet | ~0.3M 级 | — | 2.4 MB | BSD-3 |
| **SPAN** | 无参注意力 | **411K** | 45 GFLOPs @720p×2 | ~1.7 MB | **Apache-2.0** |
| SPAN-F | 同上（更轻） | 更小 | — | — | Apache-2.0 |
| **SAFMN** | 空间自适应调制 | **228~240K** | 14 GFLOPs @720p×4 | ~1 MB | Apache-2.0 |
| SMFANet | 高效 CNN | 186~197K | 11 GFLOPs @720p×4 | — | 见仓库 |
| PLKSR / RealPLKSR | 大核卷积 | 中量级 | — | — | 见 spandrel |

**读法**：x4plus 一个模型 ≈ 40 个 SAFMN 的计算量。CPU 上想进"秒级"，只能靠右侧这几行。

**这些轻量模型的质量并没有崩**：SAFMN/SPAN 在 ×4 上的 PSNR 约 32.2dB（Set5），与 IMDN/ShuffleMixer 同级，差距在 0.1dB 内。也就是说 —— **放弃的是"GAN 质感增强"，不是"分辨率提升"**。这个取舍对"预览 / 批量处理 / 网页里的实时反馈"完全可接受。

> 实现提示：这两个模型都是 BasicSR 系（pth），且 **spandrel 原生支持**（含 `SAFMNBCIE`，注意它的输入尺寸必须是 **16 的倍数**）。用 spandrel 加载 = 不用自己写网络结构。

### 2.2 格式可得性矩阵（★ = 官方直接提供，需 = 需自行转换）

| 模型 | 官方 .pth | ONNX | ncnn (.param/.bin) | OpenVINO IR |
|---|---|---|---|---|
| RealESRGAN_x4plus | ★ | 需（或第三方现成） | ★（官方 ncnn 包含） | 需 |
| RealESRGAN_x4plus_anime_6B | ★ | 需 | ★ | 需 |
| realesr-animevideov3 | ★ | 需 | ★ | 需 |
| realesrnet-x4plus | ★ | 需 | ★ | 需 |
| **realesr-general-x4v3** | ★ | ★（HF/Qualcomm，4.55MB） | **✗ 官方 ncnn 包不含** | 需 |
| Real-CUGAN（动漫） | — | — | ★（nihui 独立项目） | — |
| SPAN / SAFMN | ★ | 需 | 需（pnnx） | 需 |
| GFPGAN（人脸） | ★ Apache-2.0 | — | — | — |
| CodeFormer（人脸） | ★ NTU S-Lab | — | — | — |

**ONNX 现成权重的可信来源（本轮实际核对过）**：
- `SceneWorks/real-esrgan-onnx` — x2/x4，opset 17，动态 H/W，fp32，**BSD-3**，附 sha256 与导出脚本，注明"消费端按 512px + 16px padding 分块"，且给出**与 torch 参考实现的比对结果（CPU PSNR ≈ 101dB）**。这份 model card 的严谨程度值得直接抄成我们的验收标准。
- `skillsafe-ai/realesrgan-x2plus` — 同时提供 fp32（63.97MB）与 **fp16（32.21MB）**，opset 17，给出 fp32 最大绝对误差 ~2e-6、fp16 ~7e-4 的量化验证数据，并附 **onnxruntime-web + WebGPU** 的用法。若将来要做网页端，这是模板。
- `qualcomm/Real-ESRGAN-x4plus`、`qualcomm/Real-ESRGAN-General-x4v3` — 面向移动端导出，含 ONNX。
- ModelScope `cix/ai_model_hub_25_Q3` — 有 `realesrgan-x4.onnx`。

⚠️ 但这些第三方权重都**没有 Intel/NVIDIA 官方的质量背书**，行动建议是：**先用它们跑通，再用自己导出的做正式发布**（自己导出同时能控制 opset / 静态 shape / 预处理烘入）。

### 2.3 纠正一个常见误解："ncnn 只有那 4 个模型"

`realesrgan-ncnn-vulkan` 官方 README 明确列出的模型**只有 4 个**：

```
-n model-name  (default=realesr-animevideov3, can be
                realesr-animevideov3 | realesrgan-x4plus |
                realesrgan-x4plus-anime | realesrnet-x4plus)
```

也就是说官方便携包**不含 `realesr-general-x4v3`**（因此也没有 `-dn` 去噪强度参数）。完整参数：`-i -o -s(2/3/4) -t(tile,0=auto) -m -n -g(gpu-id) -j(load:proc:save) -x(TTA) -f -v`。

**但这个限制不成立**——ncnn 官方已经推荐用 **`pnnx`** 做转换（`onnx2ncnn` 已被标记为 legacy）：

```bash
pip install pnnx
pnnx model.onnx inputshape=[1,3,512,512] fp16=1 optlevel=2
# → model.ncnn.param + model.ncnn.bin
```

RRDBNet 用到的算子（Conv / LeakyReLU / DepthToSpace(mode=CRD) / Resize）**在 pnnx 的 ONNX 算子支持表里都是 ✅**。所以"任意 spandrel 支持的架构 → ncnn"这条路是通的。

另两个必须知道的坑：
1. **官方 ncnn 仓库最后提交是 2022-04**，且 TODO 里至今挂着 **"Bug: Some PCs will output black images"** —— 已知会在部分机器输出全黑图。**把它当兜底通道，就必须给用户留"换后端"的逃生门**，不能静默失败。
2. 用外部工具（chaiNNer 等）转出来的 `.param`，**可能需要手工把第 2、3 列的 `input` 改成 `data`**，否则 ncnn 加载报错。Upscayl 文档专门记录过这个不兼容。

### 2.4 许可要点（比模型选型更容易出事的地方）

| 宽松可商用 | 需谨慎 |
|---|---|
| Real-ESRGAN 全系（BSD-3） | SUPIR（自定义，需逐条读） |
| SPAN / SAFMN（Apache-2.0） | CodeFormer / StableSR（NTU S-Lab 1.0） |
| SwinIR / HAT / OSEDiff（Apache-2.0） | Upscayl 本体（AGPL-3.0） |
| GFPGAN（Apache-2.0） | **Upscayl 内置的 Remacri / Ultramix / Ultrasharp 三个模型标注"非商用"** |
| ncnn / pnnx（BSD-3） | OpenVINO 运行时本身可用，但**它附带的 Open Model Zoo 预训练模型有各自条款** |

两个实操原则：
- **代码许可 ≠ 权重许可**，必须分别确认（Real-ESRGAN 两者都是 BSD-3，这点很省事）。
- 若商用：只从 `Upscayl Standard / Lite / High Fidelity / Digital Art` 和 Real-ESRGAN 官方模型里选，避开那三个 NC 模型。

## 3. 后端 / 运行时调研

### 3.1 五条通道的能力矩阵

| 通道 | 覆盖硬件 | 吃的模型格式 | 优势 | 限制 |
|---|---|---|---|---|
| **ORT + CUDA EP** | NVIDIA | `.onnx` | 生态最成熟、和 ONNX 直连 | 需要 `onnxruntime-gpu`（非普通版），8G 卡需 tile |
| **ORT + OpenVINO EP** | Intel CPU / iGPU / dGPU / NPU | `.onnx` | ~~一个 ORT API 就吃下整个 Intel 家族~~ | ⛔ **实测后否决，见 §9**：比 ORT 自己的 CPU EP **慢 2.5 倍**。版本配对是硬约束（见 §3.2）。**不要用。** |
| **OpenVINO 原生** | 同上 | `.xml`+`.bin` | 性能上限最高（IR 比裸 ONNX 快数倍） | 多一套代码路径 |
| **ncnn-Vulkan** | N / Intel / AMD 全吃 | `.param`+`.bin` | **零依赖、免 CUDA、免 Python**，最好的兜底 | 仅 ncnn 系模型；官方包有已知黑图 bug |
| TensorRT | NVIDIA | `.onnx` / `.trt` | 8G 卡上还能再提 1.5~2x | `.trt` 绑定 GPU 架构+驱动，必须现场构建 |

**明确排除：DirectML。** 实测（Arc A750 + yolo11n）：OpenVINO-GPU **3.8ms** / ORT-CPU 26.9ms / **DirectML 73.1ms** —— 在 Intel 平台上比纯 CPU 还慢 2~3 倍，且已进入维护模式。不要把 `DmlExecutionProvider` 放进优先级列表。

### 3.2 OpenVINO EP 的具体事实（已核对官方文档）

```bash
pip install onnxruntime-openvino   # Windows 需另外 pip install openvino
```

- **支持设备**：Intel CPU / iGPU / dGPU / NPU；Python **3.10–3.13**（覆盖本机 3.13.12）。
- **关键参数 `device_type`**：`CPU | GPU | GPU.0 | GPU.1 | NPU | AUTO | HETERO | MULTI`，还可以写 `AUTO:GPU,NPU,CPU`。
- **有 `cache_dir`**：可缓存编译产物，显著改善二次启动延迟 —— 桌面应用必开。
- **`reshape_input`**：可为动态 shape 指定上下界，这是性能关键（见 3.3）。
- **版本必须配对**：ORT 1.24.1 ↔ OpenVINO 2025.4.1；1.23.0 ↔ 2025.3；1.22.0 ↔ 2025.1。
- ⚠️ **`precision="FP16"` 自 ORT 1.23 起已废弃**，新写法是 `load_config` 里的 `INFERENCE_PRECISION_HINT = "f16"`。老教程抄过来会踩坑。
- NPU 相关参数（`enable_qdq_optimizer`、`disable_dynamic_shapes`）只对量化模型有意义 —— 但见 3.4，**超分不建议上 NPU**。

### 3.3 静态 shape vs 有界动态 shape（一个容易埋雷的设计点）

Intel 官方指南（文档 816445）给出的两条路：

- **静态 shape**：`x = torch.rand(1,3,512,512)` → 官方原话是 "much faster"，但它的示例代码是在 Python 里 `cv2.resize` 到固定尺寸 —— **这会改变长宽比**，直接把图拉变形。这是文档里没点破的坑。
- **动态 shape**：支持任意尺寸，但官方也写明 "come with a trade-off, which may increase the inference time"。
- **★ 官方真正的最优解写在第 13 页**：给动态维度**设上下界**——

```python
model.reshape([1, 3, -1, -1])                  # 全动态（差）
model.reshape([1, 3, (512, 768), (512, 768)])  # 有界动态（好）← 推荐
```

原话是这能 "give additional optimizations during the model compilation"。

**结论**：正确做法不是"选静态或动态"，而是 **用固定 tile 尺寸切块 + 给 shape 设定合理边界区间**。这样既拿到静态 shape 的编译优化，又保住长宽比、不牺牲大图能力。

### 3.4 Intel 集显：证据的边界在哪

我把 Intel 文档 816445 逐页读完了，**它没有任何性能数字**，只有流程和代码。可确证的是：

- ✅ **验证平台**：Intel Core（Tiger Lake / Alder Lake / Raptor Lake）+ **集显**，以及 Intel Arc 独显；OpenVINO 2023.2，Ubuntu 22.04，Real-ESRGAN v0.3.0。
- ✅ **设备选择代码**：`ov.Core().available_devices` → 有 GPU 就用 GPU，否则回落 CPU。这是"多硬件适配"最直接的实现参考。
- ✅ **预处理**：`cv2.imread` → **BGR→RGB** → `/255.0` → `transpose(2,0,1)` → `reshape(1,C,H,W)`。**注意 Real-ESRGAN 系吃 RGB/[0,1]，且通道顺序搞错会出现蓝橙互换**。
- ⚠️ **集显性能只能实测**。第三方数据点：某仓库称 Intel iGPU 上 512→2048 约 **0.72s**（未经独立验证，仅供参考量级）。
- ⚠️ **NPU 不适合超分**。第三方测试报告（Lenovo ThinkPad T14s Gen5，Core Ultra 7）里，同一 ESRGAN 在**相同时间内 NPU-FP16 只跑完 iGPU-FP16 一半的推理量**；即使换 INT8，NPU 也只与 GPU 持平。**结论：集显才是 Intel 平台的加速器，NPU 不是。**

### 3.5 关于"OpenVINO 快 5~13 倍"的更正

这个数字本轮查到了原始出处：来源是 HuggingFace 第三方仓库 `ibrhr/Real-ESRGAN-OpenVINO`，测试平台 **Intel Xeon Platinum 8581C（8C/16T，AVX-512 + AMX）**。

| 模型 | 512→2048 | PyTorch | OpenVINO | 加速比 |
|---|---|---|---|---|
| x4plus | | 19.919 s | 1.485 s | 13.4x |
| x4plus_anime_6B | | 6.617 s | 0.583 s | 11.3x |

**AMX/AVX-512 正是拉开这个差距的主因，消费级 CPU 没有。** 所以：
- Xeon+AMX 上：13x（可信，但与目标用户无关）
- 消费级 CPU（i5-12400F 只有 AVX2）：**✅ 已实测 = 1.64x**（见 §9），不是 2~4x
- 方向性结论**需要修正**：OpenVINO 原生仍是 Intel CPU 首选（比 ORT CPU EP 快 1.64x），但**不是数量级优势**；而"经 ORT 注册 OpenVINO EP"这条路已被实测否决。
- 另外该 IR 权重的来源与转换脚本未经审计，建议自转。

## 4. 转换流水线方案

**一份权重，四路分发**——这是整个方案的地基：

```
官方 .pth（BSD-3，可商用）
      │
      ├─(A) torch.onnx.export  ──→  .onnx          【主格式：ORT / Web / 通用】
      │        opset 17（Intel 指南用 12，社区现成用 17；RRDBNet 只涉及 Conv/
      │        LeakyReLU/DepthToSpace(CRD)/Resize，两者都行，选 17 更稳）
      │        · 导出后必须做数值比对，不能只看"能跑"
      │        │
      │        ├─(B) ovc 或 ov.convert_model  ──→  .xml + .bin   【Intel CPU/集显】
      │        │      · 建议 --compress_to_fp16（体积减半，Intel GPU 有 FP16 优化）
      │        │      · ★ 建议把预处理烘进 IR（mean/scale/reverse_channels 用
      │        │        ov.PrePostProcessor 设置），让模型直接吃 uint8 输入
      │        │        —— 第三方现成 IR 就是这么做的，对集显尤其省
      │        │
      │        ├─(C) pnnx  ──→  .ncnn.param + .bin              【零依赖兜底】
      │        │      pnnx model.onnx inputshape=[1,3,512,512] fp16=1
      │        │      · 转换后检查 .param 第 2/3 列是否需要 input→data
      │        │
      │        └─(D) trtexec  ──→  .trt（可选，N 卡专属）        【高端加速】
      │               · .trt 绑定 GPU 架构 + 驱动版本，不能跨机型分发，
      │                 必须在用户机器上现场构建并缓存
      │
      └─(E) 直接进 spandrel 加载（PyTorch 路径，用于人脸修复等复杂分支）
```

**验收标准**（借鉴社区已验证的阈值，直接可用）：

| 精度 | 最大绝对误差 | PSNR | 说明 |
|---|---|---|---|
| fp32 | < 1e-4 | > 100 dB | 误差应接近浮点噪声级 |
| fp16 | < 5e-2 | > 45 dB | 低于此值说明 fp16 有问题 |

**注意**：以上是"数值一致性"验收。它与"画质"不是一回事 —— 转换正确 ≠ 输出好看。

| | **A · 纯 CPU** | **B · Intel 集显** | **C · RTX 30/40（8G）** |
|---|---|---|---|
| 主后端 | OpenVINO CPU（或 ORT CPU EP） | **OpenVINO GPU** | **ORT CUDA EP** |
| 备选 | ncnn-Vulkan（若机器有 Vulkan） | ncnn-Vulkan | TensorRT（现场构建） |
| 模型格式 | IR（主）/ ncnn | IR（主）/ ncnn | ONNX（主） |
| 模型包 | x4plus（最终）+ **SPAN/SAFMN（快速预览）** | x4plus / anime_6B / animevideov3（IR） | x4plus / general-x4v3（ONNX fp16） |
| 精度 | FP32 / INT8（**禁 FP16**） | FP16（Intel GPU 有专门优化） | FP16（几乎白送：显存 −40%、速度 +30%、PSNR 损失 <0.2dB） |
| tile | 128 | 256 | **512** |
| shape | 有界动态 | 有界动态 | tile 固定 → 可静态 |
| 输入上限 | ≤1280px | ≤1920px | 不限（分块） |
| 降级链 | tile 128→96 → 2x → 换轻量模型 → 提示仅支持预览 | tile 256→192→128 → 切 OpenVINO CPU | 512→384→256→128 → 换小模型 → 显存不足提示 |
| 预期量级 | x4plus：数十秒~分钟；**SPAN/SAFMN：秒级** | 几秒~十几秒 / 1080p 4x（**待实测**） | 秒级 / 1080p 4x |

**三档通用的一条共享管线**（人脸场景）：
```
整图超分（分档后端） → 人脸检测 → 人脸区域交 CodeFormer/GFPGAN 精修 → 融合回背景
```
人脸修复**不要**按档位换方案，它是独立的一条共享支线。

## 6. 应用架构方案

### 6.1 核心设计：ONNX 作中间层，运行时按 EP 注册

```python
# 伪代码：一个 API，覆盖三种硬件
import onnxruntime as ort

def build_providers(profile):
    providers = []
    if profile.has_cuda:
        providers.append(("CUDAExecutionProvider", {
            "device_id": 0,
            "cudnn_conv_algo_search": "HEURISTIC",
            "arena_extend_strategy": "kSameAsRequested",   # 8G 卡更省显存
        }))
    if profile.has_intel:
        # 显式给 GPU 而非 AUTO —— AUTO 在部分机型会选到 CPU
        providers.append(("OpenVINOExecutionProvider", {
            "device_type": "GPU",        # 或 AUTO:GPU,CPU
            "cache_dir": cache_path,     # ★ 编译缓存，桌面应用必开
            "load_config": '{"GPU":{"INFERENCE_PRECISION_HINT":"f16"}}',
        }))
    providers.append(("CPUExecutionProvider", {}))
    return providers   # 注意：绝不加入 DmlExecutionProvider
```

**`IEngine` 接口建议**（三条通道共用同一套契约）：

```
IEngine
├─ probe() -> Profile                     # 探测硬件 → 决定档位
├─ load(model_pack) -> handle             # 按 Profile 选格式并加载
├─ infer(tensor, tile, precision) -> tensor
├─ benchmark_once() -> {ms, peak_mem}     # 首次运行出一组真实数字，用于校准
└─ capabilities() -> {max_input_px, supported_scales, supports_half}
```

### 6.2 能力探测（本机已有 `tools/hwprobe.py` 作为基础）

现有脚本已经解决了两个真实存在的坑，直接沿用：
1. **NVIDIA 显存必须走 `nvidia-smi`** —— WMI 的 `AdapterRAM` 是 uint32，超过 4GB 会溢出（本机就被误报成 4095MB）；
2. **必须过滤虚拟显示器适配器** —— 本机的 GameViewer Virtual Display 会被误认成 GPU。

需要补的能力：OpenVINO `available_devices`（判断集显是否存在 GPU 设备）、各 EP 的真实可用性（**只列出 provider 名字不等于能用，必须实跑一次**）。

### 6.3 降级必须是"显式"的

统一原则：**显存/内存不足 → 缩 tile → 换轻量模型 → 明确告知不支持**。任何一步都不得静默降低画质后照常返回。用户看到的每一张图，都应该能知道它是用哪个模型、哪个精度、哪档设置的产物。

## 11. P0 实测结果回填（2026-09-29 执行，完整报告见 `图像超分修复-P0实测报告.md`）

> 环境全部安装在项目内 `.venvs/`，未污染全局。
> 机器：i5-12400F / 15.8 GB RAM / RTX 3050 OEM 8 GB。模型：Real-ESRGAN x4plus（16.7 M 参数）。

### 11.1 P0-1 ✅ CUDA EP 真实性通过

判定**不能看 `session.get_providers()`**（只能证明 EP 对象被创建），必须看 ORT profile 里的节点归属：

```
CUDAExecutionProvider   1024 nodes      ← CPU 节点 0 个
```

→ 全图在 GPU 上执行。**注意这是"静默回退"唯一的可信检测手段**——ORT 在 EP 创建失败时只打一条 warning 就回退 CPU，性能差 10 倍却毫无提示。

### 11.2 P0-2 ✅ 3050 实测矩阵（CUDA EP，HEURISTIC + kSameAsRequested，runs=5）

| 精度 | tile | mean (ms) | p95 (ms) | 峰值显存 (MB) | 占可用 7.4 G |
|---|---|---|---|---|---|
| **fp16** | 256 | **441.8** | 443.0 | 1 505 | 19.8 % |
| fp16 | 320 | 670.7 | 672.9 | 2 274 | 30.0 % |
| fp16 | 384 | 948.4 | 952.0 | 3 216 | 42.4 % |
| **fp16** | **512** | **1 667.6** | 1 672.5 | 5 610 | 74.0 % |
| fp32 | 256 | 644.9 | 646.8 | 2 142 | 28.3 % |
| fp32 | 320 | 1 047.5 | 1 051.2 | 3 338 | 44.0 % |
| fp32 | 384 | 1 478.5 | 1 480.3 | 4 725 | 62.3 % |
| fp32 | 512 | 2 946.0 | 2 962.1 | 7 293 | **96.2 %** |

**1080p 整图（1080×1920 → 4320×7680）：**

| 后端 | 耗时 | 峰值 |
|---|---|---|
| GPU fp16 + tile 512 | **20.42 s** | 显存 5.5 GB |
| CPU OpenVINO 原生 fp32 + tile 512 | **272.6 s ≈ 4.5 min** | RSS 3.55 GB |

→ GPU/CPU **13.3x**。

**要点：**
- fp16 相对 fp32 **快 1.46–1.77x、省 23–32% 显存**（不是常说的"省 40%"）。
- **fp32@512 峰值占可用显存 96.2%，已进危险区**；fp16@512 为 74%，是 8 GB 卡甜点。
- 8 GB 卡上 **`fp16 + tile 384`** 是稳健全局最优（比 512 快 1.76x、省 43% 显存）。
- 可用显存是 **7.4 GB 不是 8 GB**（桌面进程常占 ~600 MB），分档时必须按 7.4 算。

### 11.3 P0-3 ✅ 后端对比（i5-12400F，tile 256 / 512，fp32）

| 后端 | tile 256 | tile 512 | 相对 ORT CPU EP |
|---|---|---|---|
| ORT CPU EP | 8 004.5 ms | 33 437.8 ms | 1.00x |
| **ORT + OpenVINO EP**（2025.4.1 已配对） | 20 358.9 ms | 85 576.1 ms | **0.39x（慢 2.5 倍）** |
| **OpenVINO 原生 fp32** | **4 893.9 ms** | **23 661.1 ms** | **1.64x** |
| OpenVINO 原生 fp16 | 5 936.0 ms | 23 426.6 ms | 1.35x |

**三条修正结论：**
1. **13x → 1.64x。** 消费级 CPU 上 OpenVINO 的真实优势是 1.64 倍，不是数量级。
2. **CPU 路径用 fp32。** fp16 在桌面 CPU 上无收益（tile 256 甚至更慢：5936 vs 4894 ms），因为没有 fp16 加速单元，反而要来回转换。
3. 🔴 **ORT 的 OpenVINO EP 在架构上被否决。** 它比 ORT 自己的 CPU EP 还慢 2.5 倍、比 OpenVINO 原生慢 4 倍。虽然它能带来"一个 ORT session 通吃 Intel/NVIDIA"的便利，但代价太大。
   → **Intel 腿必须走 OpenVINO 原生 API；NVIDIA 腿走 ORT/CUDA EP。** 两者仍可共用同一份 ONNX。

**OpenVINO EP 的 ABI 配对是硬约束（已确证）**：EP DLL 内嵌编译路径
`C:\Users\gta\Downloads\openvino_toolkit_windows_2025.4.1.20426.82bbf0292c5_x86_64`
→ `onnxruntime-openvino 1.24.1` 硬链接 **OpenVINO 2025.4.1**。装 2026.4.0 会 `WinError 127` + **静默回退 CPU（0 个 OV 节点 / 1409 个 CPU 节点）**。
⚠️ 附带纠正：`ctypes.WinDLL` 单独探测 EP DLL **不权威**（裸载报 WinError 1114，但 ORT 在宿主进程内加载正常），判定必须以 ORT session 为准。

### 11.4 🔴 新发现：`arena_extend_strategy` 默认值造成 10.3 倍劣化

同一形状（fp32 @ tile 512），只改这一个参数：

| `arena_extend_strategy` | 延迟 | 峰值显存 |
|---|---|---|
| `kNextPowerOfTwo`（**ORT 默认**） | **30 993.6 ms** | 7 391.0 MB |
| `kSameAsRequested` | **2 998.0 ms** | 7 447.5 MB |

**延迟差 10.3x，显存占用几乎相同（差 0.8%）。** 两次独立进程都落在 31–33 s，四次观测都落在 3.0–3.1 s，稳定复现。
原因是按 2 的幂向上取整的 arena 在 RRDBNet 上采样阶段（张量尺寸跳 2x/4x）产生大块碎片，96% 占用时 cuDNN 拿不到 workspace。
**注意这与 ORT 官方文档说法相反**（文档称 kSameAsRequested 更慢）。
**并且这个坑只在 fp32 + 大 tile 出现**——fp16@512 用默认策略并不慢（1.66 s）。只在 fp16 上验证会完全漏掉。

→ 代码里必须显式设置：
```python
opts = {
    "arena_extend_strategy": "kSameAsRequested",  # 默认值实测慢 10.3x
    "cudnn_conv_algo_search": "HEURISTIC",        # 默认 EXHAUSTIVE，本机影响 <3%
    "do_copy_in_default_stream": "1",
}
```
（被证伪的假设：我最初怀疑是 `cudnn_conv_algo_search=EXHAUSTIVE`，A/B 实测 EXHAUSTIVE 3115.1 ms vs HEURISTIC 3027.3 ms，**几乎无差别**。）
