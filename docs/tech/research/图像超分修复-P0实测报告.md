## 0.5 这份报告该怎么用（重要，先读）

**本机测试的目的是"验证机制是否成立 / 适配当前环境"，不是产出可以写进产品规格的性能数字。** 本机只有一张 RTX 3050 OEM + 一颗 i5-12400F，**它不能代表用户环境**——用户可能是有核显的 CPU、40 系卡、笔记本双显卡、老驱动、显存被其它程序占满、CPU 无 AVX2、Mac、乃至浏览器 WebGPU。

因此本文的数据必须分成两类看：

| 类别 | 内容 | 是否可迁移到其它硬件 |
|---|---|---|
| ✅ **机制 / 现象** | EP 会静默回退；`arena_extend_strategy` 默认值可致数量级劣化；ORT 的 OV EP 是负收益；OpenVINO GPU 插件会误枚举非 Intel 卡；WDDM 拿不到按进程显存；fp16 在无 fp16 单元的 CPU 上无收益 | **可迁移**。这些是可被独立验证的因果，换硬件仍是同一套判据，应直接写进代码防御 |
| ⚠️ **量级 / 倍数** | 「1.64x」「10.3x」「20.4 s」「5.5 GB」「快 46~77%」 | **仅本机成立**。同一命令换机器就会变。只能作为**同一台机器上的相对比较**，不能作为跨机器的绝对值承诺 |

> 具体设计见 `图像超分修复-跨环境自适应设计.md`。

## 2. P0-1：CUDA EP 真实性验证 ✅ 通过

### 2.1 为什么必须验证

`session.get_providers()` **只能证明 EP 对象被创建**，不能证明它真的执行了计算。ORT 在 EP 创建失败时只打一条 warning，然后**静默回退 CPU**——性能差 10 倍以上却毫无提示。这是本项目最危险的单点。

**唯一可信的证据是 ORT profiling JSON**：其中 `cat:"Node"` 的事件各自带 `args.provider`，按 provider 计数即可得到节点级归属。

### 2.2 实测结果

```

model input        : input [1, 3, 'h', 'w'] tensor(float)
output shape       : (1, 3, 1024, 1024)   mean=0.534278

--- node-level provider assignment (ground truth) ---
  CUDAExecutionProvider               1024 nodes
```

**CPU 节点 0 个 → 全图在 GPU 上执行。P0-1 通过。**

工具：`tools/p0_1_cuda_smoke.py`（自适应静态/动态 shape，输出 PASS/FAIL 判定）；`tools/bench_ort.py` 也内置了"请求了加速 EP 但 session 未创建"的显式告警。

## 3. P0-2：3050 上的 tile × 精度矩阵 ✅ 测得

### 3.1 方法（以及第一版为什么是错的）

**第一版做法**：一个进程跑完整个矩阵，在每个 tile 前采一次设备显存基线。
**结果无效**，两个原因：

1. ORT 的 CUDA context、cuDNN handle、device arena 是在**创建 session 时**分配的，那时基线已经采过了。于是只有每个精度的**第一行** delta 有意义（4719 MB），其余行全部 ≈ 0。
2. `nvmlDeviceGetComputeRunningProcesses()[i].usedGpuMemory` 在 **Windows WDDM 下返回 0**；`nvidia-smi --query-compute-apps=used_memory` 显示 `[N/A]`。**按进程显存根本查不到**。

**第二版做法**（`tools/p0_2_vram_matrix.py`，本报告数据来源）：
- **每个 (精度, tile) 组合单独开一个子进程** → 一个坏格子不会带走整轮结果，且基线干净；
- 基线在**任何 ORT session 存在之前**采集；
- 峰值 = 运行期间设备 `used` 的最大值（5 ms 轮询）；
- 报告 `peak_delta_mb = 峰值 − 干净基线`。

⚠️ 仍需注意：设备 `used` 是**全局值**，包含其它进程。本机桌面进程常占 **~600 MB**，实测可用显存约 **7.4 GB（不是 8 GB）**。下表百分比以 7580 MB 为分母。

### 3.2 实测矩阵（CUDA EP，HEURISTIC + kSameAsRequested，runs=5）

| 精度 | tile | mean (ms) | p50 | p95 | 峰值显存 (MB) | 权重+context 底噪 | 占可用 7.4G |
|---|---|---|---|---|---|---|---|
| **fp16** | **256** | **441.8** | 441.8 | 443.0 | **1 505** | 112 | 19.8% |
| fp16 | 320 | 670.7 | 670.5 | 672.9 | 2 274 | 112 | 30.0% |
| fp16 | 384 | 948.4 | 948.8 | 952.0 | 3 216 | 112 | 42.4% |
| **fp16** | **512** | **1 667.6** | 1 667.4 | 1 672.5 | **5 610** | 112 | **74.0%** |
| fp32 | 256 | 644.9 | 644.8 | 646.8 | 2 142 | 144 | 28.3% |
| fp32 | 320 | 1 047.5 | 1 045.7 | 1 051.2 | 3 338 | 144 | 44.0% |
| fp32 | 384 | 1 478.5 | 1 478.1 | 1 480.3 | 4 725 | 144 | 62.3% |
| fp32 | 512 | 2 946.0 | 2 943.1 | 2 962.1 | 7 293 | 144 | **96.2%** |

数据质量：p95 与 p50 差距 < 0.3%，矩阵**单调**且近似 tile² 缩放（fp32 256→512 理论 4.0x，实测 4.57x，超出部分来自 512 时的显存压力）。全部 8 格 `active_providers` 均为 CUDA，**无回退**。

### 3.3 读表要点

- **fp16 相对 fp32：快 1.46–1.77 倍，省 23–32% 显存**（不是常见的"省 40%"）。
- **fp32@512 峰值 7293 MB = 可用显存的 96.2%**，已经进入危险区；**fp16@512 为 74.0%，是 8 GB 卡的甜点**。
- tile 从 512 降到 384：**快 1.76 倍、省 43% 显存**，而目视质量损失很小 → 8 GB 卡上 `fp16 + tile 384` 是稳健全局最优。
- 底噪（权重 + context）fp32 144 MB / fp16 112 MB，差值 32 MB ≈ 半个权重文件，自洽。

### 3.4 真实场景：1080p 照片整图

输入 1080×1920（2.07 MPix）→ 输出 **4320×7680（4x，32.9 MPix）**，分块数 12（tile 512）

| 后端 / 配置 | 整图耗时 | 峰值显存 / 内存 | 有效吞吐 |
|---|---|---|---|
| **GPU · fp16 + tile 512**（实测） | **20.42 s**（p95 20.46，stdev 40 ms） | 显存 5.5 GB | 0.102 MPix/s |
| **CPU · OpenVINO 原生 fp32 + tile 512**（实测） | **272.6 s ≈ 4.5 min** | **RSS 3.55 GB** | 0.008 MPix/s |
| CPU · ORT CPU EP + tile 256（按单块外推） | ≈ 400 s ≈ 6.7 min | — | ~0.005 MPix/s |

**GPU / CPU 整图比 = 13.3x**（与单块比 23.66 / 1.6676 = 14.2x 一致）。

自洽性检验：12 块 × 1.6676 s = 20.0 s（实测 20.42 s，误差 2%）；12 块 × 23.66 s = 284 s（实测 272.6 s，误差 4%）→ 测量可信，分块拼接的额外开销可忽略。

> ⚠️ **质量隐患**：当前 `tools/_bench_common.py` 的 `tiled_infer` **没有重叠与羽化**，只是把越界的最后一个窗口挪回图内。它作为"固定 shape 处理任意分辨率"的**形状验证器**是合格的，但会留下**可见接缝**。生产版必须改为 overlap + feather 混合，代价是重叠区域约 (1 − (tile−2·pad)²/tile²) 的额外计算。
>
> ⚠️ **CPU 档的内存**：tile 512 时进程 RSS 峰值 **3.89 GB**（净增 3.55 GB）。16 GB 机器可用，但若并行处理或多图队列，需要限制并发。

## 4. 🔴 重大发现：`arena_extend_strategy` 默认值造成 10.3 倍劣化

### 4.1 现象

同一台机器、同一模型、同一形状（**fp32, tile 512**），只改 `arena_extend_strategy`：

| `arena_extend_strategy` | 延迟 | 峰值显存 |
|---|---|---|
| `kNextPowerOfTwo`（**ORT 默认**） | **30 993.6 ms** | 7 391.0 MB |
| `kSameAsRequested` | **2 998.0 ms** | 7 447.5 MB |

**差 10.3 倍，而显存占用几乎一样（差 0.8%）。**

### 4.2 可复现性

| 观测 | `kNextPowerOfTwo` | `kSameAsRequested` |
|---|---|---|
| 第 1 次 | 33 288.2 ms | 3 115.1 ms |
| 第 2 次 | 30 993.6 ms | 3 027.3 ms |
| 第 3 次 | — | 2 998.0 ms |

两个独立进程都落在 31–33 s；四次观测都落在 3.0–3.1 s。**稳定复现。**

### 4.3 解释

`kNextPowerOfTwo` 把每次 arena 扩展请求向上取整到 2 的幂。RRDBNet 的上采样阶段张量尺寸会跳变 2 倍、4 倍，恰好落在 2 的幂边界上，取整导致 arena 出现大块无法利用的碎片；碎片化到 96% 占用时，cuDNN 无法分配到所需 workspace，只能退到慢算法，同时在 WDDM 下触发主机内存分页。

**注意这与 ORT 官方文档相反**——文档称 `kSameAsRequested` "利于调试但比 kNextPowerOfTwo 慢"。在 8 GB 消费卡 + RRDBNet 这个组合下，结论完全颠倒。

### 4.4 被证伪的假设（记录过程）

我最初的假设是 **cuDNN 算法搜索 `EXHAUSTIVE`**（默认值）导致，因为它需要大 workspace。**A/B 实测否定了这个假设：**

| `cudnn_conv_algo_search`（均配 kSameAsRequested） | 延迟 |
|---|---|
| EXHAUSTIVE | 3 115.1 ms |
| HEURISTIC | 3 027.3 ms |

**几乎无差别（2.9%）。** 真凶是 arena 策略。两个设置都建议显式指定，但**只有 arena 策略是决定性的**。

> 📌 另一个反直觉点：**fp16@512 用默认 arena 策略并不慢（1.66 s）**。这个劣化是 **fp32 + 大 tile** 特有组合。所以只在 fp16 上做验证会完全漏掉这个坑。

## 5. P0-3：CPU 路径实测 —— 13x 是假的，ORT+OV EP 是死路

### 5.1 三后端同输入同模型对比（i5-12400F，tile 256 / 512，fp32）

| 后端 | tile 256 | tile 512 | 相对 ORT CPU EP |
|---|---|---|---|
| ORT CPU EP | 8 004.5 ms | 33 437.8 ms | 1.00x（基准） |
| **ORT + OpenVINO EP**（2025.4.1 已配对） | **20 358.9 ms** | **85 576.1 ms** | **0.39x（慢 2.5 倍）** |
| **OpenVINO 原生 fp32** | **4 893.9 ms** | **23 661.1 ms** | **1.64x** |
| OpenVINO 原生 fp16 | 5 936.0 ms | 23 426.6 ms | 1.35x |

### 5.2 结论

1. **"OpenVINO 在 CPU 上快 5~13 倍"不成立。** 那个数字来自第三方 HF 仓库在 **Xeon Platinum 8581C（带 AVX-512 + AMX）** 上的测试。在 i5-12400F 上真实倍数是 **1.64x**（OpenVINO 原生 fp32 vs ORT CPU EP）。
2. **fp16 在这个 CPU 上没有收益**（tile 256 甚至更慢：5936 vs 4894 ms）——桌面 CPU 无 fp16 加速单元，反而要来回转换。**CPU 路径用 fp32。**
3. 🔴 **ORT 的 OpenVINO EP 是性能死路。** 它比 ORT 自己的 CPU EP 还慢 2.5 倍。理论上它能带来"一个 ORT session 通吃 Intel/NVIDIA"的架构便利，但代价太大 → **Intel 路径走 OpenVINO 原生 API，不要在 ORT 里注册 OpenVINO EP。**

### 5.3 OpenVINO EP 的 ABI 配对是硬约束

**证据**：`onnxruntime_providers_openvino.dll` 里内嵌了编译时的绝对路径：
```
C:\Users\gta\Downloads\openvino_toolkit_windows_2025.4.1.20426.82bbf0292c5_x86_64\...
```
→ `onnxruntime-openvino 1.24.1` 硬链接 **OpenVINO 2025.4.1**。

| 安装的 openvino | 结果 |
|---|---|
| 2026.4.0 | `ctypes.WinDLL` 报 **WinError 127**（依赖缺导出符号）；ORT 报 `Failed to create OpenVINOExecutionProvider`；**静默回退 CPU，profile 显示 0 个 OV 节点、1409 个 CPU 节点** |
| 2025.4.1 | session providers 含 `OpenVINOExecutionProvider`；profile = `{'OpenVINOExecutionProvider': 1}`，**CPU 节点 0 个** |

（那个 `1` 是 ORT 把整个图融合成一个 OpenVINO 子图，不是"只有 1 个算子跑在 OV 上"——因为 CPU 节点为 0。）

⚠️ **方法论纠正**：`ctypes.WinDLL` 单独加载 EP DLL **不权威**。裸载会报 `WinError 1114`（DllMain 失败），但 ORT 在宿主进程内加载完全正常。**判定必须以 ORT session 为准**，这也是 `tools/diag_ovep.py` 第 2 步会提示的。

## 6. 对应用架构的直接影响

### 6.1 修正后的后端优先级

| 硬件 | 后端 | 依据 |
|---|---|---|
| NVIDIA（8 GB 级） | **ORT + CUDA EP**，`fp16` + `tile 384~512` | P0-1/P0-2 实测 |
| Intel CPU | **OpenVINO 原生 API**，`fp32` | P0-3：比 ORT CPU EP 快 1.64x；经 ORT 反而慢 2.5x |
| Intel 集显 | OpenVINO 原生，device=`GPU` | 第三方数据；**本机 F 后缀无核显，未验证** |
| 通用兜底 | ORT CPU EP | 无依赖、随处可跑 |
| ~~ORT + OpenVINO EP~~ | **不要用** | P0-3：慢 2.5x |
| ~~DirectML~~ | **不要用** | 前轮实测：Intel 上比 CPU 还慢 2~3 倍 |

→ **"两条腿"结构成立但需要修正**：NVIDIA 腿 = ORT/CUDA；Intel 腿 = **OpenVINO 原生**（不是 ORT 注册 EP）。两条腿对模型的需求可以统一在同一个 ONNX 文件上。

### 6.2 必须写进代码的默认值

只有**机制性**的项可以硬编码（它们是因果，不随硬件变）。**数量性的项一律走自标定，不写死。**

```python
# ✅ 可硬编码：这些是机制，不是数值
opts = {
    "arena_extend_strategy": "kSameAsRequested",  # 默认 kNextPowerOfTwo 在 fp32+大 tile 下实测慢 10.3x
    "cudnn_conv_algo_search": "HEURISTIC",        # 默认 EXHAUSTIVE，本机影响 <3% 但更省 workspace
    "do_copy_in_default_stream": "1",
}
# ✅ 可硬编码：防御性判定
assert_provider_actually_used(sess, expect="CUDA")   # 不信 get_providers()，读 profile
assert_no_intel_gpu_misidentified(ov_devices)        # 看 FULL_DEVICE_NAME，不信设备列表里有 "GPU"

# ❌ 不可硬编码：必须由探测/标定得出
# tile = 384        ← 随可用显存、模型、驱动浮动
# half = True       ← 随 GPU 是否原生支持 fp16 浮动（Intel 集显上另说）
# 可用显存 = 7.4G   ← 随桌面进程占用浮动，本机今天 7.4G 明天可能 6.8G
```

### 6.3 Profile 分档（**本机标定样例**，产品必须现场重算）

下表是**本机的标定结果**，用来示范"标定应该产出什么形状的结论"，而**不是**可以装进产品的映射表——用户机器上的 `peak` 列会完全不同。

| 可用显存（本机实测） | 本机推荐 | 本机预期（512² 块） | 产品该怎么定 |
|---|---|---|---|
| ≥ 8 GB 独占 | `fp16` + `tile 512` | 1.67 s | 探测到独占显存后，从 **保守值起步**向上试探，命中"峰值 < 80% 可用"即停 |
| ~7.4 GB（本机实况） | `fp16` + `tile 384` | 0.95 s | 同上 |
| 4 GB | `fp16` + `tile 256` | 0.44 s | 同上 |
| 纯 CPU（i5-12400F） | OpenVINO 原生 `fp32` + `tile 256` | 4.89 s | 按**物理内存**而非显存定档（tile 512 时 RSS 3.55 GB） |

## 7. 未验证 / 剩余风险

> **定位调整（2026-09-30）**：Intel 集显**本轮不测**。原因不是它不重要，而是**本机不可能测出通用结论**——用一台机器的核显数值去代表全部核显（UHD 630 / Iris Xe 96EU / Arc iGPU / AMD 核显 / Apple 统一内存）本身就是错误的取样方式。正确做法是**把集显当作"未知硬件"处理**，靠运行时探测 + 自标定兜住，见 `图像超分修复-跨环境自适应设计.md`。
>
> 因此下表不再有"硬阻塞项"，只有"待真机自证项"。

| 项 | 状态 | 说明 |
|---|---|---|
| Intel 集显（iGPU）OpenVINO 加速 | ⏸️ **本轮不测（非阻塞）** | 本机 i5-12400**F** 屏蔽核显。已具备探测代码路径（`hwprobe.py` 读 `FULL_DEVICE_NAME` 区分 Intel/非 Intel），**产品上线后在真实核显机器上自标定即可**，不需要开发机先行验证 |
| 集显的**共享显存**语义 | ⚠️ 未验证，但已知风险点 | 核显无独立显存，用的是内存切片，`可用显存` 这个概念本身不成立 → 集显档必须按**物理内存**分档，并预留系统占用，见自适应设计文档 |
| OpenVINO GPU 插件对**非 Intel** GPU | ⚠️ 已发现是**陷阱**（可迁移） | 它会把 NVIDIA RTX 3050 枚举为 `NVIDIA GeForce RTX 3050 OEM (dGPU)` 并接受调用，但实测 **7193.5 ms @ tile256，比 CPU 的 4893.9 ms 还慢**，且 tile 1024 直接报 `Exceeded max size of memory object allocation`。**判定 Intel GPU 必须看 `FULL_DEVICE_NAME`。** 这条是机制，换机器同样成立 |
| TensorRT（含 fp16/INT8） | ❌ 未测 | 本机无 TensorRT 运行时；且 `.trt` 引擎绑定架构与驱动，**本就不能预构建**，只能现场建 |
| 4060 Ti / 专业卡 | ❌ 未测（且**不应**在开发机测） | 无硬件，也不该用推测数据填充。交给运行时自标定 |
| 老驱动 / 笔记本双显卡 / 显存被占满 | ❌ 未测 | 真实用户的高频环境，**本机单卡环境测不出来**。自适应设计里用"启动自检 + 失败降级"覆盖 |
| ~~轻量模型（SPAN/SAFMN）在 CPU 上的真实速度~~ | ✅ **已实测**（`T-801`，2026-10-09） | 预测"比 x4plus 快 40~70 倍"**被实测确认**：`SAFMN ×4`（239,520 参数）1080p 全图 **5.13 s**、单块 256² **129 ms**、峰值内存 **687 MB**；`SPAN ×2`（410,700 参数）**6.43 s / 116 ms / 407 MB**；对照 `RealESRGAN_x4plus` 4 894 ms（单块）、272.6 s（1080p）、3 894 MB → **38~53×**。**结论：CPU 档可用**，且**不需要 `min_ram_mb`**。见 `图像超分修复-T801-轻量模型CPU速度结论.md` |
| 分块接缝 / overlap 羽化 | ⚠️ 未实现 | 当前 `tiled_infer` 无重叠，会有可见接缝。**这是产品质量缺陷，与硬件无关，必须修** |
| fp16 数值精度验收 | ❌ 未测 | 已定义阈值（fp32 max_abs<1e-4 且 PSNR>100dB；fp16 max_abs<5e-2 且 PSNR>45dB）但没有实测对照。**注意：阈值是机制可迁移的，具体误差值不是** |
| 按进程显存 | ⚠️ **平台限制**（可迁移） | Windows WDDM 拿不到，只能报设备级 delta。若做多进程/服务端形态，需要换 Linux 或改用 `torch.cuda.memory_allocated` 类手段 |
| CPU 档内存开销 | ⚠️ 已实测但未分档 | OpenVINO 原生 tile 256 = **RSS 净增 825 MB**，tile 512 = **3.55 GB**。**CPU 档的瓶颈是物理内存而非显存**，分档规则必须与 GPU 档分开 |

**结论**：剩余未验证项里，只有两项**必须**在开发阶段解决——「轻量模型 CPU 速度」（影响架构选型）和「分块羽化」（质量缺陷）。其余全部应当**下沉为运行时的探测/标定/降级逻辑**，而不是继续在单机上补测。
