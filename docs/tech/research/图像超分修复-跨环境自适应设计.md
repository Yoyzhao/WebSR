# 图像超分修复应用 · 跨环境自适应设计

> 目标：**一套代码跑到任何机器上都不崩、不慢得离谱、不糊弄用户**。
> 前提认知：本机（i5-12400F 无核显 + RTX 3050 OEM 8G）**不代表用户环境**，其实测数值只用于验证机制，不作为产品参数。
> 时间：2026-09-30

---

## 一、问题陈述：为什么"本机测好"不等于"通用"

前一阶段（`图像超分修复-P0实测报告.md`）在单机上得到了一整套数字。直接用它们做产品参数会踩三类坑：

| 坑 | 具体表现 | 后果 |
|---|---|---|
| **取样偏差** | 用户环境是长尾：核显笔记本、双显卡、老驱动、40 系、Mac、浏览器 WebGPU、显存被别的程序占满 | 开发机能跑，用户机器 OOM 或慢 10 倍 |
| **数值漂移** | 同一台机器，桌面进程占用变化 → 可用显存从 8 GB 标称掉到 7.4 GB 甚至 6.8 GB；驱动升级 → 性能跳变 | 硬编码的 tile 甜点失效 |
| **判据错位** | 代码里写 `if "GPU" in ov_devices` 就认为能用集显——实际 OpenVINO 会把 NVIDIA 卡也枚举成 GPU 设备 | 静默选错后端，性能反而更差 |

**结论**：产品的正确形态不是"带着一张参数表"，而是**带着一套测量与决策程序**。

---

## 二、核心原则

1. **机制硬编码，数值运行时求**。
   可以写死的只有因果性防御（EP 真实性校验、arena 策略覆盖、集显判定看全名、OOM 降档链）；所有数量（tile、精度、线程数、并发度）必须现场测。
2. **宁可保守起步，不要假设标称规格**。
   显存不读标称值，读 `nvml` 实读可用值；CPU 不假设有 AVX-512，读 CPUID；不假设核显可用，读设备全名。
3. **兼容必须显式可观测**。
   每一档决策都要能回答："这台机器为什么用了这个 tile / 这个精度 / 这个 EP"。把决策理由写进日志与 UI，否则线上问题无从排查。
4. **降级要出声，升级要缓慢**。
   降档立刻生效并提示用户；升档只在连续多次稳定后才尝试，避免在阈值附近来回抖动。
5. **标定是异步的、可缓存的、可中断的**。
   首启标定不能让用户盯着白屏等 1 分钟。应当：先用安全默认值把第一张图跑出来，标定在后台完成，下次启动生效。
6. **未知硬件走保守默认，而不是报错**。
   任何探测失败都必须落到一个"一定能跑"的兜底配置上。

## 三、整体架构：探测 → 标定 → 决策 → 反馈

```
┌─ 阶段 A：能力探测 Capability Probe（毫秒级，不加载模型）─────────────┐
│  读硬件事实：CPU 指令集/核数/内存、GPU 型号/架构/驱动/可用显存、       │
│  OpenVINO 设备、浏览器 WebGPU adapter、操作系统与电源状态            │
│  产出：DeviceFacts（纯事实，不含决策）                              │
└──────────────────────────────┬─────────────────────────────────────┘
                               ↓
┌─ 阶段 B：EP 可用性实测（秒级，加载最小模型）────────────────────────┐
│  对候选 EP 逐个「真建 session + 真跑一次 + profile 验节点归属」      │
│  ⚠️ 绝不信任 get_available_providers()：它只说明"编译进去了"        │
│  产出：VerifiedBackend[]（真正可用的后端列表 + 实测相对速度）        │
└──────────────────────────────┬─────────────────────────────────────┘
                               ↓
┌─ 阶段 C：首启自标定 Auto-Calibration（秒~分钟级，后台异步）─────────┐
│  在候选 tile 上采样，测延迟与峰值内存；对照 fp16/fp32 数值误差        │
│  产出：CalibrationRecord → 缓存到本地                                │
└──────────────────────────────┬─────────────────────────────────────┘
                               ↓
┌─ 阶段 D：决策 Profile Resolution ──────────────────────────────────┐
│  合并 DeviceFacts + VerifiedBackend + CalibrationRecord + 用户偏好   │
│  产出：RuntimeProfile（tile / precision / EP / threads / 并发度）    │
└──────────────────────────────┬─────────────────────────────────────┘
                               ↓
┌─ 阶段 E：运行时反馈 Runtime Feedback（每次任务）───────────────────┐
│  水位监控 + OOM 降档 + 稳定后缓升 + 全程显式提示                     │
└────────────────────────────────────────────────────────────────────┘
```

**关键设计**：A→D 向前依赖，但**每一层都有独立的安全默认值**。任何一层失败，用该层的默认值继续，绝不阻断流程。

## 四、阶段 A：能力探测（Capability Probe）

### 4.1 探测项清单

| 类别 | 探测项 | 获取方式 | 为什么需要 |
|---|---|---|---|
| **CPU** | 架构 / 指令集（SSE4.2, AVX2, AVX-512, AMX, VNNI） | CPUID（Python 用 `cpuinfo` / `py-cpuinfo`） | 决定 OpenVINO 是否值得上、是否可能吃到 AMX 的 13x 级收益 |
| | 物理/逻辑核数 | `os.cpu_count()` + `psutil.cpu_count(logical=False)` | 设 `intra_op_num_threads`；**超线程核不能当两个用** |
| | 是否大小核（P/E core） | 厂商型号映射表 | 大核上跑推理，避免线程被调度到 E core |
| | 物理内存总量与当前可用 | `psutil.virtual_memory()` | **CPU 档的瓶颈是内存不是显存**（本机 tile 512 时 RSS 3.55 GB） |
| **NVIDIA GPU** | 型号 / 计算能力 sm_XX | `pynvml` + `torch.cuda.get_device_capability()` 或 CUDA 驱动 API | 决定可用 TensorRT 精度、kernel 兼容性 |
| | 驱动版本 / CUDA 运行时版本 | `nvidia-smi --query-gpu=driver_version` | 决定 ORT/TRT 版本上限 |
| | **显存总量 + 当前可用** | `pynvml.nvmlDeviceGetMemoryInfo()` | 唯一可信的显存依据；**不要用标称值** |
| | 是否笔记本版（Max-Q）/ 是否被 MUX 切换 | 设备名启发式 + `nvidia-smi -q` | 性能与功耗策略不同 |
| | 是否独显（区别于核显） | 设备名 + 是否存在 `Optimus` 迹象 | 双显卡机器要选对 |
| **Intel GPU** | 设备**全名** | OpenVINO `FULL_DEVICE_NAME` | **必须看全名**：OpenVINO 会把 NVIDIA 卡也枚举成 `(dGPU)` |
| | 是核显还是 Arc 独显 | 全名匹配（`Intel(R) UHD/Iris Xe/Arc`） | 核显走共享内存，显存语义不同 |
| | 共享内存大小 | 系统内存 + BIOS 预留（通常拿不到准确值） | 核显档要按内存分档并预留系统占用 |
| **OpenVINO** | `available_devices` | `core.available_devices` | 候选设备列表 |
| | 各设备的 `FULL_DEVICE_NAME` / `DEVICE_TYPE` | `core.get_property()` | 区分 CPU/GPU/NPU 与真假 Intel GPU |
| **ORT** | `get_available_providers()` | API | **仅作候选，不作结论** |
| **OS / 环境** | Windows/macOS/Linux、WDDM 与否 | `platform` | WDDM 下拿不到按进程显存 |
| | 是否在虚拟机 / 容器 | 启发式 | 会影响可用设备 |
| | 电源模式（笔记本） | `psutil.sensors_battery()` | 电池模式下不建议跑重任务 |
| **浏览器** | WebGPU adapter 是否存在 | `navigator.gpu.requestAdapter()` | 决定纯前端形态能否加速 |

### 4.2 探测代码骨架

现有的 `tools/hwprobe.py` 已经是雏形（含 `--json`），产品化时按下述结构收敛：

```python
@dataclass
class DeviceFacts:
    os_name: str
    is_wddm: bool                     # Windows 下 True → 放弃按进程显存
    cpu: CpuFacts                     # arch, isa set, cores, ram_total/avail
    nvidia: list[NvidiaGpuFacts]      # name, cc, driver, vram_total/free
    intel_gpu: list[IntelGpuFacts]    # full_name, is_integrated
    ov_devices: dict                  # {"CPU": {...}, "GPU": {...}, "NPU": {...}}
    ort_available: list[str]          # 仅候选
    webgpu: bool | None
    probes_failed: list[str]          # 哪些探测失败了（必须记录！）

def probe() -> DeviceFacts:
    """纯读事实，不做任何决策，不抛异常。任何单项失败都记入 probes_failed 并继续。"""
```

**硬性要求**：

- **绝不抛异常**。某项探测失败（如 `pynvml` 初始化失败、驱动太老）必须降级为"未知"并记录，而不是让整个启动流程崩掉。
- **绝不读取标称规格当可用值**。CUDA 的 `totalGlobalMem` 也不等于可用——很多卡预留显存。
- **区分"核显"与"独显"**：`intel_gpu.is_integrated` 必须显式判定，因为它决定走显存分档还是内存分档。
- **记录每个探测项的耗时**：探测本身不能成为启动瓶颈。

## 五、阶段 B：EP 可用性实测（这一步最容易漏）

### 5.1 为什么必须实测

前一阶段最贵的教训：**`session.get_providers()` 列出了一个 EP，不代表它执行了计算**。

- ORT 在 EP 创建失败时**只打一条 warning，然后静默回退 CPU**，性能差 10 倍以上却毫无提示；
- OpenVINO EP 会因 ABI 不匹配（EP DLL 内嵌编译版本 ≠ 安装版本）在 `WinDLL` 时报 `WinError 127`，但 ORT 内部可能报另一套错误后静默回退；
- `openvino` 的 GPU 插件会**接受**非 Intel GPU 的调用，只是慢（本机比 CPU 还慢）。

### 5.2 验证协议

```python
def verify_backend(ep_name: str, probe_model_path: str) -> BackendVerdict:
    """对单个 EP 做真实性验证。返回 verdict 而不是 bool。"""
    # 1) 尝试真建 session
    try:
        sess = ort.InferenceSession(probe_model_path, so, providers=[ep_name, "CPUExecutionProvider"])
    except Exception as e:
        return BackendVerdict(usable=False, reason=f"session_create_failed: {e}")

    # 2) session 里真的有它吗
    if ep_name not in sess.get_providers():
        return BackendVerdict(usable=False, reason="ep_not_in_session_providers")

    # 3) 🔴 关键：开 profiling 跑一次，数节点归属
    profile = run_once_with_profiling(sess)
    assign = count_nodes_by_provider(profile)     # {"CUDAExecutionProvider": 1024, ...}
    if assign.get(ep_name, 0) == 0:
        return BackendVerdict(
            usable=False,
            reason=f"silent_fallback: 0 nodes on {ep_name}, actually {assign}",
        )

    # 4) 通过 → 顺便测一次相对速度，用于后端排序
    return BackendVerdict(
        usable=True,
        reason=f"{assign[ep_name]} nodes",
        node_assignment=assign,
        latency_ms=bench_once(sess),
    )
```

**判定规则表**

| 观测 | 判定 | 处理 |
|---|---|---|
| session 创建抛异常 | 不可用 | 记录异常，跳过该 EP |
| `ep not in sess.get_providers()` | 不可用 | 记录"EP 对象未创建"，跳过 |
| profile 中该 EP 节点数 = 0 | **静默回退** | **必须记录为异常事件**，因为这通常意味着 DLL/版本问题，不是正常情况 |
| 节点数 > 0 且无 CPU 节点 | 完全可用 | 采用 |
| 节点数 > 0 但有 CPU 节点 | 部分可用 | 记录 CPU 节点占比；若 > 30% 视为不划算，跳过 |
| 可用但比 CPU EP 慢 | 可用但不划算 | 从候选链中剔除，记录原因 |
| profile 中该 EP 只有 1 个节点 | **正常**（可能整图融合成一个子图） | 用"CPU 节点是否为 0"交叉验证，避免误判 |

> ⚠️ **最后一条是踩过的坑**：OpenVINO EP 把整个 RRDBNet 融合成单个子图，profile 显示 `{'OpenVINOExecutionProvider': 1}`。若按"节点数少 = 没接管"理解会误判。**判据必须是"CPU 节点数"**。

**候选链与淘汰记录**

```
候选 EP 链（按硬件形态展开，取第一个通过验证且速度达标的）：
  NVIDIA  → [CUDA, TensorRT]            验证后用实测最优
  Intel   → [OpenVINO 原生, OpenVINO EP] ⚠️ 实测 OV EP 是负收益，默认走原生 API
  AMD     → [DirectML, CPU]             ⚠️ 前轮实测 DirectML 在 Intel 上比 CPU 还慢 2~3 倍
  Apple   → [CoreML/MPS]
  兜底    → [CPU]
```

## 六、阶段 C：首启自标定（Auto-Calibration）

### 6.1 标定目标

只标定**真正影响体验且无法从事实推导**的量：

| 待标定量 | 为什么不能推导 | 标定方法 |
|---|---|---|
| **tile 尺寸** | 同一型号显卡，可用显存随占用浮动；不同模型激活大小差异大 | 在候选集合上采样，取"峰值 < 80% 可用"的最大值 |
| **精度（fp16/fp32）** | 取决于 GPU 是否原生支持 fp16（CPU 上 fp16 反而更慢） | 先按硬件能力筛，再用小样例做数值对照 |
| **实际 EP** | 见阶段 B | 实测 + profile 验证 |
| **线程数（CPU）** | P/E 核混用、超线程、内存带宽 | 在小样例上扫 {物理核数, 逻辑核数, 物理核数×0.75} |
| **并发度** | 取决于内存/显存余量 | 由"峰值 < 80%"反推 |

### 6.2 标定算法（tile）

```python
def calibrate_tile(backend, model, resol_range, cand_tiles=[256, 320, 384, 512, 640, 768],
                   budget_ms=8000, safety=0.80):
    """返回 (best_tile, curve)，curve 记录每档实测值 —— 曲线本身要存下来，
    因为下次可用显存变了要能在曲线上插值，不必重测。"""
    curve = []
    best = None
    t0 = time.time()

    for tile in cand_tiles:                      # 从小到大，尽早命中即止
        if time.time() - t0 > budget_ms:
            curve.append({"tile": tile, "skipped": "budget_exhausted"})
            break
        free_before = read_free_mem(backend)     # 每档都重读，因为它会变
        try:
            lat, peak = run_timed(model, tile, runs=3, warmup=1)
        except OutOfMemory as e:                 # 显式区分 OOM 与其它异常
            curve.append({"tile": tile, "oom": str(e)})
            break                                # 再大必然也 OOM，停止
        except Exception as e:
            curve.append({"tile": tile, "error": str(e)})
            continue                             # 其它异常：跳过这一档，继续

        used_ratio = peak / free_before
        curve.append({"tile": tile, "latency_ms": lat, "peak_mb": peak,
                      "used_ratio": round(used_ratio, 3)})
        if used_ratio < safety:
            best = tile                          # 记录最大安全档
        else:
            break                                # 超过安全线，不再往上试

    return best or MIN_SAFE_TILE, curve
```

**关键设计点**

1. **从安全侧起步、向上试探**，而不是从大到小试到 OOM。前者失败代价低、不留碎片状态；后者每次 OOM 都可能让 CUDA context 处于异常状态。
2. **每档重读可用内存**。不能开头读一次就用到底——本机教训就是这个。
3. **显式区分 OOM 与其它异常**。OOM 是"到顶了"，其它异常是"这档有问题"，处理方式不同。
4. **保存完整曲线而不是单一结论**。可用显存变了可以插值，不必重测；也能用于诊断。
5. **有预算上限**（本机设 8 秒）。超预算就停在当前最优档。首次使用体验优先。

### 6.3 标定算法（精度）

```python
def calibrate_precision(backend, model_fp32, model_fp16, sample_img,
                        fp32_thresh=(1e-4, 100.0), fp16_thresh=(5e-2, 45.0)):
    """max_abs 相对 fp32 参考；PSNR 阈值。达标才启用 fp16。"""
    if not backend.supports_native_fp16:      # CPU / 老 GPU 直接跳过
        return "fp32", "backend_has_no_native_fp16"
    ref = run(model_fp32, sample_img)
    got = run(model_fp16, sample_img)
    max_abs, psnr = compare(ref, got)
    ok = max_abs < fp16_thresh[0] and psnr > fp16_thresh[1]
    return ("fp16" if ok else "fp32"), f"max_abs={max_abs:.2e} psnr={psnr:.1f}dB"
```

> 阈值是机制（可迁移），**具体误差值不是**——每次标定都要重算，因为换驱动、换 ORT 版本都可能改变 fp16 的实际行为。

**失效条件（任一命中即重标定）**：`fingerprint` 中任一字段变化、模型文件哈希变化、距上次标定超过 N 天、用户手动触发、运行期连续降档 ≥ 2 次。

**存储位置**：应用数据目录，按 fingerprint 分片，允许多份（换显卡后回旧配置仍可用）。

### 6.5 标定的用户可见性

- 首启：**先用安全默认值把第一张图跑出来**（tile 取曲线最小值偏上、精度取 fp32），标定在后台跑；
- 标定完成：静默切换，不做弹窗打扰；在"设置 → 性能"里显示标定结果与理由；
- 提供"重新标定"按钮，并说明用途（换了显卡/驱动、感觉变慢时用）。

## 七、阶段 E：运行时反馈与降级

### 7.1 水位监控

每次任务前后读一次可用显存/内存。**注意两个已知限制**：

- Windows WDDM 下 `nvmlDeviceGetComputeRunningProcesses().usedGpuMemory` 返回 0，`nvidia-smi --query-compute-apps=used_memory` 是 `[N/A]` → **只能读设备级 `used`**，它包含其它进程；
- 因此**按进程显存监控在 Windows 上做不到**。替代方案：读设备级 `used` 的**增量**（任务前后差值），并把"设备被其它进程占用"作为一等公民显示给用户。

```python
class WatermarkMonitor:
    def before_task(self): self.free_before = read_free(); self.used_before = read_used()
    def after_task(self):
        delta = read_used() - self.used_before
        if delta / self.free_before > 0.85:
            self.consecutive_high += 1
        else:
            self.consecutive_high = 0
        return delta
```

### 7.2 降档与升档

```
降档（立即生效，必须提示用户）
  连续 2 次 used_ratio > 0.85  →  降一档 tile
  出现 OOM                    →  降一档 tile 并立刻重试一次
  重试仍 OOM                  →  换小模型（general-x4v3）
  仍失败                      →  明示"当前硬件/显存状态不支持该档位"，给出建议

升档（缓慢，仅在上次降档后稳定运行 N 次任务后尝试）
  连续 10 次 used_ratio < 0.60 且无 OOM  →  试探性升一档
  试探失败或再次触发降档              →  回退并**拉长**下次升档的等待次数（指数退避）
```

**为什么升档要慢**：避免在阈值附近抖动。用户感知到"一会儿快一会儿慢"比"一直略慢"更糟。

### 7.3 不可静默

必须让用户能回答"现在用的是哪个档位、为什么"：

- 状态栏/设置页显示：后端 EP、精度、tile、可用显存、已用比例、是否处于降档后状态；
- 降档时给出**一次性**提示（不要每次任务都弹）："检测到显存紧张，已自动降到 tile 256 以保证稳定性。";
- 日志记录每次决策的输入与理由，便于线上排查。

## 八、未知硬件的安全默认矩阵

**任何探测/标定失败都必须落到这里。** 目标不是最优，而是"一定能跑出正确结果"。

| 环境 | 安全默认 | 理由 |
|---|---|---|
| 探测完全失败 | ORT CPU EP + fp32 + tile 128 + 并发 1 | 无依赖、随处可跑、最省内存 |
| 有 NVIDIA 卡但 EP 验证未通过 | 同上（不冒险用 CUDA） | 静默回退的代价是"看似加速实则更慢" |
| 有 Intel 集显但未标定 | OpenVINO 原生 CPU + fp32 + tile 按内存定 | 集显共享内存语义不明，先不用 |
| 显存被占满（可用 < 2 GB） | tile 128 或 256 + fp16（若支持），并**提示用户显存被占用** | 让用户知道是别的原因，而不是软件差 |
| 物理内存 < 8 GB 的纯 CPU | tile 128 + 并发 1 + 输入边长上限（如 1280） | 本机实测 CPU tile 512 需 RSS 3.55 GB |
| 浏览器无 WebGPU | WASM 回退 + 明示"慢 10~100 倍" + 限制输入尺寸 | 不要让用户以为程序卡死 |
| 笔记本电池模式 | 提示可能降速，或建议插电 | 功耗策略会导致性能剧烈波动 |
| 老驱动导致 EP 不可用 | 落到 CPU EP，并提示"建议升级显卡驱动以启用加速" | 给出可执行的行动建议 |

## 九、探测/标定必须产出的数据结构

产品内部至少要有三个明确的对象，避免"到处读全局变量"：

```python
DeviceFacts          # 阶段 A：纯事实，无决策，可序列化用于 bug 报告
VerifiedBackend      # 阶段 B：真实验证过的后端 + 节点归属 + 相对速度
CalibrationRecord    # 阶段 C：tile 曲线 + 精度判定 + 指纹 + 理由
RuntimeProfile       # 阶段 D：最终决策（tile/precision/ep/threads/concurrency）
RuntimeFeedbackState # 阶段 E：水位、连续高位计数、降档状态、退避计数
```

**落盘要求**：`DeviceFacts` + `VerifiedBackend` + `CalibrationRecord` 三者**必须能一键导出**成单个 JSON。用户报障时，这一个文件就能解释"为什么他慢/崩"——这比任何远程诊断都有效。

## 十、把"本机实测"放回它该在的位置

| 本机实测的产物 | 正确用途 | 错误用途 |
|---|---|---|
| EP 真实性验证方法（profile 数节点） | **吸收为阶段 B 的标准流程** | 只在开发机跑一次就丢 |
| `arena_extend_strategy` 默认值陷阱 | **硬编码为防御性设置** | 当作"某个性能数字"来记忆 |
| 显存矩阵（tile × 精度） | 作为自标定**曲线的合理区间参照**，用于校验标定结果是否离谱 | 作为产品参数表直接查表 |
| 1080p 整图耗时（20.4 s / 272.6 s） | 用于**判断自标定结果是否超出合理量级**（如果标定出 2 s 或 2000 s，说明有问题） | 写进产品宣传或作为 SLA |
| OpenVINO GPU 插件误枚举 NVIDIA 卡 | **硬编码判定规则**（看 `FULL_DEVICE_NAME`） | — |
| fp16 在 CPU 上无收益 | **硬编码规则**（CPU 路径禁 fp16） | — |
| 分块无羽化有接缝 | **必须修复的产品缺陷** | — |

**一句话**：本机测试的正当产出是**方法与防御规则**；任何**数量**都要在用户机器上重新求。

## 十一、反面清单

- ❌ **不要用开发机的数值做产品参数表**。包括 tile 甜点、显存余量、耗时预期。
- ❌ **不要相信 `get_available_providers()`**。它只说"编译进去了"。
- ❌ **不要用 `session.get_providers()` 当作 EP 生效的证明**。必须看 profile 节点归属。
- ❌ **不要用节点数少来判断 EP 没接管**。整图融合成一个子图是正常的，看 CPU 节点数。
- ❌ **不要用 `"GPU" in ov_devices` 判断 Intel 集显可用**。看 `FULL_DEVICE_NAME`。
- ❌ **不要读标称显存当可用显存**。本机标称 8 GB，实测可用 7.4 GB。
- ❌ **不要用 try/except OOM 作为主要降档手段**。要按水位主动降，OOM 只是最后一道防线。
- ❌ **不要静默降级**。用户必须知道自己现在是什么档位。
- ❌ **不要让首启标定阻塞第一张图**。先跑安全默认，标定放后台。
- ❌ **不要把 CPU 档和 GPU 档用同一套分档规则**。CPU 档瓶颈是内存不是显存。
- ❌ **不要假设有核显就一定能用**。核显共享内存，且 OpenVINO 会误枚举。
- ❌ **不要为了"通用"而放弃最优**。自标定的目的恰恰是让每台机器都拿到**属于它自己**的最优参数。

---

## 十二、落地顺序建议

1. **先做阶段 A + 阶段 B**（探测 + EP 验证）。这两步无成本、无风险，且能立刻暴露"用户机器上其实没用上 GPU"这类严重问题。
2. **再做阶段 E**（水位监控 + 显式降级）。它能在标定尚未成熟时先兜住稳定性。
3. **最后做阶段 C**（自标定）。它依赖前两者提供的事实与验证结果，且需要最多的调参打磨。
4. **阶段 D 是黏合剂**，随前三步逐步丰富即可，不必一次设计完整。

**在阶段 C 完成前**，用 §八 的安全默认矩阵 + 用户可手动选择档位过渡。
