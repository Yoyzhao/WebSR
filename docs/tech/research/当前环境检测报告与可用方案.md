## 二、⚠️ 一个必须纠正的前提：本机测不了 Intel 集显

你说"重点场景是 CPU + Intel 集显"，但**本机 CPU 是 i5-12400F，F 后缀表示核显被物理屏蔽**，主板视频输出都不可用。所以：

- **本机无法用于验证 Intel 集显路径**，需要另找一台带核显的机器（i5-12400 / i5-12500 / 或任意 Iris Xe、UHD Graphics 笔记本）；
- 但**管线代码可以先在本机用 OpenVINO 的 CPU 设备验证**——OpenVINO 的 CPU 设备在任何 x86 上都能跑，你先确认"ONNX → IR 转换 + 前后处理"正确，最后只差"GPU 设备识别"那一步，再拿去带核显的机器上验证；
- 更省事的替代：**ncnn-Vulkan 一条路同时覆盖 NVIDIA 独显和 Intel 集显**（都吃 Vulkan），本机 Vulkan 已就绪，可以直接测。

**建议**：把"Intel 集显"从"本机可测"改成"需第二台机器验证"，不要因为它挡住主线进度。

## 三、⚠️ 第二个纠正：Intel 平台不要用 DirectML

我上一版建议里把 DirectML 列为 Intel 集显的备选，**核实后需要收回**：实测数据（Arc A750 + yolo11n，30 次推理取平均）：

| 后端 | 单帧耗时 |
|---|---|
| **OpenVINO，GPU** | **3.8 ms** |
| OpenVINO，处理器 | 14.9 ms |
| ONNX Runtime，处理器 | 26.9 ms |
| **ONNX Runtime，DirectML** | **73.1 ms** ← 最慢 |

结论非常明确：**在 Intel 平台上，DirectML 比纯 CPU 还慢 2~3 倍**；社区文档的原话是 "Do not choose DirectML on an Intel machine except to measure it, because it is the slowest option on this hardware by a wide margin"。此外 DirectML 已进入维护模式，不适合新项目作为主路径。

**Intel 平台的正确优先级：`OpenVINO` ≫ `ncnn-Vulkan` > `ONNX Runtime CPU EP` ≫ `DirectML`（不用）**

## 五、本机立即可用的方式（按建议顺序）

### 方案 A ⭐ 最省心：ncnn-Vulkan 便携包（今天就能跑通）

Vulkan 已就绪，**零 Python 依赖、零 CUDA 依赖**，一条命令出图：

```bash
# 下载 Real-ESRGAN-ncnn-vulkan Windows 便携包（含 exe 与模型）
# 解压后：
./realesrgan-ncnn-vulkan.exe -i input.jpg -o output.png -n realesrgan-x4plus -s 4
# 显存不够时降 tile：
./realesrgan-ncnn-vulkan.exe -i input.jpg -o output.png -n realesrgan-x4plus -t 256
```
优点：同时覆盖 **NVIDIA 独显 + Intel 集显**（都吃 Vulkan），验证成本最低。
缺点：只有 ncnn 支持的模型（Real-ESRGAN / Real-CUGAN 系），无法接扩散模型。

### 方案 B ⭐ 主力方案：ONNX Runtime GPU（Python 管线）

**注意：不需要单独安装 CUDA Toolkit。** 这是最常见的误区——ORT / PyTorch 的 pip wheel 自带 CUDA 运行时，只要显卡驱动够新（本机 610.88 完全够）。

推荐用**隔离虚拟环境**安装，避免污染现有 Python：

```bash
# 1) 建隔离环境
python -m venv .venv-sr
.venv-sr/Scripts/activate

# 2) 安装带 CUDA 运行时的依赖（ORT 1.28 对应 CUDA 12.x + cuDNN 9）
pip install onnxruntime-gpu            # 关键：不是 onnxruntime
pip install opencv-python pillow numpy
# 如需让 ORT 找到 CUDA/cuDNN DLL，可再装：
pip install nvidia-cuda-runtime-cu12 nvidia-cudnn-cu12
# 并把这些包内的 bin 目录加入 PATH

# 3) 验证 CUDA EP 是否真的启用
python -c "import onnxruntime as ort; print(ort.get_available_providers())"
# 期望看到 CUDAExecutionProvider（只列出不等于能用，需跑一次模型才算通过）
```

**模型路径**：
- 官方 `scripts/pytorch2onnx.py` 导出（需 PyTorch）；
- 或用现成的 ONNX 转换脚本（如 Intel 官方指南 816445 提供的静态/动态 shape 两种导出方式）；
- **静态 shape 更快**（本机固定 tile 512 即可用静态 shape 导出，如 `[1,3,512,512]`）。

**推理参数**（本机 8G 专属）：
```
tile = 512        # 8G 的最佳平衡点，性能损失约 15%
tile_pad = 10     # 出现网格接缝调到 32
half = True       # fp16：显存约 -40%、速度约 +30%、PSNR 损失 <0.2dB
batch = 1
```
显存不足时按 `512 → 384 → 256 → 128 → 换 general-x4v3 小模型` 自动降级。

### 方案 C：PyTorch（最灵活，体积最大）

只有需要**微调 / 训练 / 跑 GFPGAN、CodeFormer 官方实现**时才装。CUDA wheel 约 2.5 GB 下载量，含 CUDA 运行时，无需额外装 Toolkit。

### 方案 D：OpenVINO（本机用于验证管线，非性能路径）

本机是 N 卡，OpenVINO 的 GPU 插件只支持 Intel GPU，所以**本机只能用 OpenVINO 的 CPU 设备**——但这对"先验证管线正确性（ONNX→IR 转换、前后处理、输出比对）"已经足够，而且 OpenVINO 对 Intel CPU 有 oneDNN/AVX 优化，对纯 CPU 用户通常仍是正解。

```bash
pip install openvino
python -c "import openvino as ov; print(ov.Core().available_devices)"
```

## 六、Intel 集显路径专门方案（给目标用户，需第二台机器验证）

Intel 官方有专门的部署指南：**《Using Real-ESRGAN to Upscale Images on the Intel Platform》(文档号 816445, 2024.02)**，已在 Tiger Lake / Alder Lake / Raptor Lake 平台的**集显**上验证通过。标准流程：

```
PyTorch .pth  →  (1) 导出 ONNX（静态或动态 shape）
              →  (2) 转 OpenVINO IR（.xml + .bin）
              →  (3) OpenVINO 推理（device_name="GPU" 用集显，或 "AUTO" 自动选）
```

关键要点：
1. **必须转成 IR**，不要直接喂 ONNX 给 OpenVINO（虽然能跑，但性能差数倍）；
2. **device_name 用 `"AUTO"`** 最省事——OpenVINO 会自己在 CPU/GPU/NPU 之间选，这是"多硬件适配"最优雅的实现；
3. **FP16 是 Intel GPU 的优化项**（OpenVINO 对 Intel GPU 有专门的 FP16 优化）；
4. 集显与系统**共享内存**，16GB 以下机型务必限制输入尺寸（建议 ≤1920）并配合小 tile；
5. 也存在社区预转好的 IR 模型（如 HuggingFace 上的 Real-ESRGAN-OpenVINO），可作为对照参考。

**⚠️ 关于性能数字，必须把来源讲清楚**（我已逐页读完 Intel 文档 816445，**它没有任何性能表格**，只有流程与代码）：

| 模型 | 输入→输出 | PyTorch | OpenVINO | 加速比 |
|---|---|---|---|---|
| x4plus | 512→2048 | 19.919 s | **1.485 s** | **13.4x** |
| x4plus | 1024→4096 | 79.385 s | 5.955 s | 13.3x |
| x4plus_anime_6B | 512→2048 | 6.617 s | 0.583 s | 11.3x |

来源是第三方 HuggingFace 仓库 `ibrhr/Real-ESRGAN-OpenVINO`，测试平台是 **Intel Xeon Platinum 8581C（8 核 16 线程，带 AVX-512 与 AMX）**。

**这个平台和消费级 CPU 不是一回事**：AMX/AVX-512 正是 OpenVINO 拉开差距的主因，而 i5-12400F 这类消费级 CPU 只有 AVX2。所以：
- 在 Xeon+AMX 上：**13x**（可信，但与你用户无关）
- 在消费级 CPU 上：**预期 2~4x**（推测，**必须实测**）
- 结论层面仍然成立：OpenVINO 是 Intel CPU 的优先选择；但**别把 13x 写进产品预期**。
- 另外该仓库是第三方转的 IR，权重来源与转换脚本未公开审计，**建议自己按 3.1/3.2 节流程转一遍**，而不是直接采信。

## 七、架构修正：ONNX Runtime 统一 API + 动态注册 EP

这轮核实让上一版的架构建议更清晰了——**不要为不同硬件选不同的推理框架，而是统一用 ONNX Runtime，在运行时注册不同的 Execution Provider**：

```python
# 伪代码：一个 API，三种硬件
import onnxruntime as ort

providers = ort.get_available_providers()
if "CUDAExecutionProvider" in providers:          # NVIDIA
    ep = [("CUDAExecutionProvider", {}), "CPUExecutionProvider"]
elif "OpenVINOExecutionProvider" in providers:    # Intel（CPU / 集显 / NPU）
    ep = [("OpenVINOExecutionProvider", {"device_type": "AUTO"}), "CPUExecutionProvider"]
else:                                             # 兜底
    ep = ["CPUExecutionProvider"]

sess = ort.InferenceSession("model.onnx", providers=ep)
```

**明确不要**把 `DmlExecutionProvider` 放进优先级列表（除 AMD 显卡外无收益，Intel 上反而更慢）。

**唯一例外**：ncnn-Vulkan 走独立通道（它不是 ORT 的 EP），用于"最省心、零依赖"的兜底路径。所以最终是**两条腿**：
```
ONNX Runtime（CUDA / OpenVINO / CPU，走 ONNX 模型）
        +
ncnn-Vulkan（走 ncnn 模型，零依赖兜底）
```

## 附：本次探测的实现要点（给 `tools/hwprobe.py`）

- NVIDIA 显卡通过 `nvidia-smi --query-gpu=... --format=csv,noheader,nounits` 获取，能拿到**真实显存**（WMI 的 `AdapterRAM` 是 uint32，超过 4GB 会溢出——本机就显示成 4095MB，不可用）；
- 非 N 卡通过 `Win32_VideoController` 枚举，并**过滤掉虚拟适配器**（如 GameViewer / Basic Display），否则会把虚拟显示器误判成 GPU；
- Intel F/KF 后缀自动判定"无核显"，避免给出错误路径；
- 所有探测项独立 try/except，任一项失败不阻断整体；
- 输出 `--json` 可直接被应用能力层消费。
