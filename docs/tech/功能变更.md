## 2026-10-10 · T-703 主链路系统联调：画质与接缝验收（S1 画质红线落地）

**性质**：**系统联调 + 画质验收** —— 第一个回答「**画得好不好**」的交付（此前所有验证只答

### 验收结论（客观指标）

| 判据 | 结果 |
|---|---|
| **`F-01` 尺寸** | 逐条**精确 = 源 ×4（误差 0）**（7 组模型矩阵全过） |
| **`F-01` 色彩** | **互换反证全部为恒等映射**：输出按 ×scale 面积平均回源尺寸后，恒等映射误差 **< R↔B 互换映射误差** |

**官方参考交叉校验**（管线正确性，而非自证）。

> ⚠️ **教训：显示假象陷阱**。缩放的整幅并排对比图会因显示重采样产生观感假象 —— 一度据此误判
> "沙由金黄变灰、天空偏青"，量化后两半通道均值差 `< 1`，**1:1 裁剪**证实色彩一致。

## 2026-10-09 · 内置模型补齐「风格」维度：新增动漫与轻量通用两个模型

**性质**：**新增内置资产**（不改代码逻辑）。用户指出 Real-ESRGAN 有写实 / 动漫 / 通用之分，
核查确认那是**独立权重文件，不是参数档位**——本项目把"换风格"实现为「**换模型**」（F-05），
但内置清单原先只有 `RealESRGAN_x4plus` **一个风格**的三个技术变体（fp32 / fp16 / IR），
因此界面上"看不出风格可选"。本次补入两个风格模型。

### 新增内置模型

| 模型 | 风格 | 架构 / 参数 | 显存门槛 | 说明 |
|---|---|---|---|---|
| `RealESRGAN_x4plus_anime_6B.onnx` | **动漫** | RRDBNet 6 块 / 4,467,779 | 2048 MB | 针对线条与平涂色块优化，适用于动画截图与插画；处理写实照片仍应选通用模型 |
| `realesr-general-x4v3.onnx` | **轻量通用** | SRVGGNetCompact / 1,213,296 | 1024 MB | 4.6 MB，体积与算力需求远低于 x4plus，面向低配 / 纯 CPU 场景 |

内置项由 **3 → 5**，现涵盖三个风格：**通用/写实、动漫、轻量通用**。

### 不变的（重要）

- **风格仍由「模型」区分，不由参数区分**：参数面板**不新增**"风格"开关——PRD §7.3 明确

## 2026-10-09 · 首启自标定落地 + 应用环境换入 GPU 版 ONNX Runtime（T-805 + 环境变更）

**性质**：**新增功能（引擎阶段 C）+ 部署环境升级**。"自动"档首次从**保底档**升级为**本机实测参数**；
同时应用环境接通 CUDA（用户要求"GPU 环境必须要有"）。

### 新增能力

| 能力 | 说明 |
|---|---|
| **逐档 tile 标定** | 逐档测量延迟与**峰值显存**，产出 `tile_curve`（含 `recommended_tile`）与 `precision_decision`；结论落 `Calibration` 表 |
| **预算与停止条件** | 阶段 C 有 **≤8s 预算**（硬边界），超预算**停在当前最优档**；单档遇到高水位即停止继续上探 |
| **逐档异常隔离** | 某一档加载/推理失败只作废该档，不影响整条曲线与最终结论 |
| **触发接口** | `POST /api/system/calibrate`（异步，返回 `task_id`；已有作业在跑则返回当前状态不叠加）与 `GET /api/system/calibration` |
| **首启自动标定** | 启动序列第 2 步：**能力探测 / EP 验证完成之后**，若无有效标定则**非阻塞**投递后台标定（标定依赖指纹与已采纳后端，不能与探测并发） |
| **结论绑定硬件指纹** | 换卡 / 换驱动 / 换 ORT 组合即失效重标（与 EP 验证缓存同一套指纹口径） |

### 行为变化（对用户可见）

- **"自动"档不再等于"保底档"**：标定完成后 `using_fallback` 变为 `false`，`source` 由
  `fallback` 变为 `calibration`，参数为**本机实测最优**。
- **本机实测（RTX 3050 8G）**：`64 → 70ms / 941k px/s`、`128 → 179ms / 1466k`、
  **`256 → 670ms / 1564k`（最优，显存 34%）**、`384 → 1534ms / 1538k`、
  `512 → 3485ms / 1204k ↓`（**显存 95% → 触发停止**）。推荐 **256**。
  若按直觉取 512，**吞吐反降 23% 且吃掉 95% 显存**。
- **档位由 T0 升为 T1**：应用环境换入 GPU 版 ORT 后，真机节点归属 **CUDA 1024 / CPU 0**。
- **档位模拟下不冒充结论**：`simulation_enabled` 打开时产出标 `simulated: true`，
  **`is_storable()` 为假**，不写入正式标定表。

### 修复的缺陷（均为**真实产品缺陷**，不是测试问题）

- **CUDA 13 包布局导致 DLL 未注册 → 静默回退 CPU**：CUDA 13 的运行时 DLL 位于
  `nvidia/cu13/bin/x86_64/`（比 CUDA 12 **多一层 `x86_64`**），而 `runtime_env.py` 只扫
  `nvidia/<pkg>/{bin,lib}` → CUDA 运行时未注册，ORT 只打一条 warning 就回退 CPU
  （报 `cublasLt64_13.dll is missing (Error 126)`）。已使 `_candidate_dirs()` 兼容两层布局。
- **EP 验证缓存误命中 → 标定跑在 CPU 上**：`hardware_fingerprint` 原先未纳入
  "ORT 可用 EP 列表" → 换 CPU 版→GPU 版时 **ORT 版本号未变（都是 1.30.0）**，
  指纹相同 → 缓存**沿用旧结论**"CUDA 不可用"。已把 `ort_available_providers` 纳入指纹。
  **教训**：缓存键必须覆盖**全部会影响结论的输入**，不只是版本号。
- **`runtimes.module_version()` 查不到 GPU 版版本号**：`onnxruntime-gpu` 是**独立发行名**，
  用模块名 `onnxruntime` 查会 `PackageNotFoundError`（诊断里丢版本号）。已加发行名映射。
- **`verify_t803_engine.py` 从未注册 DLL 路径**：脚本没调 `prepare_dll_paths()`，
  进程内 CUDA 找不到 `cublasLt` 而回退；且断言单向预设"sr-app 必然无 CUDA"，
  该前提在换装后不成立。已补调用并改为**双向判定**。

### 明确未交付（诚实边界）

- **T1 以外档位未验证**（T2/T3 无对应硬件）；标定结论**不得进产品参数表**
  （开发机实测值不硬编码，"机制硬编码、数值运行时求"）；
- **真实照片的人眼质量复核仍未做**——标定只回答"多快"，不回答"多好"。

### 新增能力

## 2026-10-09 · 引擎阶段 D/E 落地：参数决策、水位反馈与保底档（T-804）


**性质**：**新增功能（引擎控制面）**。首次让"这次任务用多大的块、什么精度、哪个后端"
变成**可解释、可降级、可追溯**的引擎结论；但**不产生图像**——真实推理由 `T-806` 接入。

### 新增能力

| 能力 | 说明 |
|---|---|
| **阶段 D 决策** | 每个任务产出一份 `RuntimeProfile`：`tile / precision / backend / overlap / feather_px / concurrency` + `using_fallback / degraded / reasons / downgrades / source` |
| **决策来源可追溯** | `source ∈ {calibration, user, fallback}`——标定命中 / 用户指定 / 保底档，界面"本次决策"直接可解释 |
| **因果性防御** | 四类硬约束**无条件执行**（不信任来源）：后端必须已验证、CPU 路径禁 fp16、fp16 需 `compute_cap ≥ 5.3`、tile 不低于下界且对齐模型倍数。触发即记 `downgrades` + `degraded=true` |
| **过渡区取值** | `overlap = feather_px = align_down(tile/4, align)`——沿用 T-802 质量对照实验验证过的 1:4 比例与"feather = overlap"交接契约 |
| **阶段 E 水位反馈** | 任务边界采样显存/物理内存，口径取**较大者**（T0 档的真瓶颈是内存）；连续 **2 次 > 85%** 触发下一次任务**降一档** |
| **OOM 降档链** | 识别资源耗尽类异常 → `tile` 折半（至下界 64）→ 后端 GPU→CPU（仅当 CPU 已验证）→ 耗尽报 `VRAM_INSUFFICIENT` / `RAM_INSUFFICIENT`；**只重试一次** |
| **保底档（§6.8）** | 未标定时的保守下界参数（下界 tile / `fp32` / 并发 1 / 已验证后端首项），**不写入**标定记录与模型元信息；界面必须可见"当前为保底档" |
| **决策可取证** | 诊断导出新增 `decision`（最近一次决策 + 保底档与水位策略）与 `watermark`（水位历史）两个区段 |

### 行为变化（对用户可见）

- 任务详情的 `resolved` 从**占位常量**变为**真实引擎决策**，并新增
  `overlap` / `feather_px` / `concurrency` / `source` 四个字段（挂账 T-700 契约补齐）；
- 任务失败时，资源耗尽类错误不再笼统报"推理执行失败"，而是区分
  `VRAM_INSUFFICIENT`（GPU 后端）与 `RAM_INSUFFICIENT`（CPU 后端），并在 `detail` 里带上
  已降档次数、生效后端与当时的资源水位；
- 连续高水位后，下一个任务的 `resolved.downgrades` 会明确写出"因连续 N 次水位超阈值而降档"；
- OOM 后会自动降一档重试一次，任务详情的进度提示会显示"资源不足，已降档（tile → 128）后重试"。

### 修复的缺陷

- **并发槽被观测动作占住**：水位采样需起 `nvidia-smi` 子进程（百毫秒级），原先排在
  终态落库之后、释放并发槽之前 → "任务已显示完成，但提交新任务仍返回 409
  `TASK_ALREADY_RUNNING`"。已改为终态落库后**立即释放并发槽**，观测与广播排其后。

### 明确未交付（诚实边界）

- **真实推理与真实产物**（`T-806`）：`resolved` 是**决策结果**，不是已发生的加速；

- **两个必踩的坑**：`ncnn.Mat(numpy)` 按 **(c,h,w)** 解释且**借用**缓冲区

### 质量红线是怎么被证明的

"无可见接缝"若只靠肉眼看图，无法回归、也无法证伪。这里用的是**带判别力的对照实验**：

| 分组 | 边界峰比（接缝指标） |
|---|---|
| 硬切（无重叠拼贴，已知有接缝） | **63.0** ← 证明指标确实能测出接缝 |
| **本实现（overlap + feather）** | **1.3** ← 无孤立阶跃 |
| 逐像素推理器下与整图推理对比 | **逐像素精确相等（max abs diff = 0）** |

边界峰比 = 块边界列的跨列差分 ÷ 邻域中位差分——接缝的本质不是"梯度大"，而是**该处梯度
相对周围突然变大**。真实图像的人眼复核属 S1 闭环验收，需 T-806（模型加载器）就位后跑
真实 RealESRGAN。

| 每行分割线 | ~760px | **+40% 高度逼出滚动**，且与基线正面冲突 |
| 卡片式（`bg-elevated` 无描边） | ~760px | **实测更差**：padding 压缩内容宽（272→248px），hint 折行增多；嵌套层级过重 |
| **语义分组线** | **563px** | **采纳** —— 1 条线分清「可调」与「自动档接管」，仅 +21px |
| 纯增大行距 | 590px | 最贴基线，但边界感弱于线条 |

**落地**：只在**第 4 行前**加 1 条线 ——

- 组 1（1–3 行）自动档 / 模型 / 放大倍数 —— 用户直接决定
- 组 2（4–6 行）分块 tile / 精度 / 后端 —— 「自动档」打开时由引擎接管
- **组内仍靠留白**，线只标记语义边界，故不与基线相悖

**为何不逐行加线**：6 条**等权重**的线会稀释「哪 3 项会被自动档接管」这一关键信息 —— 线越多，重点越模糊。

**实测**：仅第 4 行为 1px 线（`#2e2e2e`），其余 0px；控件左边界仍全部对齐 `x=127`（无回归）；左栏与窄屏抽屉一致。

## 2026-10-08 · 字体自托管（拉丁子集）

**性质**：消除「设计意图无法落地」的隐患。此前项目**未引入任何 webfont**，字体完全依赖系统安装。

### 问题

字体栈声明为 `Inter, "Noto Sans SC", system-ui, …`，但实测本机 **Inter 与 JetBrains Mono 均未安装** —— 界面实际渲染回退到第二顺位（Noto Sans SC / Cascadia Mono）。

后果不是「难看」（Noto Sans SC 的拉丁部分质量不错），而是**视觉验收不可复现**：换一台装过 Inter 的机器，字宽随之改变，换行位置与表格列宽跟着变。

### 处置

自托管两份**拉丁子集可变字体**，不依赖用户系统：

| 项 | 内容 |
|---|---|
| 文件 | `web/src/assets/fonts/` 下两个 woff2 |
| 声明 | 新建 `web/src/styles/fonts.css`（`@font-face` + `unicode-range`） |
| 引入 | `web/src/main.ts` 增加一行 `import './styles/fonts.css'` |
| 来源 | `@fontsource-variable` 5.3.0 —— **可变字体**，一个文件覆盖全部字重 |
| 子集 | **仅 latin** —— 界面无西里尔 / 希腊 / 越南字符，其余子集不打包 |

**体积**：Inter 47 KB ＋ JetBrains Mono 39 KB = **86 KB**（构建产物 48.25 + 40.40 KB）。

**中文不走 webfont**：`unicode-range` 把两个字体限定在拉丁字符，中文自动回退到系统的 Noto Sans SC。回退链：

```
拉丁字符 → Inter（自托管）         ｜  中文字符 → Noto Sans SC（系统）
技术数值 → JetBrains Mono（自托管）  ｜  其中的中文 → 系统字体
```

### 实测验证

| 检查项 | 结果 | 判定 |
|---|---|---|
| `document.fonts` | `Inter @100 900`、`JetBrains Mono @100 800` 均 loaded | ✅ |
| 顶栏 `WebSR`（纯拉丁 5 字符） | **Inter（webfont）** | ✅ 自托管生效 |
| 导航项（中文） | Noto Sans SC（系统） | ✅ 正确回退 |
| 档位徽标（数字/字母 8 字符） | **JetBrains Mono（webfont）** | ✅ 等宽生效 |

控制台零错误；构建通过（1687 模块）。

### 顺带清理

删除 `src/assets/` 下 3 个**零引用**的脚手架残留：`hero.png`、`vite.svg`、`vue.svg`。
（`public/favicon.svg` 与 `public/icons.svg` 为实际使用，保留。）

### 未处理

**斜体**：`ParamDiffRow` 的「自动档」标记使用 `font-style: italic`，但该处文本是**中文** —— Inter 无中文字形，引入 Inter Italic 无意义，保持浏览器合成斜体。

## 2026-10-08 · UI 可用性调整（用户反馈驱动）

**性质**：5C 前端上线试用后的两项可用性问题修复。**不改变任何功能语义**，仅调整阅读密度与版面一致性。

### 变更 1：默认字号偏小（2K 分辨率下阅读吃力）

**根因**：`tokens.css` 定义了 `--font-size-*` 字号体系，但组件内 **111 处 `font-size` 是硬编码 px**、token 仅被引用 14 次 —— 字号体系名存实亡，直接调整 token 不生效。

**处置**：

| 步骤 | 内容 |
|---|---|
| ① 收敛硬编码 | 125 处 `font-size` 全部改为 token 引用（**先决条件**，否则后续无效） |
| ② 字阶上调一档 | 重新编号：`10/11/12/13/15/18/24` → `11/12/13/14/16/20/26`（token 名始终等于像素值） |
| ③ 布局尺寸同步 | 顶栏 `56→60`、表格行 `48→52`、输入框 `36→40`、图标按钮 `32→36` |

**影响**：`body` 字号 `13 → 14px`；主正文 `12/13 → 13/14px`；辅助文字 `11 → 12px`。面板宽度未改动（320 / 340）。

### 变更 2：独立页内容宽度不一致

**根因**：`PAGE_MAX_WIDTH` 逐页差异化（tasks 1344 / models 1408 / hardware 1200 / settings 880），切换页面时内容区左右边界跳变。

**处置**：统一为 **1344**。

**连带调整**（否则会引入「label 与值相隔近千像素」的新问题）：

- **P5 系统配置**：改为 **grid 双列**（每列约 630px），label 与值保持成组；< 1280 视口退回单列
- **P4 硬件能力**：`SettingsRow` 增加**容器查询** —— 卡体 ≥ 1000px 时改为「固定 220px label 列 + 值左对齐」

**边界约束**：容器查询在 compact 档（卡体 < 968px）与窄卡体（工作台右栏约 300px、设置页双列约 630px）**不触发**，这些场景保持原有两端对齐不变。
