## 2026-10-09 · 前置验证收口：ncnn 在 Windows/Python 下**可用**（T-210）

**性质**：**结论任务**，不改动产品代码，但**解除了一条横在 `T-806` 前面的未知项**，并把 PRD / tech-arch / ADR-003 中所有"条件支持（未验证）"的表述改回与事实相符。

### 结论

| 判据 | 结果 |
|---|---|
| 获取方式 | ✅ PyPI **官方 wheel**（`cp38`~`cp314` × `win_amd64`），**无需自行编译** |
| 真实推理（非"仅 import"） | ✅ `realesrgan-x4plus` 999 层，64×64 → 256×256 |
| 是否全黑（ncnn 已知 bug） | ✅ **未触发**（mean 0.4834 / std 0.1748） |
| 与 ONNX 主路径一致性 | ✅ **corr 1.0000 / PSNR 63.39 dB** |
| Vulkan 后端 | ✅ wheel 内含，真机枚举 RTX 3050；CPU↔Vulkan 最大差 0.0067 |
| 降级路径（外部 exe） | ✅ `realesrgan-ncnn-vulkan.exe` rc=0，220→880 px 非全黑 |

**14/14 断言通过，脚本判定 `usable`。**

### 功能层面的变化（措辞与承诺口径）

- **PRD §7.5 `.bin` 行**：ncnn 由"**条件支持**（验证通过前不计入 v1 承诺）"→
  "**已验证可用**"，并保留**按模型评估层覆盖**的约束。**未单方面扩大承诺**——
  是否列入 v1 交付清单留待 §2.7 切片在 S1 验收时确认。
- **PRD §7.2 / tech-arch §7 风险 1**：ncnn 可用性风险行**关闭**。
- **tech-arch §7 风险 2**：黑图/Vulkan 风险**降级为运行时探测项**（本机未触发，
  但"无 Vulkan 设备时的回退"仍未验证，T-806 须显式判定）。
- **ADR-003**：决策本身**不变**（ncnn 仍是可选后端、失败即降级），
  但"必须在实现前验证"的两条风险中第 1 条已关闭。

### 交付物

| 产物 | 位置 |
|---|---|
| 验证脚本 | `tools/verify_ncnn_windows.py`（14 项断言，可重复运行） |
| 结论文档 | `docs/tech/research/图像超分修复-T210-ncnn可用性验证结论.md` |
| 证据 | `.workbuddy/verify/t210/ncnn_verify_report{,_128}.json`、`exe_out_x4.png` |
| 隔离环境 | `.venvs/sr-ncnn`（项目内新建，未污染既有四个环境） |

### 给后续实现的关键情报（T-806 直接用）

- **两个必踩的坑**：`ncnn.Mat(numpy)` 按 **(c,h,w)** 解释且**借用**缓冲区
  （传 HWC 会越界；数组被 GC 会**无回溯段错误退出 139**）；
  `create_gpu_instance()` 必须配对 `destroy_gpu_instance()`，否则解释器退出阶段崩溃。
- **依赖代价可控**：wheel 硬依赖 `opencv-python`（113 MB），但**运行期不加载 cv2** →
  用 `ncnn --no-deps` 安装，代价从 ~130 MB 降到 ~14 MB。
- **Vulkan 的收益随 tile 面积增长**：64×64 输入时 Vulkan 比 CPU **慢**（0.74×），
  128×128 时 **快 2.36×**——小 tile 会被固定开销吃掉。

### 边界（未验证项，不得据此下结论）

非 RealESRGAN 的 ncnn 模型、无 Vulkan 的 Windows、无 AVX2 的老 CPU、
Intel/AMD 显卡、tile×显存矩阵、多任务并发（ncnn 的 GPU 实例是进程级单例）。

## 2026-10-09 · 步骤 5D 引擎核心：能力探测与 EP 真实性验证（T-803）

**性质**：F-06「硬件能力面板」的数据来源，也是"**不用错后端**"这一承诺的技术基础。

### 交付物

| 模块 | 交付 |
|---|---|
| `engine/device_probe.py`（**阶段 A**） | `DeviceFacts`：CPU（名称/架构/核数/内存总量与可用）、NVIDIA GPU（名称/驱动/显存标称与**实读可用**/计算能力）、Intel GPU（**按 `FULL_DEVICE_NAME` 判定，区分核显/独显**）、OpenVINO 设备、ORT 候选提供器。**永不抛异常**，失败项与"前置缺失而跳过"分别记录 |
| `engine/ep_verify.py`（**阶段 B**） | 候选链展开 + 逐后端真实性验证（**ORT profile 节点级归属**）+ 剔除规则（部分接管 > 30% / 比 CPU 慢） |
| `engine/backend_cache.py` | 验证结果缓存到 `data/calibration/`，**硬件指纹（含驱动与 ORT 版本）变化即作废** |
| `engine/capabilities.py` | 阶段 A → 缓存 → 阶段 B 编排 + **档位判定（§6.2）** + 契约 `Capabilities` 组装 |

### 功能层面的变化

- **硬件能力面板不再是占位**：`/api/system/capabilities` 返回**实读**数据（本机：RTX 3050 OEM /
> 
驱动 610.88 / 标称 8.0 GB / 实际可用约 6.9 GB），并给出**识别出的档位与理由**。
- **"不用错后端"**：EP 对象存在**不再被当作可用**。唯一判据是 ORT profile 的节点归属：
  **目标 EP 节点数 > 0 且 CPU 节点数 = 0**。EP 创建失败（DLL 缺失、ABI 不匹配）时 ORT
  只打一条 warning 就静默回退 CPU——现在这种"看似加速实则更慢"的情况会被**检出并记录为异常事件**。
- **档位不再"检测到显卡就升档"**：档位由**实读可用显存 + 已验证后端**推导，
  且**不按设备型号分支**（代码级禁止）。本机 `.venvs/sr-app` 无 CUDA 时如实落 T0 并说明原因。
- **诊断导出增强**：新增 `probe`（探测失败项、跳过项、每项耗时）与
  `ep_verification`（硬件指纹、缓存状态、采用/排除的后端、异常事件），
  做到"一键导出即可解释为什么他慢/崩"。
- **启动第 2 步落地**：能力探测 → EP 验证在**线程里非阻塞**执行；失败只记异常事件，
  服务照常可用（保底档兜底）。
- **新增运行时依赖**：`onnxruntime`（CPU 基线 wheel）。

### 真机取证（这是本任务最值得看的一行）

| 后端 | 节点数 | **CPU 节点数** | 干净延迟 | 判定 |
|---|---|---|---|---|
| **CUDAExecutionProvider** | 1024 | **0** | **677.8 ms** | ✅ 已接管 |
| CPUExecutionProvider | 1409 | 1409 | 8215.8 ms | ✅ 保底 |

同一台机器、同一模型（RealESRGAN_x4，256×256 输入）：**CUDA 比 CPU 快 12.1 倍**，
档位判定为 **T1**。证据存 `.workbuddy/verify/t803/cuda_evidence.json`。

**性质**：S1 的**质量红线**交付——超分结果靠它才不会出现可见接缝。

### 交付物

| 模块 | 交付 | 验证 |

| `engine/tiling.py`（M4 分块与拼接） | `plan_tiles` 分块计划 + `TileAccumulator` **overlap + feather 加权拼接**；`stitch` 纯函数入口 | 87/87（含 T-802 全量） |

### 功能层面的变化

- **新增能力**：任意尺寸图片 → 固定尺寸块序列 → **无可见接缝**拼接回原尺寸 × 放大倍数。
- **替换掉的东西**：`tools/_bench_common.py::tiled_infer` 是**无羽化**的基准形状验证器，
  按 tech-arch §6.5 明确"生产实现必须重写"——本任务是产品侧重写，`tools/` 保持基准形态不动。
- **新增运行时依赖**：`numpy`。
- **顺带修复**：上传缩略图补 **EXIF 方向转正**（此前手机竖拍图会出现"缩略图方向 ≠ 超分结果方向"，
  且旁车元信息宽高是转正前的值）。

### 质量红线是怎么被证明的

"无可见接缝"若只靠肉眼看图，无法回归、也无法证伪。这里用的是**带判别力的对照实验**：

| 分组 | 边界峰比（接缝指标） |
|---|---|
| 硬切（无重叠拼贴，已知有接缝） | **63.0** ← 证明指标确实能测出接缝 |
| **本实现（overlap + feather）** | **1.3** ← 无孤立阶跃 |
| 逐像素推理器下与整图推理对比 | **逐像素精确相等（max abs diff = 0）** |

边界峰比 = 块边界列的跨列差分 ÷ 邻域中位差分——接缝的本质不是"梯度大"，而是**该处梯度
相对周围突然变大**。真实图像的人眼复核属 S1 闭环验收，需 T-806（模型加载器）就位后跑
真实 RealESRGAN。

| **语义分组线** | **563px** | **采纳** —— 1 条线分清「可调」与「自动档接管」，仅 +21px |
| 纯增大行距 | 590px | 最贴基线，但边界感弱于线条 |

**落地**：只在**第 4 行前**加 1 条线 ——

- 组 1（1–3 行）自动档 / 模型 / 放大倍数 —— 用户直接决定
- 组 2（4–6 行）分块 tile / 精度 / 后端 —— 「自动档」打开时由引擎接管
- **组内仍靠留白**，线只标记语义边界，故不与基线相悖

**为何不逐行加线**：6 条**等权重**的线会稀释「哪 3 项会被自动档接管」这一关键信息 —— 线越多，重点越模糊。

**实测**：仅第 4 行为 1px 线（`#2e2e2e`），其余 0px；控件左边界仍全部对齐 `x=127`（无回归）；左栏与窄屏抽屉一致。

## 2026-10-08 · 字体自托管（拉丁子集）

**性质**：消除「设计意图无法落地」的隐患。此前项目**未引入任何 webfont**，字体完全依赖系统安装。

### 问题

字体栈声明为 `Inter, "Noto Sans SC", system-ui, …`，但实测本机 **Inter 与 JetBrains Mono 均未安装** —— 界面实际渲染回退到第二顺位（Noto Sans SC / Cascadia Mono）。

后果不是「难看」（Noto Sans SC 的拉丁部分质量不错），而是**视觉验收不可复现**：换一台装过 Inter 的机器，字宽随之改变，换行位置与表格列宽跟着变。

### 处置

自托管两份**拉丁子集可变字体**，不依赖用户系统：

| 项 | 内容 |
|---|---|
| 文件 | `web/src/assets/fonts/` 下两个 woff2 |
| 声明 | 新建 `web/src/styles/fonts.css`（`@font-face` + `unicode-range`） |
| 引入 | `web/src/main.ts` 增加一行 `import './styles/fonts.css'` |
| 来源 | `@fontsource-variable` 5.3.0 —— **可变字体**，一个文件覆盖全部字重 |
| 子集 | **仅 latin** —— 界面无西里尔 / 希腊 / 越南字符，其余子集不打包 |

**体积**：Inter 47 KB ＋ JetBrains Mono 39 KB = **86 KB**（构建产物 48.25 + 40.40 KB）。

**中文不走 webfont**：`unicode-range` 把两个字体限定在拉丁字符，中文自动回退到系统的 Noto Sans SC。回退链：

```
拉丁字符 → Inter（自托管）         ｜  中文字符 → Noto Sans SC（系统）
技术数值 → JetBrains Mono（自托管）  ｜  其中的中文 → 系统字体
```

### 实测验证

| 检查项 | 结果 | 判定 |
|---|---|---|
| `document.fonts` | `Inter @100 900`、`JetBrains Mono @100 800` 均 loaded | ✅ |
| 顶栏 `WebSR`（纯拉丁 5 字符） | **Inter（webfont）** | ✅ 自托管生效 |
| 导航项（中文） | Noto Sans SC（系统） | ✅ 正确回退 |
| 档位徽标（数字/字母 8 字符） | **JetBrains Mono（webfont）** | ✅ 等宽生效 |

控制台零错误；构建通过（1687 模块）。

### 顺带清理

删除 `src/assets/` 下 3 个**零引用**的脚手架残留：`hero.png`、`vite.svg`、`vue.svg`。
（`public/favicon.svg` 与 `public/icons.svg` 为实际使用，保留。）

### 未处理

**斜体**：`ParamDiffRow` 的「自动档」标记使用 `font-style: italic`，但该处文本是**中文** —— Inter 无中文字形，引入 Inter Italic 无意义，保持浏览器合成斜体。

## 2026-10-08 · UI 可用性调整（用户反馈驱动）

**性质**：5C 前端上线试用后的两项可用性问题修复。**不改变任何功能语义**，仅调整阅读密度与版面一致性。

### 变更 1：默认字号偏小（2K 分辨率下阅读吃力）

**根因**：`tokens.css` 定义了 `--font-size-*` 字号体系，但组件内 **111 处 `font-size` 是硬编码 px**、token 仅被引用 14 次 —— 字号体系名存实亡，直接调整 token 不生效。

**处置**：

| 步骤 | 内容 |
|---|---|
| ① 收敛硬编码 | 125 处 `font-size` 全部改为 token 引用（**先决条件**，否则后续无效） |
| ② 字阶上调一档 | 重新编号：`10/11/12/13/15/18/24` → `11/12/13/14/16/20/26`（token 名始终等于像素值） |
| ③ 布局尺寸同步 | 顶栏 `56→60`、表格行 `48→52`、输入框 `36→40`、图标按钮 `32→36` |

**影响**：`body` 字号 `13 → 14px`；主正文 `12/13 → 13/14px`；辅助文字 `11 → 12px`。面板宽度未改动（320 / 340）。

### 变更 2：独立页内容宽度不一致

**根因**：`PAGE_MAX_WIDTH` 逐页差异化（tasks 1344 / models 1408 / hardware 1200 / settings 880），切换页面时内容区左右边界跳变。

**处置**：统一为 **1344**。

**连带调整**（否则会引入「label 与值相隔近千像素」的新问题）：

- **P5 系统配置**：改为 **grid 双列**（每列约 630px），label 与值保持成组；< 1280 视口退回单列
- **P4 硬件能力**：`SettingsRow` 增加**容器查询** —— 卡体 ≥ 1000px 时改为「固定 220px label 列 + 值左对齐」

**边界约束**：容器查询在 compact 档（卡体 < 968px）与窄卡体（工作台右栏约 300px、设置页双列约 630px）**不触发**，这些场景保持原有两端对齐不变。
