## CHG-20261011-02 · 后端 `tier_reason` 去掉内部实现名（承接 CHG-20261011-01 遗留项）

### 🔴 Bug-003：t603 端口写死 8000 —— 「测的东西没跑，断言却绿了」

这是本轮**最有价值的发现**，其危害不是红灯，而是**假绿**：

1. 脚本把端口写死 8000（`--port` / `wait_health` URL / `APP_PORT`），而它要验证的是
   「**起自己的后端进程**、在**临时数据目录**上完成迁移」；
2. 开发后端占用 8000 时，子进程 bind 失败**静默退出**（stdout 全空，连 bind 错误都没打）；
3. `wait_health` 轮询 8000 拿到的是**开发后端**的 200 → **`A1 假通过`**；
4. 临时库从未迁移 → `A2/A3` 失败 → 播种 `Task` 抛 `no such table: task`，
   脚本带**裸 Traceback 中断**，B/C 场景根本没跑到，**报出的失败数因而失真**。

> 🔑 与 T-706「断言把缺陷固化成了期望」同族：**绿灯不等于被测对象真的跑过**。

**修复**：新增 `free_port()`（`socket.bind(("127.0.0.1", 0))` 由内核分配），端口贯穿三个调用点；
A3 失败时**显式判停**并给可读结论（不再裸 Traceback 中断）；`wait_health` 失败时回带子进程日志尾部。

## CHG-20261011-04 · 模型库与工作台：简介拆两级、卡片降密度、移除「不做推荐」冗余文案

**性质**：**前端 UI 优化**（用户反馈 2 条）—— 不改契约、不改后端逻辑。

### 1. 移除「模型始终由你选择，系统不做推荐」

- 工作台模型行删除该 `hint`；模型库顶部说明删去同义的前半段
  「模型不做自动推荐：引擎不会替你挑选，也不会按显存排序」，**只保留后半段有解释价值的置灰说明**。
- **理由**：这是**否定式表述**——用户要的是「有哪些模型可用」，不是被告知系统不做什么。
  PRD §7.3 的「不做自动推荐」本就该由**行为**保证（无推荐标记、排序不干预），不需要靠文案反复声明；
  且同一件事在两页说了两遍。腾出的位置改放**模型简介**，信息量更高。

### 2. 适配简介拆成「定位 + 补充」两级

T-716 的简介统一按「定位 + 适合 + 不适合」三段撰写，但此前**整段以同字号同色渲染成 3 行文字块**，
与模型名称争夺注意力——用户无法一眼看出「这个模型是干什么的」。

- 在 `viewModel.ts` 新增 `splitDescription()`：以**首个句末标点**（。！？）为界拆成
  `descLead`（定位）与 `descDetail`（补充）。分号/逗号**不**作切分点
  （定位句内常含「（如 SRVGGNetCompact，1.21M 参数）」这类括注）。
- **安全回落**：无句末标点、或首句超过 64 字时，**整段作为 lead、detail 留空**——不截断、不丢原文。
- **共用**：模型库卡片与工作台模型行**用同一份拆分**，避免同一模型在两页呈现形态不同
  而让用户误以为数据不一致。
- 已用线上 11 个模型的真实简介验证：`lead + detail === 原文`，**无一例信息丢失**。

### 3. 模型卡片版式重构

| 元素 | 改前 | 改后 |
|---|---|---|
| 名称 | 15px / 600 | **17px / 600**（主导层） |
| 简介 | 13px 次级色，**整段 3 行** | 定位 **14px 主色** + 补充 **13px 三级色 2 行**（`title` 悬浮看全文） |
| 倍率徽标 | 13px 常规 | 13px **加粗**、底色加深 |
| 资源事实 | **3 行**「标签 … 值」 | **1 行**内联：`最低显存 4.0 GB · 体积 63.9 MB · 步数 1`，上加分隔线 |

- **卡片信息层级由此变为**：名称 > 定位 > 补充 > 资源事实 > 后端徽标 > 操作。
- 资源事实原本 3 行占了近 1/3 卡高，却只有「最低显存」真正影响选型（体积/步数属低频信息）；
  压成单行后**同屏可见卡片由 2.5 行增至 3 整行**。
- ⚠️ `.mc-title` 类名**保留不动**：UI E2E 的「使用此模型深链」断言以 `.model-card .mc-title` 取名，
  改名会打断该断言（已在类上留注释标注）。

### 顺带发现 → **已于同日以 CHG-20261011-05 修复**

### 3. 语义（`server/app/services/task_cleanup.py`，逐条可核）

- **只删终态**（completed / canceled / failed / interrupted）。运行 / 排队 / 取消中 → `409 TASK_NOT_TERMINAL`
  （`detail.status` 给出当前态）。**「删除」不得成为绕过「取消」的后门** —— 取消是协作式的，必须走它自己的通道。
- **记录与文件一起删**（PRD §315：「清理必须同时删除文件与数据库记录，且**不得删除模型库中的模型文件**」）：
  `outputs/tsk_<id>/` 整目录 + 产物行指向的文件 + `uploads/<file_id>.<ext>` / `thumbs/<file_id>.jpg` /
  旁车 `uploads/<file_id>.json` —— ⚠️ **仅当没有其它任务仍引用该 `file_id` 时**才删。
  同一张原图可被多次提交（`CHG-20261011-07` 起还支持「产出回灌为源图」的多轮迭代），
  无脑删原图会让**别的任务**失去预览与对比。
- **`data/models/` 永不受影响**：模型是用户显式导入的资产，与任务清理无关。
- **路径安全**：每个待删路径都经 `_under_root()` 校验（`artifact.path` 是库里的字符串，不能无条件信任）。
- **顺序：先删文件、后删记录**。反过来一旦中途失败，磁盘上会留下「没有任何记录指向」的隐形垃圾
  （正是 `Bug-006` 里那类孤儿文件的来源）；先删文件失败时记录仍在列表里、用户可重试且报错明确。
- **不依赖 `ON DELETE CASCADE`**：迁移期 `PRAGMA foreign_keys=OFF` 下 CASCADE 不生效，会静默留下产物行
  （与 `settings_store.cleanup_expired_tasks` 同一处置：显式先删 `ARTIFACT` 再删 `TASK`）。
- ⚠️ **文件是永久删除**（`unlink`/`rmtree`，不进回收站）—— 界面文案据实写「不可恢复」。

**媒体层配套**（`media_store.py`）：新增 `create=False` 的路径助手与 `task_outputs_path()` ——
清理侧只求路径不该建目录，否则「删掉最后一份上传」会顺手把空目录又建回来，收尾后目录状态自相矛盾。

### 🔴 修复了一个真实缺陷：**真实 OOM 根本没被识别**

**现象**：主动请求 `tile=1024/2048/4096` 均**真实 OOM**（`onnxruntime` 报
`Failed to allocate memory for requested buffer of size 4294967296`），但任务终态是
`INTERNAL_ERROR / 推理执行失败 / 请导出诊断 JSON` —— **看不出是显存不够**。

**根因**：推理异常被 `engine/model_loader.py::infer()` 包装成
`ModelLoadError(INFERENCE_FAILED, "推理执行失败", detail={"exception": <原始错误>})`，
而 `ModelLoadError.__init__` 调 `super().__init__(message)` → **`str(exc)` 只剩面向用户的话术**；
`engine/watermark.py::is_oom_error()` **只读 `str(exc)`** → **对真实 OOM 恒为 False**。

**两个后果**：
1. **降档重试完全失效** —— 核心机制在最需要它的时候是哑的；
2. **违反 PRD §2.2 铁律 5「降级必须显式」** —— 用户只看到一个通用内部错误。

**修复**：`is_oom_error()` 改为遍历 `_candidate_texts()` —— **看穿包装层**，把
`str(exc)` + `message`/`reason` 属性 + `detail` 字典值 + `__cause__`/`__context__` **异常链**（深度 4）
**全部**纳入判定，而不是只看最外层那句面向用户的话术。

**修复后行为（真实推理路径）**：

| 请求 | 修复后结果 |
|---|---|
| `tile=1024` | **`completed`**，自动降档 **`1024 → 512`**，`degraded=true` —— 降档链**真的把任务救回来了** |
| `tile=4096` | **`VRAM_INSUFFICIENT`** + 「显存不足：已自动降档仍无法完成」+ `downgrade_attempts=1` + 水位 `ratio 0.9495` |

### 怎么在不伪造硬件事实的前提下真实触发 OOM（方法）

**不降显存、不改 `device_facts`**，用**产品自身的真实入口**：
`POST /api/tasks` with `params.auto=false, tile=<很大>`，配一张**短边小于 tile 的图**。
非自动档允许用户显式指定 tile，因果性防御只保证「≥ 下界、是 align 倍数」，**不为"这台机器跑不动"兜底**
（那是降档链的职责）；短边小于 tile 的图会被 `plan_tiles` **居中补齐成完整 `tile×tile` 块** →
**单块即耗尽显存**，触发快、可重复。**这条路径不需要档位模拟，且比 `force_vram` 更贴近生产 —— 用户真的会这么干。**

### 三条纪律（写进契约 §4.4）

1. **只覆盖「判定输入」，不伪造「硬件事实」** —— `device_facts` 一个字不改（**诚信判据**：

### 缓存纪律（易踩，本轮的坑）

- **模拟态下不读写 EP 验证缓存**（`cache_state = "bypassed_simulation"`）。理由：指纹恒按
  **真实** facts 计算，把"带模拟成分"的 verdict 写进去会**污染真实硬件指纹下的缓存**——
  之后即使关掉模拟，也会命中一份不属于本机的结论。
- **`probe_hardware_snapshot` 不需要清缓存**：真实探测值恒存，模拟在**每次取用时叠加**。
  两者不对称是刻意的。
- **标定匹配仍用真实指纹**：标定结论是在真实硬件上测出来的，拿模拟档位去匹配只会得到
  不属于这台机器的参数。

### 行为变化（对用户可见）

- **修复"前端假象"**：`stores/system.ts` 此前在**浏览器里**改写 `caps.tier` 并写

### 明确未交付 / 诚实边界

- 模拟**只验证控制面**（判定 / 门控 / 链路 / 参数传递 / 界面态），**不代表真实性能**。
- T2/T3 的**数据面**（真实吞吐 / 峰值显存）仍无法在本机取得 —— 本机仍是单一样本。

- **"自动"档不再等于"保底档"**：标定完成后 `using_fallback` 变为 `false`，`source` 由

- **本机实测（RTX 3050 8G）**：`64 → 70ms / 941k px/s`、`128 → 179ms / 1466k`、

### 修复的缺陷（均为**真实产品缺陷**，不是测试问题）

- **CUDA 13 包布局导致 DLL 未注册 → 静默回退 CPU**：CUDA 13 的运行时 DLL 位于

- **`runtimes.module_version()` 查不到 GPU 版版本号**：`onnxruntime-gpu` 是**独立发行名**，

| **两格式正确拒绝** | `.pth` / `.safetensors` 报 `needs_convert` 并**指向离线转换**（真实加载属 T-807/S2）；单独 `.bin` 一律拒绝 |
| **可选后端可查询** | openvino / ncnn 缺失不是故障：返回**可展示的状态**（缺什么 + 一条可照做的安装建议），探测**不 import 重库**（不成为启动/列表的瓶颈） |
| **可判别的失败码** | `runtime_missing` / `file_missing` / `companion_missing` / `unsupported_format` / `needs_convert` / `load_failed` / `inference_failed`——每条都带 `reason` 与 `detail` |
| **模型输入约束读取** | 读 ONNX 输入形状，产出 `InputSpec`（动态 H/W / 静态固定边长 / 输入 dtype）。**永不抛异常**，读不到就如实说"读不出，不猜" |
| **真实推理编排** | 预处理 → 分块（`plan_tiles`）→ 逐块推理 → 羽化加权拼接 → 落盘；**协作式取消**（不留半个文件）；进度覆盖 `preprocessing / inferencing / stitching / saving` 四阶段 |
| **产物落库** | 输出写入 `ARTIFACT` 表（`kind=output`，含 `sha256` / `size_bytes`），对外 `path` 带 `data/` 前缀（与前端 Mock 约定一致） |
| **尺寸回填** | `TaskOut.output_width` / `output_height` 与产物宽高**由真实推理结果回填**（不再是恒 null 的占位） |
| **执行事实分层** | `resolved.execution` 记录**实际发生**的事（输出尺寸 / 块数 / 耗时 / 后端描述 / sha256），与 `resolved` 顶层的**决策事实**分开 |

### 行为变化（对用户可见）

- **任务不再"演"**：提交超分任务后产出的是磁盘上真实的图像文件，尺寸 = 原图 × 倍数，
  `sha256` 与文件实际内容一致。例：`100x80` 输入 → `tile=64 / overlap=16 / stride=48`，
  4 块（2×2），输出 `400×320`。
- **任务详情新增执行事实**：`resolved.execution` 与顶层的 `output_width/height` 有值；
  产物列表出现 `kind=output` 的条目（此前恒为空）。
- **`.pth`/`.safetensors` 会被明确拒绝**并提示"需离线转换为 ONNX"，而不是含混失败。
- **静态输入模型可正常运行**：如固定 `512×512` 输入的模型，tile 由模型约束确定
  （正好等于 512），不再因 `overlap` 退化而报错。

### 修复的缺陷

- **验证脚本的时序竞争**（T-804 回归中 1/132 偶发失败）：任务状态先落 `completed`，
  水位采样（起 `nvidia-smi` 子进程，百毫秒级）在其后，脚本却立刻断言。
  与 T-804 修过的并发槽竞态**同源**。已改为**轮询等待 ≤5s**。
- **四处验证脚本自身缺陷**：两处朴素子串检查把 docstring 里的说明文字
  （`` `engine/` 不 import fastapi / sqlalchemy / pydantic ``、``一次 `import openvino` ``）
  当成 import 语句**误报纯度违规**——与 T-804 踩过的同一坑，已改为**行首锚定正则**；
  一处测试夹具与自身描述矛盾（要验"决策 fp32"却复用了 fp16 的档位桩）；
  一处用了不存在的基准路径（导致断言在错误的失败码上）。
- **校验顺序缺陷**：原实现把"运行时未安装"排在"配套文件缺失"之前，会让一台没装
  openvino 的机器永远看不到"缺 `.bin` 配套"这个真问题，也让 companion 分支
  在应用环境**不可观测**。已改为**结构性校验先于环境性校验**，并加回归断言钉住。

### 明确未交付（诚实边界）

- **应用环境跑不出 GPU 加速**：`.venvs/sr-app` 装的是 CPU 版 `onnxruntime`（**部署决定**，
  非代码缺陷）。需要 CUDA 请换 `onnxruntime-gpu`。本任务证明的是"**加载器与编排正确**"，
  **不是**"这台机器已加速"。
  > ⚠️ **本条已于同日消解**：应用环境当晚换入 `onnxruntime-gpu[cuda,cudnn] 1.30.0`，
   > 真机 CUDA EP 生效（1024 节点 / CPU 0），档位 T1。详见上方 T-805 条目。
- **ncnn 仍是"条件支持"**：剩余条件是**具体模型的层覆盖需运行时校验**（加载失败即剔除），
  不是"后端能不能跑"（T-210 已关闭该问题）。
- **不是"四格式可加载"**：任务池原措辞按 PRD §2.7 切片修正为
  **"三格式可加载 + 两格式正确拒绝并指向转换"**。`.pth`/`.safetensors` 的真实加载属 T-807（S2）。
- **"能出图" ≠ "出得好看"**：验证用的是**合成图 + 基准模型**（尺寸正确、非全黑、非常量、
  sha256 一致）。**真实照片的人眼质量复核（"无可见接缝"）尚未做**，属 S1 闭环验收。
  **不要把"121/121 全绿"读成"画质已验收"。**
- **真实长任务下的资源争抢未验证**；P3 与实验性后端的独立子进程形态（ADR-005）未实现。

## 2026-10-09 · 引擎阶段 D/E 落地：参数决策、水位反馈与保底档（T-804）


**性质**：**新增功能（引擎控制面）**。首次让"这次任务用多大的块、什么精度、哪个后端"
变成**可解释、可降级、可追溯**的引擎结论；但**不产生图像**——真实推理由 `T-806` 接入。

### 新增能力

| 能力 | 说明 |
|---|---|
| **阶段 D 决策** | 每个任务产出一份 `RuntimeProfile`：`tile / precision / backend / overlap / feather_px / concurrency` + `using_fallback / degraded / reasons / downgrades / source` |
| **决策来源可追溯** | `source ∈ {calibration, user, fallback}`——标定命中 / 用户指定 / 保底档，界面"本次决策"直接可解释 |
| **因果性防御** | 四类硬约束**无条件执行**（不信任来源）：后端必须已验证、CPU 路径禁 fp16、fp16 需 `compute_cap ≥ 5.3`、tile 不低于下界且对齐模型倍数。触发即记 `downgrades` + `degraded=true` |
| **过渡区取值** | `overlap = feather_px = align_down(tile/4, align)`——沿用 T-802 质量对照实验验证过的 1:4 比例与"feather = overlap"交接契约 |
| **阶段 E 水位反馈** | 任务边界采样显存/物理内存，口径取**较大者**（T0 档的真瓶颈是内存）；连续 **2 次 > 85%** 触发下一次任务**降一档** |
| **OOM 降档链** | 识别资源耗尽类异常 → `tile` 折半（至下界 64）→ 后端 GPU→CPU（仅当 CPU 已验证）→ 耗尽报 `VRAM_INSUFFICIENT` / `RAM_INSUFFICIENT`；**只重试一次** |
| **保底档（§6.8）** | 未标定时的保守下界参数（下界 tile / `fp32` / 并发 1 / 已验证后端首项），**不写入**标定记录与模型元信息；界面必须可见"当前为保底档" |
| **决策可取证** | 诊断导出新增 `decision`（最近一次决策 + 保底档与水位策略）与 `watermark`（水位历史）两个区段 |

### 行为变化（对用户可见）

- 任务详情的 `resolved` 从**占位常量**变为**真实引擎决策**，并新增
  `overlap` / `feather_px` / `concurrency` / `source` 四个字段（挂账 T-700 契约补齐）；
- 任务失败时，资源耗尽类错误不再笼统报"推理执行失败"，而是区分
  `VRAM_INSUFFICIENT`（GPU 后端）与 `RAM_INSUFFICIENT`（CPU 后端），并在 `detail` 里带上
  已降档次数、生效后端与当时的资源水位；
- 连续高水位后，下一个任务的 `resolved.downgrades` 会明确写出"因连续 N 次水位超阈值而降档"；
- OOM 后会自动降一档重试一次，任务详情的进度提示会显示"资源不足，已降档（tile → 128）后重试"。

### 修复的缺陷

- **并发槽被观测动作占住**：水位采样需起 `nvidia-smi` 子进程（百毫秒级），原先排在
  终态落库之后、释放并发槽之前 → "任务已显示完成，但提交新任务仍返回 409
  `TASK_ALREADY_RUNNING`"。已改为终态落库后**立即释放并发槽**，观测与广播排其后。

### 明确未交付（诚实边界）

- **真实推理与真实产物**（`T-806`）：`resolved` 是**决策结果**，不是已发生的加速；
- **首启自标定**（`T-805`，属 S2）：标定消费路径已实现，但 S2 前 `calibration` 表恒为空，
  线上**永远**走保底档；
  > ⚠️ **本条已于同日消解**：`T-805` 已实现并跑通，本机已有**真实标定记录**（推荐 tile=256），
  > "自动"档 `using_fallback` 变为 `false`。详见上方 T-805 条目。
- **并发度生效**（G-06 / `T-907`）：`concurrency` 只是决策产物，调度仍为 **1**；
- **模型对齐倍数**：默认 8，真实取值待 `T-806` 读 ONNX 输入约束。
  > ✅ **T-806 已兑现**：`model_constraints()` 会读 ONNX 输入约束并**只收紧不放宽**；
  > 静态输入模型另走 `fixed_tile` 通道（要求"正好等于 N"，非倍数关系）。

## 2026-10-09 · 步骤 5D 引擎核心首项：M4 图像处理与分块羽化拼接（T-802）

### 功能层面的变化

- **新增能力**：任意尺寸图片 → 固定尺寸块序列 → **无可见接缝**拼接回原尺寸 × 放大倍数。

  且旁车元信息宽高是转正前的值）。

### 质量红线是怎么被证明的

"无可见接缝"若只靠肉眼看图，无法回归、也无法证伪。这里用的是**带判别力的对照实验**：

| 分组 | 边界峰比（接缝指标） |
|---|---|
| 硬切（无重叠拼贴，已知有接缝） | **63.0** ← 证明指标确实能测出接缝 |
| **本实现（overlap + feather）** | **1.3** ← 无孤立阶跃 |
| 逐像素推理器下与整图推理对比 | **逐像素精确相等（max abs diff = 0）** |

相对周围突然变大**。真实图像的人眼复核属 S1 闭环验收，需 T-806（模型加载器）就位后跑
真实 RealESRGAN。

## 2026-10-08 · 字体自托管（拉丁子集）

**性质**：消除「设计意图无法落地」的隐患。此前项目**未引入任何 webfont**，字体完全依赖系统安装。

### 问题

字体栈声明为 `Inter, "Noto Sans SC", system-ui, …`，但实测本机 **Inter 与 JetBrains Mono 均未安装** —— 界面实际渲染回退到第二顺位（Noto Sans SC / Cascadia Mono）。

后果不是「难看」（Noto Sans SC 的拉丁部分质量不错），而是**视觉验收不可复现**：换一台装过 Inter 的机器，字宽随之改变，换行位置与表格列宽跟着变。

### 处置

自托管两份**拉丁子集可变字体**，不依赖用户系统：

| 项 | 内容 |
|---|---|
| 文件 | `web/src/assets/fonts/` 下两个 woff2 |
| 声明 | 新建 `web/src/styles/fonts.css`（`@font-face` + `unicode-range`） |
| 引入 | `web/src/main.ts` 增加一行 `import './styles/fonts.css'` |
| 来源 | `@fontsource-variable` 5.3.0 —— **可变字体**，一个文件覆盖全部字重 |
| 子集 | **仅 latin** —— 界面无西里尔 / 希腊 / 越南字符，其余子集不打包 |

**体积**：Inter 47 KB ＋ JetBrains Mono 39 KB = **86 KB**（构建产物 48.25 + 40.40 KB）。

**中文不走 webfont**：`unicode-range` 把两个字体限定在拉丁字符，中文自动回退到系统的 Noto Sans SC。回退链：

```
拉丁字符 → Inter（自托管）         ｜  中文字符 → Noto Sans SC（系统）
技术数值 → JetBrains Mono（自托管）  ｜  其中的中文 → 系统字体
```

### 实测验证

| 检查项 | 结果 | 判定 |
|---|---|---|
| `document.fonts` | `Inter @100 900`、`JetBrains Mono @100 800` 均 loaded | ✅ |
| 顶栏 `WebSR`（纯拉丁 5 字符） | **Inter（webfont）** | ✅ 自托管生效 |
| 导航项（中文） | Noto Sans SC（系统） | ✅ 正确回退 |
| 档位徽标（数字/字母 8 字符） | **JetBrains Mono（webfont）** | ✅ 等宽生效 |

控制台零错误；构建通过（1687 模块）。
